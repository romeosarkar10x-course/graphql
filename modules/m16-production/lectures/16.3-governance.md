# 16.3 Governance

## Hook (2 min)

Four teams change one schema. Without rules, the review happens in chat, the field someone removes was used by
last year's iOS app, and nobody knows who owns `Club`. Governance is that knowledge, written down where every
pull request runs into it.

## Concept (15 min)

### Style guides

Naming (camelCase fields, PascalCase types), descriptions on everything public, money as minor units plus
currency, bounded lists, nullability rules (Module 7). Linters enforce the mechanical part (graphql-eslint,
Module 13.6). The rest is judgment, and it needs a reviewer.

### Review boards vs automated checks

A board catches shape problems and sets direction. It does not scale to every pull request, and it can become
the bottleneck. Automated checks scale but cannot judge. The common split:

- **automated**: lint, composition, breaking-change detection against usage (13.5);
- **people**: anything breaking, new top-level types, new public patterns;
- **escalation**: a board meeting only for disputes (game 16.9).

### Ownership metadata

GitHub's CODEOWNERS maps paths to owners. Split the schema into one file per type and ownership becomes per type.
With branch protection requiring code-owner review, a change to `Book.graphqls` cannot merge without catalog.
Federation does the same per subgraph (Module 15). Some teams add an `@owner` directive, so tools can read it
from the schema.

### Deprecate, measure, remove

1. **Deprecate** with a reason that names the replacement (`@deprecated(reason: "Use isbn13.")`) and a date in
   the changelog.
2. **Measure** usage per client and version over a window long enough for the slowest client (16.2).
3. **Remove** when it is zero, or when the remaining users are unsupported versions you can name. Do it as one
   breaking change, checked with a schema diff, with a changelog entry and a rollback.

`Club.memberCount` shows why measuring matters: it is deprecated too, but iOS 2.8.0 used it 22 times this week.

### Templates

A pull-request template turns the rules into yes/no questions:

- Breaking? With what evidence?
- Deprecated with a reason?
- Owners reviewed?
- Changelog written?

## Experiment (15 min)

Remove a deprecated field end to end with usage data as proof. Keep the other one, and say why in the changelog.

## Check

1. Why split the schema into one file per type for CODEOWNERS?
2. What makes a deprecation reason useful?
3. Which of the two deprecated fields can go, and what in the data decides it?

<details><summary>Answers</summary>

1. CODEOWNERS works on paths; one file per type makes ownership per type.
2. It names the replacement (and ideally a removal date), so clients know what to do.
3. `Book.isbn10`: its only user is a retired client version; `memberCount` is still used by a supported one.
