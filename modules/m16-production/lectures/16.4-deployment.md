# 16.4 Deployment

## Hook (2 min)

A rolling deploy of two replicas while 200 clients hold subscriptions. With nothing done about it, the clients
lost 1,318 messages (a second run: 1,429). After four small changes: 0 dropped, 0 duplicated, 0 failed queries
out of 4,166.

## Concept (15 min)

### Images

**Jib** (`jib-maven-plugin` 3.5.2) builds an OCI image from Maven without a Dockerfile or a Docker daemon. Probed:
`jib:buildTar` wrote a 159 MB image that runs as user 1000:1000. **Buildpacks**
(`spring-boot:build-image`) need a Docker daemon. Both put dependencies in their own layer, so a code change
pushes only a small layer.

### Probes

Actuator's health groups: `/actuator/health/liveness` (restart me if this fails) and `/actuator/health/readiness`
(send me traffic). Boot enables them automatically on Kubernetes; elsewhere set
`management.endpoint.health.probes.enabled`. Liveness should not include dependencies: a down database must not
make Kubernetes restart every pod.

### Graceful shutdown, in order

1. Readiness goes `REFUSING_TRAFFIC` (`AvailabilityChangeEvent`).
2. Wait longer than the load balancer needs to notice. Kubernetes uses a `preStop` sleep or an in-app drain. With
   a 1 s propagation, a 1 s drain still lost one query; 2 s lost none.
3. While draining, answer with `Connection: close`: kept-alive connections bypass the balancer.
4. Complete subscriptions, so clients reconnect elsewhere at once.
5. `server.shutdown=graceful` finishes in-flight requests, up to `spring.lifecycle.timeout-per-shutdown-phase`.
6. `terminationGracePeriodSeconds` must be longer than all of that.

### Subscriptions need a cursor

No shutdown order saves messages published while a client reconnects. The client has to say where it was
(`reviewAdded(after: $lastSeq)`), and the server has to serve what was missed, then the live feed. The order
matters. Listen first, then fetch the past, then drain the buffer, dropping by `seq`, so nothing falls in between.

### Config

Environment variables map onto properties (`SHELFIE_REVIEWS_URL` → `shelfie.reviews.url`). Secrets come from the
platform, never from the image.

### Native images and CRaC

GraalVM native images (Module 6, `bin/course native`) start in milliseconds and use less memory, at the cost of
long builds, reflection hints and no JIT peak. CRaC restores a warmed JVM from a checkpoint. It needs a JDK built
with CRaC, and care with sockets and secrets in the snapshot; the course does not run it. Both help scaling out,
not a rolling deploy whose start takes about 2 s of a 10 s cycle.

## Experiment (15 min)

Roll a deploy while 200 subscriptions are open; count dropped messages. Add one change at a time.

## Check

1. Why does graceful shutdown alone not prevent dropped subscription messages?
2. Why wait after flipping readiness instead of stopping at once?
3. Why should liveness not check the reviews service?

<details><summary>Answers</summary>

1. Messages published while a client is reconnecting reach no socket; only a resume cursor recovers them.
2. The balancer learns about readiness late; until then it still sends new connections to the stopping pod.
3. A dependency outage would restart every pod, which fixes nothing and adds load.

</details>
