# 16.5 Reliability

## Hook (2 min)

The reviews service gets slow: 2 s per call. Shelfie's club page waits for it, so every page takes 2 s; p95 2,002
ms. Add a 500 ms timeout, a circuit breaker and a bulkhead, and the same minute reads p95 3 ms, p99 502 ms. The
page loses its reviews for a while, nothing else.

## Concept (15 min)

### One query, many dependencies

A GraphQL response is assembled from many fetchers. The slowest dependency sets the latency of every query that
touches it, and a slow dependency holds threads, connections and memory while it waits. GraphQL has one advantage
over REST here: **partial results**. A nullable field can fail alone, with an error at its path, and the page
renders without it (Module 8's error design).

### The defences

- **Timeouts** per dependency, shorter than the client's own patience. A long poll (the subscription feed)
  needs its own client with its own limits.
- **Circuit breaker** (Resilience4j): count failures and slow calls in a sliding window. Past a threshold, stop
  calling for a while (open), then let a few through (half-open). It spares a struggling service and answers
  fast while the service is down. Probed: 27 calls reached the slow service in its 4 slow seconds, from 400 pages.
- **Bulkhead**: cap concurrent calls to one dependency, so it cannot take every thread or connection.
- **Load shedding**: refuse early (429/503, or a cost budget, Module 10.6) when the whole server is past its
  capacity, rather than queueing everyone into timeouts.
- **Graceful degradation**: decide per field what "unavailable" looks like. Here, `reviews: null`,
  `averageRating: null` and `extensions.code: REVIEWS_UNAVAILABLE`, so clients can show "reviews unavailable"
  instead of an error page.

### Request cancellation

When the client gives up, the server should stop too. graphql-java can abort an execution
(`ExecutionInput.cancel()`, Module 8), and fetchers can check for it. Timeouts per field bound the work for one
field; cancellation bounds the whole request.

### Measure with an open model

A closed-loop load test (N workers, each waiting for its answer) slows down with the server. In the probe it
reported p95 4 ms through a 2 s outage, because the workers were stuck and sent almost nothing. An open model
sends requests on a schedule, as independent users do, and counts latency from when each request was due.
`contract/Peak.java` does that.

## Java build (25 min)

Lab 16.5: timeouts, Resilience4j breaker and bulkhead around `ReviewsClient`, and `REVIEWS_UNAVAILABLE` errors on
the reviews fields only.

## Experiment (15 min)

Kill the reviews dependency at peak (100 club pages a second); keep p95 under 250 ms. Then remove one defence at a
time and watch which number moves.

## Check

1. Why does a timeout alone not protect a struggling dependency?
2. Why must `Book.reviews` be nullable for this design?
3. Why did the closed-loop test hide the outage?

<details><summary>Answers</summary>

1. Every request still calls it and waits up to the timeout; a breaker stops calling once it is clearly failing.
2. A non-null field's error propagates to its parent, taking the book (and maybe the page) with it.
3. Its workers waited on slow responses and sent few requests, so few slow samples were recorded.

</details>
