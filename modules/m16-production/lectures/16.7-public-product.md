# 16.7 GraphQL as a public product

## Hook (2 min)

Inside one company, a breaking change is a pull request and a message in chat. With partners, it is a contract.
Shopify releases a new API version every quarter, supports each for at least 12 months, and gives partners at
least nine months with two versions side by side. Its partners plan around those dates.

## Concept (15 min)

### Versioning a "versionless" API

GraphQL's default is evolution without versions: add, deprecate, remove when unused (16.3). That works when you
can see and reach every client. For a public API, removal by usage data alone leaves partners exposed to changes
on your schedule. Dated versions give them a schedule of their own.

Shopify's policy, from its documentation (shopify.dev, API versioning, read 2026-11-22):

- versions are named by date (`2026-04`), released quarterly at 5 pm UTC on the first day of the quarter;
- each stable version is supported for a minimum of 12 months, with at least nine months of overlap between
  consecutive versions;
- the version is in the request URL. A request for a retired version **falls forward**: it is answered by the
  oldest version still accessible.

Each version is its own schema (`2026-10.graphqls`, `2027-01.graphqls`). The server serves several at once, and a
schema diff between consecutive versions is the changelog's skeleton.

### The paperwork is the product

- **Changelog**: dated, newest first; breaking changes under their own heading, each with its replacement.
- **Migration guide**: per breaking change, the operation before and after, validated against both schemas.
- **Announcement**: who is affected, what to do, concrete dates (announcement, release, reminder, retirement),
  what happens after the last date. Usage data says who to tell; its limits say what not to promise.
- **SDKs and sandboxes**: generated clients per version (Module 12); a sandbox where the next version is already
  live, so partners can test before the release.
- **Docs**: descriptions on everything, rendered (Module 13.7), with examples that are tested.

Netflix's federated graph (more than 200 services by 2023, InfoQ) is internal. Its clients ship with the company,
so evolution by usage works there. The same tools serve both models; the policy differs by audience.

## Check

1. When are dated versions worth their cost over pure evolution?
2. What does "falls forward" mean for a partner who never upgrades?
3. Why validate the migration guide's queries?

<details><summary>Answers</summary>

1. When clients are outside your release cycle (partners, public apps) and need dates to plan around.
2. Their requests are served by the oldest supported version, so removed fields start failing validation.
3. A guide with a broken "after" query wastes every reader's time and undermines the announcement.
