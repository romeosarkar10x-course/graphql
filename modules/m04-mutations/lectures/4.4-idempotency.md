# 4.4 Idempotency, concurrency, bulk

## Hook (2 min)

Fifty identical `createReview` requests with one idempotency key, from 50 virtual threads at once, against
a check-then-insert implementation: 50, 48, 46 reviews in three runs (lab 4.4's starter). With the key
claimed by a primary key in the same transaction: 1, 1, 1.

## Concept (15 min)

### Idempotency keys

The client generates a unique key per *intended* action (a UUID) and reuses it for every retry. The
server stores key → result, atomically with the effect. A repeat returns the stored result; the same key
with a different input is an error. Stripe's API popularised it (keys kept at least 24 hours). The
database, not a JVM lock, must be the referee: several instances, restarts.

### Optimistic locking

`renameClub(input: {clubId, name, expectedVersion})` → `UPDATE clubs SET name = ?, version = version + 1
WHERE id = ? AND version = ?`. One row changed: you won. Zero: someone changed it since you read it;
return a `CONFLICT` error with the current version. JPA's `@Version` generates exactly this. GitHub's
`mergePullRequest(expectedHeadOid:)` is the same idea (game 4b).

### Partial success and bulk

A batch mutation must say what happened to each item: all-or-nothing (one error rejects the batch), or
per-item results (`deletedIds` plus `userErrors` with the item's index in `field`). Pick one, document it.

### Long-running work

Do not hold a request open for minutes: create a job row, start the work elsewhere
(`CompletableFuture.runAsync(..., executor)`, a queue), return `job { id status }` at once; clients poll
`job(id)` (or subscribe, Module 11). The job-creating mutation needs an idempotency key too.
