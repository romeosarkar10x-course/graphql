# 4.6 File uploads

## Hook (2 min)

Twenty users upload 50 MB covers through a GraphQL multipart endpoint that reads each part into a byte
array: a gigabyte of heap in the API server, for bytes it only passes to storage. The client in lab 4.6's
starter needs 219.5 MB of heap to send one of them.

## Concept (15 min)

### GraphQL has no file type

The spec carries JSON values only. Two designs:

| | Multipart request convention | Pre-signed URLs |
|---|---|---|
| Spec | community spec (jaydenseric/graphql-multipart-request-spec), not GraphQL | your API's design |
| Requests | 1 | 3: `createCoverUpload`, `PUT` to storage, `confirmCoverUpload` |
| Bytes pass through the API server | yes | no |
| Server support | DGS; Apollo Server via the separate graphql-upload package; Spring for GraphQL: no (the reference server implements it in ~60 lines) | any server that can sign a URL |
| CSRF exposure | yes, unless guarded | no (JSON mutations) |

### The multipart convention

`multipart/form-data` with parts in order: `operations` (the request JSON, `null` where files go),
`map` (`{"0": ["variables.file"]}`), then each file part. The server replaces each `null` with the
file and executes; the `Upload` scalar accepts only those.

### CSRF

A `multipart/form-data` POST is a CORS "simple request": a malicious page can auto-submit a form to your
`/graphql` with the victim's cookies, and the browser sends it with no preflight. Require a header no form
can set (`GraphQL-Require-Preflight`, Apollo's `Apollo-Require-Preflight`); the browser then preflights.

### Pre-signed URLs

The server signs a short-lived URL for one object, method and content type (S3 SigV4, here via AWS SDK
v2's `S3Presigner` against SeaweedFS; MinIO no longer publishes container images). The client uploads
straight to storage; the server checks the object on confirm. New failure modes: uploads never
confirmed (orphans, a lifecycle rule), expiry mid-upload.

### Streaming in Java

`HttpRequest.BodyPublishers.concat(ofString(head), ofFile(path), ofString(tail))` sends a file of any
size in constant memory; `readAllBytes` holds it all, and a `ByteArrayOutputStream` copies it again.

## Java build (20 min)

Lab 4.6: one Java client, both ways, streaming, at 48 MB of heap. (The plan names DGS or
multipart-spring-graphql on the server side; the reference server implements the convention directly
so the course stays on Spring for GraphQL, and Module 6 revisits DGS's support.)

## Experiment (15 min)

Upload a 50 MB cover both ways; watch heap with JDK Flight Recorder; compare `serverBufferedBytes`.

## Check (3 min)

1. Why is a JSON-only GraphQL endpoint not exposed to the same CSRF attack?
2. Which mode keeps the API server's memory independent of file size?

<details><summary>Answers</summary>

1. `application/json` is not a simple content type: the browser preflights, and CORS refuses a foreign
   origin.
2. Pre-signed URLs (`serverBufferedBytes` 8192 in the reference server: it streams the confirm check).
</details>
