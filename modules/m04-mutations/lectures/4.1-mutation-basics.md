# 4.1 Mutation basics

## Hook (2 min)

`mutation { a: withdraw(amount: 50) b: withdraw(amount: 70) }` against a balance of 100. If those two
fields ran at the same time, both could succeed. The spec says they cannot: root mutation fields run
one after another, in document order. Query fields get no such promise.

## Concept (15 min)

### Same language, different execution

A mutation is written like a query. The differences are in execution
([spec: Normal and Serial Execution](https://spec.graphql.org/September2025/#sec-Normal-and-Serial-Execution)):

| | Query | Mutation |
|---|---|---|
| Root fields | "normally": may run in parallel, any order | **serially**, in document order, each finished before the next starts |
| Nested fields | normally | normally (only the root is serial) |
| graphql-java strategy | `AsyncExecutionStrategy` | `AsyncSerialExecutionStrategy` |

"May run in parallel" needs fetchers that return a `CompletableFuture`. A fetcher that blocks the
calling thread finishes before graphql-java dispatches the next field, so even a query runs serially.

### Select data back

A mutation's return type is an ordinary object type: select into it. `joinClub` returning
`club { memberCount }` lets the client update every screen showing that club, by id, from the same
response: no follow-up query, no race between the write and the re-read. Normalised caches (Apollo,
Relay; Module 12) depend on it.

### Who is calling?

The reference server takes the acting user from an `X-Shelfie-User` header (a stand-in until Module 10).
Identity never travels in the mutation's arguments.

## Check (3 min)

1. `mutation { joinClub(...) { ... } leaveClub(...) { ... } }`: which runs first?
2. Three async root fields in a query take 200 ms each. Expected total?

<details><summary>Answers</summary>

1. `joinClub`, and `leaveClub` starts only after it completes: document order.
2. About 200 ms (measured: 228 ms), if the fetchers return futures on a pool with free threads.
