# 4.2 Inputs and payloads

## Hook (2 min)

`addReview(bookId: ID!, rating: Int!, text: String!, userId: ID!): Boolean`. Four problems in one line:
positional arguments, the client says who it is, a `Boolean` that answers neither "which review?" nor
"why not?", and nowhere to put an error. Lab 4.2 has five of these.

## Concept (15 min)

### The conventions

| Convention | Why |
|---|---|
| One argument, `input: XInput!` | One variable on the client; add fields without touching call sites; validate one object |
| A dedicated `XPayload!` per mutation | Room to grow: the changed object, related objects, errors |
| Payload carries the changed data | Client caches update from the response (4.1) |
| `userErrors: [UserError!]!` (or a result union, 4.3) | Domain failures are data |
| Verb first, camelCase: `createReview`, `joinClub` | Reads as an action; groups by verb in docs. (Shopify uses noun first, `productCreate`, to group by type: pick one and be consistent) |
| No identity in inputs | The server knows the caller; a `userId` argument is an authorisation bug waiting |
| Enums for closed sets | `status: ReadingStatus!`, not `String` |

### `clientMutationId`: history

Relay Classic required every mutation input to carry `clientMutationId` and every payload to echo it, so
a client could match responses to requests. Relay Modern dropped the requirement; HTTP already pairs
requests and responses. GitHub's schema still has it on every mutation (game 4b). New schemas: leave it out.

### Patch inputs: absent vs null

`updateClub(input: {clubId: "c1", description: null})` means "clear the description";
`{clubId: "c1"}` means "leave it". GraphQL keeps the difference (the key is present or not), and a Java
record must too: `Optional<String>` with `null` = absent, `Optional.empty()` = cleared,
`Optional.of(v)` = set. (Spring for GraphQL's `ArgumentValue<T>` does the same, Module 6.)
