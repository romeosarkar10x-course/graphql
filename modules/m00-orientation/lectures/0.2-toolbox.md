# 0.2 Your Java toolbox

## Hook (2 min)

"Works on my machine" in a GraphQL course usually means one of three things: a different JDK, a
different library version, or a server that was not running. This course removes the first two by
running everything in one Docker image, and gives you a doctor for the third.

## Concept (15 min)

### What runs where

| Where | What | Why |
|---|---|---|
| Your machine | Docker, bash, git, a browser, an IDE | That is all you install |
| Course image `graphql-course:1` | JDK 25, Maven 3.9.16, Hurl, grpcurl, jq | One toolchain for everyone; versions in [VERSIONS.md](../../../VERSIONS.md) |
| Compose services | reference Shelfie, Toxiproxy | Started by `bin/course ref up` |

You may install JDK 25 and Maven locally for your IDE (SDKMAN: `sdk install java 25-tem`,
`sdk install maven 3.9.16`). Grading always runs in the image.

### Maven in 10 minutes

Maven builds a project from one file, `pom.xml`. The parts you need now:

```xml
<project>
  <groupId>dev.shelfie</groupId>          <!-- who -->
  <artifactId>setup-doctor</artifactId>   <!-- what -->
  <version>1</version>
  <properties>
    <maven.compiler.release>25</maven.compiler.release>  <!-- compile for Java 25 -->
  </properties>
  <dependencies> ... </dependencies>      <!-- libraries, downloaded from Maven Central -->
  <build><plugins> ... </plugins></build> <!-- extra tasks, e.g. exec-maven-plugin to run main() -->
</project>
```

- **Lifecycle phases** run in order: `validate → compile → test → package → verify → install`.
  `mvn package` runs every phase up to `package`. `mvn verify` is what CI runs.
- **Plugin goals** run one task: `mvn exec:java` (run `main`), `mvn dependency:tree`.
- **Coordinates** `groupId:artifactId:version` name every library. A **BOM** (bill of materials) is
  a pom that pins a whole family of versions. Spring Boot's BOM is why `reference/shelfie-ref/pom.xml`
  lists `spring-boot-starter-graphql` without a version: Boot 4.2.0 chose graphql-java 26.1 for you.
- **The Maven Wrapper** (`./mvnw`) pins the Maven version per project and downloads it on first use.
  Commit `mvnw` and `.mvn/`; run `./mvnw` instead of `mvn` so everyone builds with the same Maven.

Inside the image, Maven's downloads go to `.cache/m2/` in the repo, so they survive between runs.

### GraphQL tools you will meet

| Tool | Use |
|---|---|
| **GraphiQL** (6.0.1 ships with Spring for GraphQL 2.1) | In-browser editor with autocomplete and a docs pane: http://localhost:8080/graphiql |
| **Altair**, **Bruno** | Desktop clients: saved collections, headers, environments. Install one if you like; optional |
| **IntelliJ GraphQL plugin** | Autocomplete and validation for `.graphql` files against a schema, configured by `graphql.config.yml` (Module 13) |

## Java build (20 min)

Lab 0.2: write your own doctor in Java. It checks the JDK version, that `hurl` and `jq` run, that the
reference server is healthy, and warns about a missing `GITHUB_TOKEN`. You meet `pom.xml`, the
wrapper, `ProcessBuilder` and `java.net.http.HttpClient`, which lecture 0.4 uses again.

## Experiment (10 min)

Break one tool on purpose (hide `hurl` from `PATH`, stop the server) and read your doctor's message.
A good FAIL line says what is wrong **and** what to do. Compare yours with `bin/course doctor`'s.

## Check (3 min)

1. You run `mvn test`. Does `compile` run? Does `package`?
2. Why does `reference/shelfie-ref/pom.xml` not state graphql-java's version anywhere?
3. Your `ProcessBuilder("hurl", "--version").start()` throws. What does that tell you, and what
   does it *not* tell you?

<details><summary>Answers</summary>

1. `compile` yes (phases up to `test` all run), `package` no.
2. The Spring Boot parent's BOM manages it (26.1 for Boot 4.2.0), consistent with Spring for GraphQL 2.1.
3. An `IOException` from `start()` means the executable was not found or could not be started. It
   says nothing about whether `hurl` works; that needs the exit code of a successful start.
</details>
