# 0.4 One request under the hood

## Hook (2 min)

GraphQL client libraries can look like magic: codegen, caches, hooks. Underneath, nearly every
GraphQL request is one HTTP POST with a small JSON body. You will send one with nothing but the JDK.

## Concept (15 min)

### The request

The [GraphQL-over-HTTP spec](https://graphql.github.io/graphql-over-http/draft) (a separate GraphQL
Foundation spec, still a draft) standardises what servers had converged on:

```http
POST /graphql HTTP/1.1
Content-Type: application/json
Accept: application/graphql-response+json, application/json

{
  "query": "query CurrentBook($clubId: ID!) { club(id: $clubId) { currentBook { title } } }",
  "variables": { "clubId": "c1" },
  "operationName": "CurrentBook"
}
```

| Body key | Required | Meaning |
|---|---|---|
| `query` | yes | The GraphQL document, as a string |
| `variables` | no | Values for the `$variables` the operation declares |
| `operationName` | no | Which operation to run when the document has several (2.7) |
| `extensions` | no | Extra, implementation-defined data (e.g. persisted query hashes, 9.6) |

**Variables** keep values out of the query text. Never build a query with string concatenation; lab 2.2
shows how that turns into injection.

### GET is optional

Servers **must** accept POST and **may** accept GET (`/graphql?query=...`); GET is only ever for
queries, never mutations. Spring for GraphQL does not accept GET by default: it answers `405`.
That is compliant. GET matters later for CDN caching (Module 9.6).

### The response and its media type

The body is the spec's response map: `data`, `errors`, `extensions`. The status code depends on
what the client accepts:

| Situation | `Accept: application/json` (legacy) | `Accept: application/graphql-response+json` |
|---|---|---|
| Valid query | 200 | 200 |
| Invalid query (fails validation) | **200** with `errors` | **400** with `errors` |
| Not GraphQL at all (no body, bad JSON) | 400 | 400 |
| Wrong request media type (`text/plain`) | 415 | 415 |

Measured against the reference server on 2026-11-21. With the legacy type, a status code tells you
almost nothing; the new media type lets 4xx mean "your request was bad", which proxies and
dashboards understand. Lecture 0.1's hook was this table.

### Java pieces

- `java.net.http.HttpClient`: the JDK's HTTP client (since Java 11).
- Jackson 3 (`tools.jackson.databind`, used by Spring Boot 4): `JsonMapper.builder().build()`,
  `writeValueAsString(Map)` to build the body, `readTree(String)` and `JsonNode.at("/data/...")` to
  read it. Jackson 3 exceptions are unchecked, which suits jshell.
- **jshell gotcha:** jshell ends a statement at the end of any line that is already complete, so a
  builder chain must keep the `.` at the end of each line, not the start of the next.

## Experiment (10 min)

Send `{ hello }` as a GET, with `Content-Type: text/plain`, and with no body. Record the status codes.
Then send `{ nope }` with each `Accept` header. Every number in the table above is yours to reproduce.

## Check (3 min)

1. What is the minimum JSON body for `{ hello }`?
2. A colleague's client sends `Content-Type: text/plain` because "it avoids a CORS preflight". Why
   might a server *want* to reject that?

<details><summary>Answers</summary>

1. `{"query":"{ hello }"}`.
2. Browsers send `text/plain` POSTs cross-origin without a preflight, so a server that accepts them
   can be driven by any website the user visits (CSRF). Rejecting non-JSON bodies closes that door
   (Module 10.3).
</details>
