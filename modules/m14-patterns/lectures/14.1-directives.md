# 14.1 Custom schema directives

## Hook (2 min)

`email: String! @mask` in the schema, and every email in the API is masked: clients see the rule in the SDL,
reviewers see it in the diff, the resolver stays `return user.email()`. Then someone writes `@currency @mask` the
other way round and a price disappears. Order matters, and the spec says so.

## Concept (15 min)

### Behaviour declared in SDL

Type-system directives annotate schema elements (`directive @mask(keep: Int = 4) on FIELD_DEFINITION`); the
server gives them meaning. They show in the SDL and in `__schema { directives }` (definitions, not where they are
applied: introspection does not expose applied directives). Spec: [Type System
Directives](https://spec.graphql.org/September2025/#sec-Type-System.Directives) and "Directive Order Is
Significant" (2.13): two orders may mean different things. A directive may be `repeatable`
([RFC #472](https://rfcs.graphql.org/rfcs/472/), merged 2020-01-10, first in the October 2021 edition); without it,
"Directives Are Unique per Location". The [Metadata Directives proposal](https://rfcs.graphql.org/rfcs/wg1096/)
(wg#1096, RFC 0, strawman since 2022) would mark a directive definition as metadata and expose its uses in
introspection, so tools could rebuild the SDL with the directives in place.

### graphql-java: SchemaDirectiveWiring

`RuntimeWiring.Builder.directive(name, wiring)`; graphql-java calls `onField` once per field and directive **while
building the schema**. The idiom: read the arguments, get the field's data fetcher from the code registry, register
one that wraps it. Two consequences:

- **Validation at start-up.** Throwing in `onField` stops the server, naming the field: `@uppercase` on a Float
  never reaches a request (lab 14.1's grader runs three broken schemas).
- **Order is wrapping.** Directives are wired in the order written; each wraps what it finds, so the first written
  sits nearest the resolver and transforms first. Probed: `@currency(code: "GBP") @mask(keep: 2)` gives
  `*******62`; `@mask(keep: 2) @currency(code: "GBP")` hands the conversion `***50`, a field error.

In Spring for GraphQL the wiring goes in a `RuntimeWiringConfigurer` bean. A value the directive cannot handle
should become a `DataFetcherResult` with an error: a thrown exception becomes Spring's opaque `INTERNAL_ERROR`.

### Directive or code

Good fits: presentation rules on many fields (`@mask`, `@uppercase`), metadata for tools (`@deprecated`,
`@specifiedBy`). Poor fits: rules that need the viewer and the data ("only the author"), anything that changes the
type, hidden I/O (`@currency` with live rates is a network call in the schema). Lab 14.6 gives `@mask` an owner rule
by reading the context, which is as far as it should go.

## Experiment (15 min)

Stack two directives on one field; does order matter? `Experiment.currencyThenMask` and `maskThenCurrency`, then
`@uppercase @mask` (which commute, and look harmless). Game 14.9's `@emojify @pirate` is the playful version.

## Check

1. When does graphql-java call `SchemaDirectiveWiring.onField`, and why does that matter for misuse?
2. Two directives on one field: which one sees the resolver's value first?
3. Why is `@auth(role: "admin")` fine but "only the review's author may see this" not a good directive?

<details><summary>Answers</summary>

1. Once per field and directive while the schema is built, so a misused directive can fail the start-up with the
   field's name instead of failing (or not) on some request.
2. The first one written: each wiring wraps the data fetcher it finds, so later directives wrap earlier ones.
3. A role is a property of the request alone; authorship needs the object and maybe a lookup, which belongs in
   the resolver or service where it can be tested with the data.
