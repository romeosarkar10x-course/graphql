# 14.4 GraphQL over existing systems

## Hook (2 min)

The book page needs one query. The catalogue is REST, reviews are gRPC, and the cover comes from Open Library,
which is someone else's and was 0.7 to 0.9 s per call when we recorded it. Switch Open Library off. Does the page
still render?

## Concept (15 min)

### Backend-for-frontend

A GraphQL layer that owns no data: each field resolves from the system that has it, and the schema is shaped for
the screen, not for the services. Clients make one request; the BFF makes the calls, close to the services. It is
also where the REST payload's long synopsis stops: the BFF reads it, the client never downloads it.

### Wrapping REST, gRPC and SOAP

- **REST**: Spring's `RestClient`. In Boot 4 there is no auto-configured `RestClient.Builder` without the
  `spring-boot-starter-restclient` (probed: "required a bean of type RestClient$Builder"); `RestClient.builder()`
  needs none.
  A 404 is an answer (null), not a failure.
- **gRPC**: stubs generated from the service's own `.proto` by `protobuf-maven-plugin` and `protoc-gen-grpc-java`
  (grpc-java 1.84.1, from the Boot BOM). Every call gets a deadline (`withDeadlineAfter`); `NOT_FOUND` is an answer.
- **SOAP**: JAX-WS or Spring Web Services clients generated from the WSDL; the resolver shape is the same. Not run in
  the course: there is no SOAP service to call.

### Resilience: one field, not the page

Make failure partial: one resolver per source, nullable fields where the source can fail, an error with a code
(`UPSTREAM_UNAVAILABLE`) on that field's path. Then the three defences, in order:

1. **Timeouts**: connect and read. Without them a hung upstream hangs every page.
2. **A circuit breaker** (Resilience4j 2.4.0): when half the recent calls failed, stop calling for a while, then let
   a few trial calls through. It protects the upstream and spares every page the timeout.
3. **A strict reading**: a 200 with an HTML maintenance page is a failure, not data.

And politeness: Open Library asks API users to identify themselves; a `User-Agent` naming the app is the minimum.

### Third-party data is messy

From the recording: Piranesi has no cover, The Remains of the Day no page count, one ISBN is filed as "The
dispossessed", the search lists Klara and the Sun as first published in 2019 and The Buried Giant in 2001. An
unknown ISBN is `{}` with 200. Nullable fields and "as Open Library has it" in descriptions are honest schema design.

## Experiment (15 min)

Wrap Open Library as `Book.openLibrary` and kill it: the grader's fake (recorded responses) hangs for 5 s, answers
HTML, answers 503 for twenty pages, then recovers. The page must answer within 1.5 s every time.

## Check

1. Why should `openLibrary` be nullable when `title` is not?
2. A timeout alone handles a down upstream. What does a breaker add?
3. Open Library answers 200 with an HTML page. Failure or data?

<details><summary>Answers</summary>

1. Open Library can fail independently; a nullable field lets the rest of the page survive (null plus an error),
   while a non-null field would null its parent. The catalogue is the page's reason to exist.
2. It stops calling: pages stop paying the timeout, and the struggling service gets room to recover; half-open
   trials find out when it is back.
3. Failure: the contract is a JSON object; treating anything else as data produces nonsense or a parse error deep
   in a resolver.

</details>
