# 14.7 Dynamic and multiple schemas

## Hook (2 min)

An admin adds a column to a table. A minute later clients can query it, with a description, and nobody restarted
anything. Meanwhile a second endpoint in the same JVM, with its own schema, is the only one that can change it.

## Concept (15 min)

### Schemas from metadata

A schema is a value: `GraphQLSchema` can be built in code (`GraphQLObjectType.newObject()`, field definitions, a
`GraphQLCodeRegistry` of data fetchers) or by generating SDL text and parsing it (`SchemaParser` plus
`SchemaGenerator`), which is easier to read and to print. Metadata (tables of types and fields) becomes the schema;
rows that make no sense (no such column, a name GraphQL refuses, an unknown type) are skipped with a warning, never
fatal. Uses: per-customer custom fields, CMS content types, admin tools, GraphQL over a database's own catalogue.

### Hot reload

In Spring for GraphQL, `/graphql` is built around one `GraphQlSource` bean (Boot creates one from schema files only
when there is none). A `GraphQlSource` of your own, holding the current `GraphQL` in an `AtomicReference`, can swap
it whole: Spring asks for it on every request, so a request runs on one schema from start to end. Probed in lab
14.7: 150 queries during six swaps, none failed. Triggers: poll a fingerprint of the metadata (simple), PostgreSQL
`LISTEN/NOTIFY`, or the admin mutation itself.

### Several endpoints in one JVM

The second endpoint is what Boot does for the first, by hand: `GraphQlSource.schemaResourceBuilder()` with its own
schema and wiring, `DefaultExecutionGraphQlService`, `WebGraphQlHandler`, `GraphQlHttpHandler`, and a
`RouterFunction` route. Do not make it a bean, or Boot's auto-configuration backs off the public one. Separate
schemas mean the public API has no admin mutations to discover, and the admin key is checked before GraphQL runs.

### The cost of dynamic

Clients generate code from a schema; fields that appear at run time have no client, and fields that disappear break
clients with no build to warn anyone (Module 13's schema checks cannot see them). Keep the core domain in reviewed
SDL; make dynamic only what users define. graphql-java's good-faith introspection check (on by default through
Spring) also limits what a client may ask in one request: probed, two `__type` fields, or `fields` under both
`queryType` and `mutationType`, are refused as `BadFaithIntrospection`.

## Experiment (15 min)

Add a column in the admin table; see the new field appear without a restart: the grader does it with plain SQL,
checks the process id, adds nonsense rows, and runs traffic during swaps.

## Check

1. Why swap a whole `GraphQL` instance instead of changing the schema in place?
2. What happens to Boot's `/graphql` if you declare the admin `GraphQlSource` as a bean?
3. Name one thing a dynamic schema breaks for clients.

<details><summary>Answers</summary>

1. Schemas are immutable; a new instance per change means each request sees one consistent schema, and requests in
   flight finish on the old one.
2. Boot's auto-configuration builds `/graphql` around the one `GraphQlSource` bean there is; with the admin source
   as a bean too, there are two, and nothing says which one the public endpoint should serve.
3. Code generation and schema checks: generated clients do not know new fields, and removed fields fail at run time
   with no build-time warning.

</details>
