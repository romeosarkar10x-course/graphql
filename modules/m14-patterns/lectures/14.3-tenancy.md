# 14.3 Multi-tenancy

## Hook (2 min)

`club(id:)` filters by tenant. `search` does not, `node(id:)` does not, a shared book's `clubsReading` does not, and
a cache keyed by id serves whoever asked first. One forgotten `WHERE` is a data breach. Make the database refuse.

## Concept (15 min)

### Where the tenant comes from

From the verified token (a `tenant` claim) or the hostname, never from anything the client types: a header or an
argument is an attacker's choice. No tenant, no data (`UNAUTHORIZED`). Put it in the `GraphQLContext` once, in an
interceptor, and read it everywhere.

### Isolation: three models

Database per tenant (strongest, costly to run), schema per tenant (search_path switching, migrations times N),
shared tables with a `tenant_id` (cheapest, and every query must filter). The third needs a floor under it:
**PostgreSQL row-level security**. A policy `USING (tenant_id = current_setting('app.tenant', true))` filters every
statement on the table; `WITH CHECK` refuses writes for another tenant.

Pitfalls, all probed in lab 14.3's workbench:

- A **superuser bypasses RLS** entirely (the course's `shelfie` user is one); a table's **owner** bypasses it unless
  `FORCE ROW LEVEL SECURITY`. Run requests as a plain role: `SET LOCAL ROLE m14_tenant` in each transaction.
- **LOCAL** settings (`set_config(..., true)`) end with the transaction, so a pooled connection never carries one
  tenant into the next request.
- **Fail closed**: with no `app.tenant`, the comparison is with NULL and no row matches.
- **Foreign key checks do not see policies**: probed, acme inserted a membership pointing at globex's club through
  a single-column key. A composite key `(tenant_id, club_id)` closes it.
- Anything outside the database (caches, search indexes, files) needs the tenant in its key.

### Per-tenant schema visibility

Plans differ: premium tenants have `Club.analytics`. graphql-java asks `Instrumentation.instrumentSchema` for the
schema of each execution, before parsing and validation; return a transformed schema (`SchemaTransformer`, fields
deleted) for basic tenants, built once per plan. Probed: the field vanishes from introspection and a query that
selects it fails validation. It is a product boundary, not a security one: resolvers must still check.

## Java build (20 min)

Lab 14.3: tenant from the JWT, `TenantDb` (role and setting per transaction), RLS policies and a composite foreign
key in `schema.sql`, `instrumentSchema` for the plan.

## Experiment (15 min)

Try to read tenant B's data as tenant A through 6 different paths: id, node, search, the shared catalogue, a
mutation, a header; with a cache warmed by B first. Then the grader connects to PostgreSQL directly and checks the
policies with no app in between.

## Check

1. The app connects as a superuser and every table has a policy. Is it isolated?
2. Why `set_config('app.tenant', ?, true)` and not `false`?
3. Why can a premium-only field not just be checked in its resolver?

<details><summary>Answers</summary>

1. No: superusers bypass row-level security. The app must switch to a non-superuser role (and owners need FORCE).
2. `true` makes it local to the transaction; a session-level setting would stay on the pooled connection and leak
   into another tenant's request.
3. It can, and it must; but then basic tenants still see the field in introspection and codegen, and get an error
   instead of a validation failure. Visibility hides it; the check protects it.

</details>
