# 14.5 Events and CQRS

## Hook (2 min)

A review is posted. Within 10 ms the book still shows 2 reviews; a second later, 3. Is that a bug? Only if the
schema pretends otherwise.

## Concept (15 min)

### Mutations as commands

A command asks for a change and may be refused (`userErrors`); its effects reach readers later. CQRS splits the
model: the write side stores what commands decide, the read side holds what queries need, shaped for them, built
from events. In GraphQL the split is visible: `createReview` returns the review `PENDING`, and the book "as the read
model has it now".

### The outbox

Write the review, then publish to Kafka: two systems, no shared transaction. Crash between them and the event is
lost; publish first and a rolled-back review was announced. The **transactional outbox**: the event is a row in the
same database transaction as the review; a relay publishes unpublished rows and marks them afterwards. That is
**at least once**: a crash after sending and before marking sends again. (Change data capture, Module 11's
Debezium, reads the same rows from the write-ahead log instead of polling.)

### The projection

A `@KafkaListener` (Spring for Apache Kafka 4.2.0 from Boot's BOM) is the read model's only writer. Because delivery
is at least once, it is **idempotent**: the `eventId` goes into a `processed_events` table in the same transaction
as the change, and a repeat finds it there. Key the topic by aggregate (`bookId`) so one book's events keep their
order on one partition.

### Eventual consistency in the schema

Say what the client sees: `ReviewStatus { PENDING PUBLISHED }`, figures that count published reviews only, and a
payload described as "before this review". A client can then show "posting..." honestly, or update its cache
optimistically (Module 12). Subscriptions (Module 11) can tell it when the projection catches up.

## Java build (20 min)

Lab 14.5: the command with the outbox, a 500 ms relay with `FOR UPDATE SKIP LOCKED`, an idempotent projection, and
queries over both models.

## Experiment (15 min)

Create a review and query it within 10 ms and after 1 s; expose a `pending` status honestly. Then the grader clears
an event's `published_at` (the relay sends it again) and publishes an event of its own: the count must not double,
and the foreign event must appear.

## Check

1. Why not send to Kafka inside the command's transaction?
2. The relay marks a row published after the broker's acknowledgement. What can go wrong, and who handles it?
3. Why key the topic by book id?

<details><summary>Answers</summary>

1. Kafka is not part of the database transaction: a send that succeeded cannot be rolled back with it, and a send
   that failed after commit loses the event. The outbox makes the event part of the same commit.
2. A crash between acknowledgement and marking publishes the event again; the projection ignores repeats by
   `eventId`.
3. Events for one key go to one partition in order, so a book's events are applied in the order they happened;
   different books still spread over partitions.

</details>
