# 18.5 Where the spec is heading

## Hook (2 min)

Module 17 built an engine from the September 2025 edition. Since then, five accepted RFCs have been merged into
the spec's main branch: a rewording of Fragments (2026-02-05), directives on directive definitions (2026-06-04),
and on 2026-09-17 empty selection sets, OneOf inhabitability and a fix to "response position". More are in
flight. This lecture is a map, dated 2026-11-23.

## Concept (15 min)

### How a change gets in

The RFC tracker (rfcs.graphql.org) follows each proposal: **RFC 0** Strawman, **1** Proposal, **2** Draft,
**3** Accepted, or X (rejected, superseded). A champion moves it at a working group meeting; an accepted change is
merged into the spec text and ships in the next edition.

### The proposals to know

| Proposal | Stage (2026-11-23) | In one line |
| --- | --- | --- |
| Incremental delivery, #1110 | RFC 2 | `@defer` (and later `@stream`) with a response format of `pending`, `incremental` and `completed` entries, no duplicated fields |
| Error behaviors, #1163 | RFC 1 | the request's `onError`: `PROPAGATE` (today, and the default for good), `NULL` (no null bubbling), `HALT` |
| Fragment arguments, #1081 | RFC 2 | fragments with their own variable definitions, and arguments at the spread |
| Service capabilities, #1208 | RFC 1 | `__service { capabilities }` and an SDL `service { capability ... }` block: what a server supports, outside the type system |
| Full Schemas | RFC 0 | SDL that includes built-in scalars, directives and introspection types, so tools need no implicit knowledge |
| Composite Schemas | RFC 0 on the tracker | the vendor-neutral federation specification, developed by its own working group (Module 15) |
| Persisted documents over HTTP | open pull request #264 in graphql-over-http | an appendix to the HTTP spec; not in its September 2026 edition |

Watch the relationships: #1163 needs #1208 (a client should only send `onError` to a server that advertises
it); fragment arguments would change validation and the executor Module 17 wrote; incremental delivery is what
Module 11's `@defer` used in an older draft's shape.

### Where Java stands

graphql-java 26.1 has `@defer` in the earlier draft's payload shape, no `@stream`, no executable descriptions,
no `onError` (only an experimental, operation-level `@experimental_disableErrorPropagation` behind a flag) and no
`__service`. Following the spec means reading the tracker, not the release notes.

## Check

1. What is the difference between RFC 2 and RFC 3?
2. Why does error behaviors depend on service capabilities?
3. Is `onError: "NULL"` safe to send to graphql-java 26.1 today?

<details><summary>Answers</summary>

1. RFC 2 (Draft) has spec text under review; RFC 3 (Accepted) is agreed and merged or ready to merge.
2. A client must know the server honours `onError` before relying on it; capabilities are how a server says so.
3. It is accepted and ignored: the reference server answers a request with `"onError": "NULL"` normally (200),
   and errors would still propagate. A client cannot rely on it without a capability.

</details>
