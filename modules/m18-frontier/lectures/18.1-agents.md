# 18.1 GraphQL for AI agents

## Hook (2 min)

Ask a model "when did The Midnight Readers hold their October wrap-up meetup?" with Shelfie's schema in context.
It writes a valid, cheap query, Shelfie answers 200, and the answer is not in the response:
`meetups(upcomingOnly: Boolean = true)` hid the past. No error anywhere. That is the agent problem in one line.

## Concept (15 min)

### The schema is machine-readable context

An agent that calls a GraphQL API reads the same things a developer does: type names, field names, arguments,
defaults and descriptions. GraphQL gives it more than most APIs: one typed schema, introspectable, with
descriptions on every element. It also gives it more rope: any selection, any depth, any mutation the schema
has.

### Operation descriptions are tool documentation

The September 2025 edition allows a description on an operation, a fragment and a variable definition (RFC
#1170, merged 2025-07-01):

```graphql
"""
The meetups of one club ($clubId, for example c1). By default only upcoming meetups; set $upcomingOnly to false
to include past ones.
"""
query ClubMeetups($clubId: ID!, $upcomingOnly: Boolean = true) { ... }
```

When an operation becomes a tool (18.2), its description is all the agent sees. A good one says what comes
back, where each variable's value comes from, what `null` means, and what the schema hides: defaults, missing
filters (Shelfie has no author filter), limits. For a mutation: what changes and how problems come back.

Mind the gap between the edition and the engines: graphql-java 26.1, which Shelfie runs, rejects descriptions on
operations (Module 17, finding 6). Lab 18.1 parses with Module 17's engine, which follows the edition, and strips
descriptions before validating with graphql-java; lab 18.2's server strips them before sending.

### Risks of LLM-written queries

- **Silent wrong answers:** hidden defaults, a filter that does not exist, the right data but misread.
- **Cost:** "list everything and filter" is a model's favourite move. Module 10's cost function prices
  `books(first: 50) { ... }` at 150 to 250 whatever the catalogue holds.
- **Writes:** a raw tool lets a misunderstanding become a mutation.
- **Introspection and fan-out:** the same attacks as Module 10, now written by something that never gets tired.

## Experiment (15 min)

Give a model the schema, then the schema and your operations, and ask it the ten questions in
`contract/agent/questions.json`. Score both runs with `agent score`: valid, Module 10 cost, and whether the

## Check

1. Why is an operation's description more important for an agent than for a human developer?
2. Shelfie's `books(first: Int = 20)`: what should FindBooks' description say about it, and why?
3. A query is valid, cost 6, and returns 200 with no errors. Can it still be a failure? Give Shelfie's example.

<details><summary>Answers</summary>

1. The agent sees only the tool's name, parameters and description when it chooses; it cannot ask a colleague or
   read the resolver.
2. That the page size is small by default and what to pass for more (and that there is no author filter), so the
   agent neither misses books nor fetches everything by habit.
3. Yes: `meetups` without `upcomingOnly: false` drops past meetups, so "when was the October meetup?" gets a valid,
