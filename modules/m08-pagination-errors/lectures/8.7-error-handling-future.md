# 8.7 Where error handling is heading

## Hook (2 min)

Two field errors on a club page, and PROPAGATE returns `data: null` after nine fetchers did their
work. A normalized client cache can keep none of it. What if the client could say "keep the nulls
where they happen, I'll read `errors`"?

## Concept (15 min)

### `onError` (RFC #1163)

[RFC #1163](https://rfcs.graphql.org/rfcs/1163/) (RFC 1, Proposal, last updated 2026-10-05, champion
Benjie Gillam) adds a request property, `onError`:

- `PROPAGATE`: today's behaviour, the default. The working group decided on 2026-08-06 that it stays
  the default forever.
- `NULL`: no propagation. The failed field is `null`, an error names its path, the parent survives.
- `HALT` (`ABORT` in earlier drafts): stop at the first error, `data: null`, one error. For scripts
  that discard partial data anyway, and the server stops doing work nobody will read.

Why NULL matters: with propagation, schema designers mark fields nullable just because they might
fail (lab 7.4). With NULL, `!` can mean "never null in correct data", which is the semantic non-null
idea, and errored responses become safe to write into normalized caches.

### The client's half

Under NULL a `rating: Float!` can arrive as `null`. A client must never read that as a value: it checks
`errors` for the path (graphql-toe; Relay's `@throwOnFieldError`) or its cache skips errored fields.

### Java today

No Java server reads `onError` yet. graphql-java 26.1 has NULL behind an experimental operation
directive, `@experimental_disableErrorPropagation`, enabled by default. The probes found:

- Overriding `ExecutionStrategy.assertNonNullFieldPrecondition` as a do-nothing "NULL mode" stops
  propagation only partly: a null item in `members: [User!]!` still nulled the whole list. The
  directive keeps `[a, null, c]`.
- Adding the directive by printing and re-parsing the query moves every error location. Add it to the
  parsed document (a `PreparsedDocumentProvider`) and the client's line and column survive.
- A HALT needs `ExecutionInput.cancel()` at the first error, and graphql-java checks the flag between
  fetchers: 3 fetchers ran instead of 9. `GraphQL.transform(b -> b.defaultDataFetcherExceptionHandler(h))`
  is silently ignored once strategies exist, so build `new AsyncExecutionStrategy(h)`.

## Java build (20 min)

Lab 8.8: `OnError.execute(graphQL, query, mode)` for all three modes, and an error-aware

## Experiment (15 min)

What the cache keeps per mode on the same page: PROPAGATE 0 fields, NULL 14 fields in 6 records, HALT 0.

## Check (3 min)

1. If NULL is so much better, why will PROPAGATE stay the default?
2. What does an error-aware cache do with `rating: null` plus an error at that path?

<details><summary>Answers</summary>

1. Every existing client was written for propagation. Under NULL their `!` types would start receiving
   nulls they never check for. Opt-in per request (or in trusted documents) breaks nobody.
2. It doesn't write the field, so the previous good rating stays cached, and it can mark the field as
   errored for the UI.
</details>
