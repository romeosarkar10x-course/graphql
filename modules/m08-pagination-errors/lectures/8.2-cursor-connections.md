# 8.2 Cursor connections

## Hook (2 min)

Same million rows, same page 45,000, 0.036 ms instead of 53 ms. The fix isn't a cache. The next page
is asked for differently: "the 20 *after this one*", not "the 20 after the first 900,000".

## Concept (20 min)

### Keyset (seek) paging

Sort by a unique key, `(published, id)`, and remember the last key you showed. The next page is
`where (published, id) > (1999, 424242) order by published, id limit 21`. With an index on
`(published, id)` that is one seek and 21 rows, at any depth. The 21st row only answers `hasNextPage`.
Inserts and deletes elsewhere can't shift it: the position is a value, not a count.

Two traps, both measured on PostgreSQL 18.7 (`_workbench/2026-11-21-m08-probe/FINDINGS.md`):

- **The OR form.** `published > ? or (published = ? and id > ?)` returns the same rows, but the
  planner uses the index only for its order and *filters*: 900,000 rows removed at offset 900,000
  (26.6 ms). The row-value form `(published, id) > (?, ?)` is an `Index Cond`. **Spring Data JPA 4.2's
  generated keyset scroll writes the OR form.** A redundant prefix, `published >= ? and (...)`, also
  fixes it (0.18 ms).
- **VACUUM.** Index-only scans need the visibility map. Before `vacuum analyze`, the same OFFSET took
  about 525 ms from Java instead of 25 ms. Autovacuum does this in production, and a freshly loaded test
  table doesn't have it.

### The Relay connection

[Cursor Connections](https://relay.dev/graphql/connections.htm): `books(first, after, last, before):
BookConnection` with `edges { cursor node }` and `pageInfo { hasNextPage hasPreviousPage startCursor
endCursor }`. Cursors are **opaque**: clients pass them back and never build them. The spec lets
`hasPreviousPage` be `false` when paging forward "if it cannot be determined efficiently". A negative
`first` must be an error.

### Spring for GraphQL 2.1

Declare `books(...): BookConnection!`, return a `Window<Book>`, take a `ScrollSubrange` argument, and
the connection types are generated. What the probes found:

- Boot's default cursor decodes to `K_["java.util.Collections$UnmodifiableMap",{"id":["java.lang.Long",375],...}]`:
  Java class names in every cursor.
- Declaring your own `CursorStrategy<ScrollPosition>` bean silently breaks `ScrollSubrange`. Boot's
  condition looks for an `EncodingCursorStrategy`, so two `CursorStrategy` beans exist, `getBean` throws
  `NoUniqueBeanDefinitionException`, and Spring catches it as "no bean". Declare an
  `EncodingCursorStrategy<ScrollPosition>`.
- `ScrollSubrange` turns `first: -1` into "no count", and ignores `before` when `first` is given.
- `hasPreviousPage` is true only when scrolling backward; `hasNextPage` only when scrolling forward.

2. A client stores a cursor for book 424242, and the book is deleted. What does the next page show?
