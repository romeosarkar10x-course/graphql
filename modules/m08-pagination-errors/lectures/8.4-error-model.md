# 8.4 The error model

## Hook (2 min)

One greeting service is flaky, and the whole response is `"data": null`, including the healthy club. Another
time a member's profile is unreadable and the club disappears, while a broken review only leaves a hole
in a list. Same exception, three blast radii. The schema's `!`s decide which one you get.

## Concept (15 min)

### Two kinds of errors

- **Request errors** come before execution: parse, validation, variable coercion. The response has
  **no `data` key** (the spec forbids it), and its errors have `locations` but no `path`. Retrying
  won't help, because the request itself is wrong.
- **Execution errors** (field errors) are raised while fetching or completing a field. The response
  has `data`, possibly `null`. Each error has a `path` made of response keys (aliases) and list
  indexes: `["club", "members", 2, "name"]`, `["a", "owner"]`. Since
  [#1073](https://rfcs.graphql.org/rfcs/1073/) (RFC 3, merged 2024-04-04), that path format is a MUST.

### Where the null goes

A failed field becomes `null`. If its type is non-null, the null moves to the parent, and so on up to
the nearest position that may be null: a nullable field, a nullable list item, or `data` itself.
Siblings are never affected. In lab 8.5:

| Failing field | Schema on the way up | Result |
|---|---|---|
| `Book.rating: Float` | nullable | `rating: null` |
| `Book.title: String!` | `currentBook: Book` | `currentBook: null` |
| `User.name: String!` | `[User!]!`, `club: Club` | `club: null` |
| `Review.body: String!` | `[Review]` | `reviews: [r1, null, r3]` |
| `Query.hello: String!` | the root | `data: null` |

[#1183](https://rfcs.graphql.org/rfcs/1183/) (RFC 3, merged 2026-09-17) clarifies that the null
propagating up adds no new error: one error per error path. [#1184](https://rfcs.graphql.org/rfcs/1184/)
(RFC 2) would stop engines adding sibling errors after a position has already been nulled.

### `extensions`

The only place for anything beyond `message`, `locations` and `path`. graphql-java writes
`extensions.classification` (`DataFetchingException`, `ValidationError`, `NullValueInNonNullableField`).
Lecture 8.5 adds a stable `code`. [#1200](https://rfcs.graphql.org/rfcs/1200/) (RFC 0) proposes a
schema `coordinate` on each error.

## Java build (15 min)

Lab 8.5: six throws at five depths in one small graphql-java schema, ten requests, a prediction file.

## Experiment (20 min)

Predict every `data` and every error path before running. The usual misses: E3 (`[User!]!` takes
the club with it), E6 (the alias is in the path and the sibling survives), and R3 (a missing variable is
classified `ValidationError`: a request error, no `data`).

## Check (3 min)

1. A response has `"data": null` and one error with a path. Request error or execution error?
2. graphql-java's default message for a fetcher exception is `Exception while fetching data
   (/club/owner) : users service down`. What is wrong with sending that to clients?

<details><summary>Answers</summary>

1. Execution error: `data` is present (null because a non-null root field failed), and the path names it.
2. It leaks internals (service names, ids, raw exception text) and it isn't a contract: clients end
   up parsing messages. Lecture 8.5 masks it and adds codes.
</details>
