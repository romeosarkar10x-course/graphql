# 8.5 Error strategy

## Hook (2 min)

Object storage is down, and the response says `S3 GetObject s3://shelfie-covers-prod/... connect to
10.0.4.17:9000 refused`. A client developer now knows your bucket name and your network, and still
doesn't know whether to retry.

## Concept (15 min)

### Three audiences

- **The client's code** needs a stable `extensions.code` to switch on: UNAUTHENTICATED, FORBIDDEN,
  NOT_FOUND, CONFLICT, INVALID_REQUEST, INTERNAL. Codes are API. Add new ones, never rename one.
- **The end user** needs a message safe to show, for the domain errors only.
- **You** need the full exception, in the log, findable from what the user reports: an `errorId` in
  the response and the same id in the log line.

Expected domain failures throw a domain exception that carries its code. Everything else is masked:
`Internal error`, code `INTERNAL`, an `errorId`. Spring for GraphQL already masks unresolved
exceptions as `INTERNAL_ERROR for <executionId>`. A contract replaces that with codes and correlation.
Hide existence where it matters: a private club you aren't in is `NOT_FOUND`, the same answer as a
club that doesn't exist.

### The Spring pieces

- `ErrorClassification`: an enum of your codes, set with `GraphqlErrorBuilder.errorType(code)`.
- `DataFetcherExceptionResolverAdapter`: exception to `GraphQLError`, per fetcher. Domain exceptions
  keep their message; the rest are masked and logged with the id.
- `WebGraphQlInterceptor`: the policy for the whole response, including request errors no resolver
  sees. It puts a request id into `GraphQLContext` before execution and into `extensions.requestId`
  after.

### HTTP status codes

GraphQL over HTTP (September 2026 edition): with `application/json`, 200 for every well-formed
response. With `application/graphql-response+json`, request errors MUST be 4xx (422 SHOULD for
validation, 400 for parse), and data with errors (even `"data": null`) SHOULD be `294`.
Spring for GraphQL 2.1.0 measured (`_workbench/2026-11-21-m08-probe/errors.txt`):

| Response | `application/json` | `application/graphql-response+json` |
|---|---|---|
| data, no errors | 200 | 200 |
| data and a field error | 200 | 200 |
| validation or syntax error | 200 | 400 |

`GraphQlHttpHandler.selectResponseStatus`, a protected method, chooses the status. An interceptor can't
change it, and a handler subclass can. Clients should read the body anyway, as the spec says.

## Check (3 min)

1. Why validate the client's `X-Request-Id` before echoing it?
2. A field changes from FORBIDDEN to NOT_FOUND. Breaking?

<details><summary>Answers</summary>

1. It goes into your logs and your responses. Unvalidated, it is a log-injection and response-injection channel.
2. Yes: clients switch on codes. Treat it like a schema change, and announce it.
</details>
