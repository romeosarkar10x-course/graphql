# 11.3 Implementing subscriptions

## Hook (2 min)

Three bots type 10,000 keystrokes a second. On Ben's phone (20 frames a second) "bot2 is typing" stays
on screen for 25 minutes after they stop.

## Concept (15 min)

### One sink, many filtered views

A `Sinks.Many` is the bus inside one JVM. Each subscription is `sink.asFlux()` plus its own operators:
`filter` by room and by "not me", which costs nothing to share. Choose the sink's behaviour on purpose:
`multicast().directBestEffort()` drops events for a subscriber that is not ready and never stalls the
others; `onBackpressureBuffer()` keeps them all, which is right for nothing a human watches live.

### Backpressure is a product decision

Spring for GraphQL's WebSocket handler requests events as it can write them, so a slow client pushes back
on the stream (a `Flux.interval` source overflowed at about 44,600 events). Something must give: drop
(typing, presence), keep the latest (`onBackpressureLatest`, a score), coalesce in time windows
(`window(250ms)` plus `distinct(author)`: at most one event per author per window), or for events that each
matter (chat messages) a bounded buffer and then a disconnect, so the client catches up with a query.
`sample(250ms)` alone loses authors: one event per window, whoever typed it.

### Cleanup

A client that disconnects **cancels** its subscription: `doOnComplete` does not run, `doFinally` does
(complete, error, cancel). Anything you count, register or lock per subscription must be released
there, or it leaks. `takeUntilOther(signal)` ends a stream from the server side, and Spring sends
`complete`: closing a room, ending a game.

A Spring-specific trap (probe 2): with `keep-alive` set and a client that stops reading, a ping written
while a data frame was still being written failed with `TEXT_PARTIAL_WRITING` and Spring closed the
session. Thinning the stream for slow clients avoids it too.

## Java build (20 min)

Lab 11.3: `typing(roomId, me)` filtered per subscriber, windowed per author and `onBackpressureLatest`;
`Room.watching` counted in `doOnSubscribe`/`doFinally`; every room stream ends with
`takeUntilOther(archived)`. The trivia mini-project and tic-tac-toe build on the same operators.

## Experiment (15 min)

`/_course/flood` sends 10,000 typing events a second for 3 s; a fast and a `--read-rate 20` client watch.
Before the fix the slow client was still reading stale events at 12 s; after, both were done at 3.1 s.

## Check

1. Which Reactor hook releases a per-subscription counter when the client simply closes the app?
2. Why is `sample(Duration.ofMillis(250))` wrong for a typing indicator with three typists?
3. A chat client cannot keep up. Should the server drop messages for it?

<details><summary>Answers</summary>

1. `doFinally` (the subscription is cancelled; `doOnComplete` never runs).
2. It keeps one event per period, so two of the three typists disappear; window per author instead.
3. No: each message matters. Buffer a bounded amount, then end the subscription with an error and let the
   client reconnect and fill its gap with a query.
