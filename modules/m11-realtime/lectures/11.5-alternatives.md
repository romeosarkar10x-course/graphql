# 11.5 Alternatives to subscriptions

## Hook (2 min)

A moderation tool inserts a pinned message straight into the database. Nobody in the room sees it until
they reload. Meanwhile 500 clients that poll every 2 seconds are costing the server 250 requests a second
in a room where three messages were sent in half a minute.

## Concept (15 min)

### Polling

The client repeats a query (`messages(after:)`) on a timer. Stateless, cacheable, works through anything,
trivially scaled. Its cost is clients × poll rate whether or not anything changed, and its delay is half
the interval on average. Measured (500 clients, every 2 s): 250 requests a second and about 1 s median
delay in a busy and a quiet room alike; in the quiet room, 12.6 s of server CPU in 30 s for 3 messages.

### Subscriptions

The cost is sockets held, connection setup (1.7 s of CPU for 500, warm) and one selection-set execution per
subscriber per event; the delay is the bus's. Measured: 52 to 84 ms median. In a busy room (1 message a
second) the CPU was about the same as polling (7.9 s against 8.8 s); in a quiet room clearly lower.

### Live queries

`@live` (in some servers and clients, not in the spec or graphql-java): the server re-sends a query's
result whenever it changes. Natural for "this screen"; expensive when results are big or change constantly.

### Webhooks

The server POSTs events to a URL another server registered: for partners, not screens. Needs retries,
signatures and idempotency keys; survives the receiver being offline.

### Change data capture

Not a client protocol: the database's change log as the source of events. Debezium reads PostgreSQL's
logical replication stream (`wal_level=logical`, a replication slot, the `pgoutput` plugin), so every
committed insert becomes an event, whoever wrote it, and a rolled-back one never does. Costs: a slot holds
WAL until it is read, and the engine's poll interval is lag (500 ms by default showed as a 614 ms median
delay; 50 ms brought it to 52 ms).

## Java build (20 min)

Lab 11.5: messages in `m11.messages`; Debezium 3.7's embedded engine (`DebeziumEngine.create(Json.class)`,
in-memory offsets, `snapshot.mode=no_data`) publishing inserts to the bus; `sendMessage` no longer
publishes itself, so each message arrives exactly once.

## Experiment (15 min)

`contract/Load.java idle|poll|subscribe` with 500 clients, a busy and a quiet room, the server's CPU from
`/proc`. One warm-up run first: the first run pays for the JIT.

## Check

1. What grows polling's cost, and what grows a subscription's?
2. Why is "insert, then publish" weaker than CDC?
3. A partner bookshop wants new reviews of its books. Subscription, webhook or polling?

<details><summary>Answers</summary>

1. Polling: clients × poll rate, regardless of events. Subscriptions: sockets held plus subscribers ×
   events.
2. A crash between the two loses the event, a publish before a rollback announces something that never
   happened, and rows written by other programs are never published.
3. A webhook (server to server, retried), fed by CDC on the reviews table; polling `reviews(since:)` is the
   runner-up.

</details>
