# 11.2 Transports

## Hook (2 min)

The train goes into a tunnel for 1.5 seconds. Three chat messages are sent meanwhile. When the phone comes
back, does it show them?

## Concept (15 min)

### graphql-transport-ws over WebSocket

One socket, many operations. The client sends `connection_init`, the server answers `connection_ack`; then
`subscribe` with an `id`, results as `next` with that `id`, and `complete` (either side) or `error`
(server). `ping`/`pong` keep it alive. The protocol is the
[graphql-ws](https://github.com/enisdenjo/graphql-ws/blob/master/PROTOCOL.md) library's (subprotocol
`graphql-transport-ws`); the older `subscriptions-transport-ws` library (confusingly, subprotocol `graphql-ws`) is unmaintained.
Spring for GraphQL serves it on `spring.graphql.websocket.path`.

### Server-Sent Events

Plain HTTP: `POST /graphql` with `Accept: text/event-stream`, and the response is a stream of
`event: next` / `data: {...}` blocks, ending with `event: complete`. This is the
[graphql-sse](https://github.com/enisdenjo/graphql-sse/blob/master/PROTOCOL.md) protocol's "distinct
connections mode"; Spring for GraphQL serves it on `/graphql` with no extra dependency. One HTTP response
per subscription, which proxies, auth and HTTP/2 already understand. Spring commits the response headers
only with the first event or keep-alive (measured), so a client cannot treat "headers arrived" as
"subscribed".

### RSocket and multipart HTTP

RSocket (Spring's `GraphQlRSocketHandler`, `RSocketGraphQlClient`) is a binary protocol with streams and
`request(n)` backpressure built in: service to service on the JVM. Multipart HTTP subscriptions (Apollo's
protocol, one `multipart/mixed` response) are spoken by Apollo Client and Router; Spring for GraphQL 2.1
does not serve them.

### Nothing resumes by itself

A drop is a `Connection reset` (WebSocket) or `IOException: closed` (SSE). Neither graphql-transport-ws nor
Spring's SSE has resumption (no `id:` lines for `Last-Event-ID`). The client must reconnect with
exponential backoff and jitter, resubscribe, and fetch what it missed with a query
(`messages(after: <last id>)`), holding live events until the gap is filled and removing duplicates by id.
Keep-alives (`spring.graphql.websocket.keep-alive`, `spring.graphql.http.sse.keep-alive`) stop idle
proxies from closing quiet connections and make dead ones fail.

## Check

1. Why "subscribe, then query the gap" and not the other way round?
2. A thousand phones lose their connection at the same second. What stops them all reconnecting in the
   same second?
3. Name one thing SSE gets for free that the WebSocket protocol has to build.

<details><summary>Answers</summary>

1. After the subscription starts, every new message arrives live; the query covers everything before.
   Querying first leaves a window between the query and the subscription where messages are lost.
2. Jitter: each client waits its backoff plus a random extra.
3. Any of: HTTP authentication and headers, proxies and load balancers that understand it, HTTP/2
   multiplexing, no `connection_init` handshake.

</details>
