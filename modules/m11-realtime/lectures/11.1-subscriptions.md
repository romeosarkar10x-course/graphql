# 11.1 Subscriptions, conceptually

## Hook (2 min)

Ada sends "anyone finished chapter 3?" to the Night Owls room. Ben and Cleo see it within a tenth of a
second, without asking. Nothing in queries and mutations can do that: they answer a request and stop.

## Concept (15 min)

### Source stream and response stream

A subscription operation selects exactly one root field. The spec splits its execution in two
([Execution, "Subscription"](https://spec.graphql.org/September2025/#sec-Subscription)):

- **CreateSourceEventStream** resolves the root field once and gets a *stream of events*: in Java a
  `Flux<Message>` (any `Publisher`). Here the server decides what counts as an event: every message in
  room r1.
- **MapSourceToResponseEvent** executes the selection set once per event, like a query whose root value is
  the event, and sends the result. That stream of results is the *response stream*.

So `subscription { messageSent(roomId: "r1") { body } }` and `{ id author body }` subscribe to the same
source stream, and each gets its own shape. A mutation publishes once; the bus fans the event out to
every source stream that wants it; each subscriber's selection set runs separately.

### Exactly one root field

`subscription { a: ticks b: ticks }` fails validation (`SubscriptionMultipleRootFields`): a response
stream maps one source stream. RFC [#860](https://rfcs.graphql.org/rfcs/860/) also forbids `@skip` and
`@include` on the root field, since they could make it zero fields; graphql-java 26.1 still accepts
`ticks @skip(if: false)` (probe 1, and Module 2's finding).

### Two kinds of errors

- A **field error** inside one event (a resolver for `risky` throws): that event arrives with `data` and
  `errors`, and the subscription goes on (probe 4).
- A **source stream error** (the `Flux` itself fails): the subscription is over. Spring for GraphQL sends
  graphql-transport-ws `error` with `"Subscription error"` and `INTERNAL_ERROR` and no `complete`; over
  SSE it sends `event: next` with `{"errors": [...]}`, then `event: complete`. A
  `SubscriptionExceptionResolver` decides what the client learns. RFC
  [#1127](https://rfcs.graphql.org/rfcs/1127/) proposes specifying this case.

A validation error on a subscription arrives over graphql-transport-ws as `next` with `errors`, then
`complete` (probe 1), where the protocol suggests an `error` message: a Spring detail worth knowing when
you write a client.

## Check

1. Two clients subscribe to `messageSent(roomId: "r1")` with different selection sets. How many times does
   the resolver for `messageSent` run, and how many times does the selection set run, for one message?
2. What does a client receive when one event's field fails, and when the source stream fails?
3. Why must a subscription have exactly one root field?

<details><summary>Answers</summary>

1. The root field resolves once per subscription (it creates each source stream); the selection set runs
   once per subscriber per event: twice for one message.
2. A field error: `next` with `data` (the failed field null) and `errors`, and the stream continues. A
   source error: graphql-transport-ws `error` (no `complete`), the subscription is over.
3. A response stream maps the events of one source stream; two root fields would mean two streams with no
   rule for combining their events.

</details>
