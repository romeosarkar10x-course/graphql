# 11.4 Scaling fan-out

## Hook (2 min)

Shelfie runs three instances behind a load balancer. Ada's message reaches the three people connected to
her instance; the other six see nothing.

## Concept (15 min)

### Every instance must see every event

A `Sinks.Many` lives in one JVM. With N instances, a mutation on one must reach subscribers on all, so
events go out to a shared bus and come back to every instance (this one included), which delivers to its
own subscribers. The relay sends; each instance's listener hands events to its local sink.

### Redis pub/sub and Kafka

- **Redis pub/sub:** `PUBLISH` to a channel, every instance `SUBSCRIBE`s. Simple and fast, **at most
  once**: Redis keeps nothing, an instance that is reconnecting misses those events.
- **Kafka:** a topic keeps the log. Events keyed by room id stay in order within the room (one partition
  per key). A consumer group *shares* partitions among its members, so fan-out needs one group per
  instance; with one shared group each event reaches one instance (lab 11.4: 6 of 9 subscribers got
  nothing). A group with committed offsets resumes after a restart and replays what it missed.
- Neither gives exactly once to a client. Clients remove duplicates by id and fill gaps by query, and that
  query must read a store every instance shares (game 11.10).

### Sticky sessions

A WebSocket or SSE response is one connection: it stays on the instance it was balanced to. The balancer
spreads new connections, skips dead instances, and should drain an instance before a deploy so its
clients reconnect gradually. Sticky sessions matter only when one logical session spans several
connections (graphql-sse's single connection mode, long-polling fallbacks).

### What is still per instance

Connection counts, in-memory history, and id counters: in game 11.10 two instances both handed out `m7`,
and a client that reconnected elsewhere asked for "messages after m7" in the wrong numbering. Shared ids
(Redis `INCR` or a database sequence) and shared history fix it.

## Experiment (15 min)

Three replicas, nine subscribers, nine messages to three different replicas: prove every client gets every
message, on each bus. Then break the Kafka group id on purpose and explain the numbers.

## Check

1. Why did a shared Kafka consumer group deliver r2's messages to exactly one instance?
2. Instance b restarts. What does it miss with Redis pub/sub, and with Kafka?
3. Why does a WebSocket not need a sticky-session cookie?

<details><summary>Answers</summary>

1. All r2 events share the key r2, so they are in one partition, and a group gives each partition to one
   member.
2. Redis: every event published while it was disconnected, for good. Kafka: nothing, if its group has
   committed offsets: it resumes and replays from where it stopped.
3. The whole session is one TCP connection, which the balancer routes once.
