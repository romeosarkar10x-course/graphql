# 11.6 `@defer` and `@stream`

## Hook (2 min)

The club page waits 1.5 seconds for its recommendations panel, which is below the fold. Everything else
was ready in 10 milliseconds.

## Concept (15 min)

### Incremental delivery

`... @defer(label: "recommendations") { recommendations { title } }` lets the server send the rest first and
the fragment later; `@stream(initialCount:)` does the same for list items. The response becomes a stream
of payloads. RFC [#1110](https://rfcs.graphql.org/rfcs/1110/) (RFC 2, draft) defines it:

```json
{"data": {"club": {"name": "Night Owls"}}, "pending": [{"id": "0", "path": ["club"], "label": "recommendations"}], "hasNext": true}
{"incremental": [{"id": "0", "data": {"recommendations": [...]}}], "completed": [{"id": "0"}], "hasNext": false}
```

The initial payload must list `pending` (non-empty); later payloads refer to those ids, may announce new
`pending` (a nested `@defer`) and must not repeat `data`; `completed` may carry `errors` when a deferred part
failed. For `@stream`, incremental entries carry `items` instead of `data`.

### What graphql-java 26.1 does

`@defer` only, behind `ExperimentalApi.ENABLE_INCREMENTAL_SUPPORT` in the `GraphQLContext`; `@stream` is an
unknown directive. Its payloads are the earlier draft's shape: no `pending` or `completed`, each
incremental entry carries `path` and `label`:

```json
{"data": {"club": {...}}, "hasNext": true}
{"incremental": [{"path": ["club"], "label": "recommendations", "data": {"recommendations": [...]}}], "hasNext": false}
```

A server cannot translate this to RFC 2 on the fly, because graphql-java does not report the pending
fragments when it sends the initial payload. Apollo Client asks for the older format with
`Accept: multipart/mixed;deferSpec=20220824` (from Apollo's documentation; not tested in this course).
With the flag off, graphql-java runs `@defer` fragments inline.

### Over HTTP

The [GraphQL over HTTP incremental delivery RFC](https://github.com/graphql/graphql-over-http/blob/main/rfcs/IncrementalDelivery.md)
uses `multipart/mixed; boundary="-"`: each part is `\r\n---\r\n`, a `Content-Type` header, a blank line and
the JSON, and the stream ends with `\r\n-----\r\n`. Spring for GraphQL 2.1 has no incremental transport:
with the flag on, its handler sent the initial payload (`hasNext: true`) and dropped the rest, and
`Accept: multipart/mixed` alone got 415.

## Java build (20 min)

Lab 11.6: an interceptor that enables incremental support only when the client names `multipart/mixed`
(`*/*` does not count), and a `RouterFunction` ordered before Boot's that calls the `WebGraphQlHandler`,
writes the initial payload, flushes, then writes each later payload from
`IncrementalExecutionResult.getIncrementalItemPublisher()`.

## Experiment (15 min)

Time to first byte with curl: 0.068 s with `@defer` over multipart against 1.51 s for JSON, with the total
unchanged (1.58 s).
