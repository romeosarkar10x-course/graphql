# 12.8 Client resilience

## Hook (2 min)

30% of responses are lost on the way back. A naive client fails 3 calls in 10. A naive retry duplicates
reviews. Lab 12.8 fixes both, and the first fix is a timeout.

## Concept (15 min)

### Timeouts first

Without a read timeout one hung connection hangs the caller forever, and no retry ever runs. Set a connect and a
read timeout on the HTTP client (lab: 500 ms each, `JdkClientHttpRequestFactory`).

### Retry what is safe, with backoff and jitter

- Retry **"no answer"** (I/O errors, timeouts) and 5xx. Never GraphQL errors or userErrors: those are answers.
- Know what your client throws: `HttpSyncGraphQlClient` surfaces RestClient's `ResourceAccessException` for an
  I/O error, not `GraphQlTransportException` (the WebSocket client uses that one); a retry configured for the
  wrong type retries nothing.
- Exponential backoff with jitter (Resilience4j `IntervalFunction.ofExponentialRandomBackoff`) spreads retries
  so clients do not hit a recovering server in lockstep.

### Idempotent replays

A lost response is not a failed mutation: in the probe Shelfie stored all 10 reviews while the client saw 4
failures. Queries, and mutations idempotent by contract (`joinClub`), may be retried blindly. Others need a way
to recognise a replay: an idempotency key the server stores with the first result, or, in Shelfie's case, the
"one review per user and book" rule (`DUPLICATE` after an unknown outcome means the first attempt worked).

### Circuit breaker

When the failure rate says "outage" rather than "weather", stop calling: fail fast, try again after a wait.
Put the retry outside the breaker so every attempt is counted, and do not retry `CallNotPermittedException`.
Measured: 100 calls to an unreachable Shelfie took 1.3–1.6 s, 98 refused by the open breaker.

### Persisted documents from the client

With APQ (9.6) the client sends only the hash first; `PersistedQueryNotFound` (every client after a server
restart with an in-memory store) means "send the text now", immediately, without backoff and without counting
against the breaker. With trusted documents (10.5) an unknown hash is a client bug, not something to retry.

### Toxiproxy is per connection

Toxiproxy picks toxics per connection: with keep-alive, a 30% `reset_peer` hit 1 request in 100. The lab
disables keep-alive (`-Djdk.httpclient.keepalive.timeout=0`) so the fault rate is per call. Real networks fail
per connection too: a bad pooled connection fails every request sent on it.

## Java build (20 min)

Lab 12.8: Resilience4j `Retry` around `CircuitBreaker` around Spring's `HttpSyncGraphQlClient`; a `reviews`
command that retries `createReview` and recovers on `DUPLICATE`.

## Experiment (15 min)

Inject 30% failures with Toxiproxy (plus 5% hung connections); measure success before and after: one attempt
65–71% of 200 queries, with retries 99–100% (four runs). Then switch the proxy off and watch the breaker.

## Check

1. Why must the timeout come before the retry?
2. A retried `createReview` answers `DUPLICATE`. Success or failure?
3. Why should `PersistedQueryNotFound` not be retried with backoff?

<details><summary>Answers</summary>

1. A call that never returns never fails, so nothing is retried and the caller is stuck; the timeout turns a
   hang into a failure the retry can handle.
2. It depends on what came before: after an unknown outcome (a lost response), it means the first attempt
   worked, so look the review up and report success; with no earlier attempt, it is a real userError.
3. It is not a failure but the first step of the protocol: the server is asking for the document text, and the
   right answer is to send it at once.

</details>
