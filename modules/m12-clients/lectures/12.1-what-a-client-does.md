# 12.1 What a client really does

## Hook (2 min)

`curl -d '{"query":"{ hello }"}'` is a GraphQL client. So is Apollo Client, at about a hundred times the
size. Everything in between is code someone had to write: this lecture lists it, and lab 12.1 makes you write
the first half yourself.

## Concept (15 min)

### The request

A GraphQL-over-HTTP request is a POST with `Content-Type: application/json` and a body of `query`,
`variables` and, when the document has several operations or you want the server's logs to say what ran,
`operationName`. Ask for `Accept: application/graphql-response+json` (Module 5): a server that speaks the
current spec then uses status codes that mean something (4xx when the request was refused before execution).

- **Documents** belong in files (`BookById.graphql`), not in string concatenation: a reviewer can read them,
  tools can validate them against the schema, and the server can cache one parsed document.
- **Variables** are JSON values next to the document, never pasted into it. Pasting is GraphQL injection
  (lecture 2.2) and makes every call a different document text.

### The response

Three different failures look alike to a careless client:

| What happened | What the client sees | What to do |
|---|---|---|
| no response (refused, reset, timed out) | an `IOException` | maybe retry (12.8) |
| the server refused the request | 4xx (or 5xx, or an HTML page from a proxy) | do not parse the body as GraphQL unless its type says so |
| it ran, partly | 200 with `data` and `errors` | the partial data is real: show it, report the errors |

Decoding is the other half: walk to a path in `data`, turn it into a typed object, and decide what `null`
means (a null field with no error is an answer).

### What a library adds

Dedupe (identical in-flight requests share one call), a normalised cache (12.5), retries and timeouts (12.8),
subscriptions (Module 11), uploads (4.6), persisted documents (9.6), typed documents or code generation
(12.3), auth headers and refresh, logging. Each is easy to start and hard to finish.

## Java build (20 min)

Lab 12.1: `ShelfieClient` on `java.net.http.HttpClient` and Jackson 3, about 110 lines of code:
`execute`, `executeNamed` (documents from files, `operationName`), `field` (dotted path into a record), and
`executeAsync` with dedupe keyed by the document and the variables serialised with sorted keys.

## Experiment (15 min)

Keep a list while you build: every concern you had to hand-write, with rough sizes, and everything your client
still cannot do. That list is the case for a library, and the next three lectures are three answers to it.

## Check

1. A proxy in front of Shelfie answers 502 with an HTML page. What must your client not do?
2. Why is a GraphQL response with both `data` and `errors` not simply a failure?
3. Two requests have the same document and variables but different `Authorization` headers. May dedupe merge them?

<details><summary>Answers</summary>

1. Parse the body as a GraphQL response. Check the status and `Content-Type` first, and report "HTTP 502"
   (the lab's `GraphQlException` with status 502).
2. Execution ran: every field without an error is valid data (a page can render all but the broken widget).
   The errors say which paths failed.
3. No: they can have different answers. The dedupe key must include everything that changes the response,
   and mutations are never deduplicated.
