# 12.5 Normalised caching

## Hook (2 min)

The book page and the club page both show *The Left Hand of Darkness* at 4.2 stars. You add a review. With a
response cache (one entry per query), one page shows 3.67 and the other still says 4.2. With a normalised
cache, both change, and nothing is refetched.

## Concept (15 min)

### Records and references

A normalised cache stores **entities**, not responses. Every object with `__typename` and an id becomes one
record (`Book:b1`); wherever it appeared, the cache keeps a reference (`{"__ref": "Book:b1"}`). Query root
fields live in a root record (`ROOT_QUERY`), keyed by field name **and arguments**:
`book({"id":"b1"})`, `reviews({"last":2})`. Aliases are response keys, never storage keys. Objects without an
id are embedded in their parent.

A read walks the document over the records; one missing field makes the whole read a miss (go to the network),
while a stored `null` is an answer. A write walks the document over the response and merges fields into records.

### Why a mutation updates every query

A mutation's root field is not stored, but the entities in its response are. If `createReview` selects
`review { book { __typename id averageRating } }`, writing it merges `averageRating` into `Book:b1`, and every
cached query that reaches `Book:b1` sees it. If it does not select the id, the book is an embedded object and
nothing changes: mutations must select what they change, with ids.

### What a cache cannot know without the schema

- default arguments: `members` and `members(first: 10)` are two keys for one list;
- that `book(id: "b2")` returns `Book:b2`, already cached by a list query: a **cache redirect** (`toReference`);
- entities identified by something other than `id` (`keyFields`), and which types a union or interface
  contains (`possibleTypes`);
- **which lists a new entity belongs in.** `createReview` returns a review; the cache cannot know that
  `Book:b1.reviews({"last":5})` should now start with it. Options: refetch, an update function that writes the
  list back, evicting the list field, or returning the list from the mutation.

### The real ones

Apollo Client: `InMemoryCache`, `typePolicies` (keyFields, field `keyArgs`/`merge`/`read`), `possibleTypes`,
`cache.modify`/`evict`/`gc`, `optimisticResponse` layers, `watchQuery`. Apollo Kotlin: the same ideas,
configured in the schema (`@typePolicy`, `@fieldPolicy`) because it has codegen. Relay: records keyed by `id`
alone (so ids must be unique across types), connections for pagination, a compiler that knows the schema.

## Experiment (15 min)

Update a book title once; prove every cached query sees it (scenario 04). Then against the real Shelfie
(`contract/cache/LiveDemo.java`): two pages, one review, both pages at 3.67 from the cache, three requests in all.

## Check

1. Why is `{"__ref": "Book:b1"}` better than a copy of the book in both queries?
2. After `createReview`, the book's average is right in every query but the reviews list is not. Why?
3. `book(id: "b2")` misses although `Book:b2` is in the cache. What is missing, and what fixes it?

<details><summary>Answers</summary>

1. One record means one update: any write to `Book:b1` is seen by every query that references it, with no
   refetch and no code that knows which queries show that book.
2. The response identifies the review and its book, but nothing in it says which cached lists (with which
   arguments, at which position) should contain the review. Only the app knows: refetch or write the list back.
3. The link between the field `book(id:)` and the record `Book:<id>`; a cache redirect (`read: toReference`,
   Apollo Kotlin's `@fieldPolicy(forField: "book", keyArgs: "id")`) makes it a hit.
