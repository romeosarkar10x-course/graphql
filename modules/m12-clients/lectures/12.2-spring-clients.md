# 12.2 Spring's GraphQL clients

## Hook (2 min)

Shelfie's digest service wants a club summary, a review form and a live chat feed, all from other services
that speak GraphQL. Spring for GraphQL ships three clients for exactly that, and they share one API.

## Concept (15 min)

### One API, three transports

| Client | Transport | Returns |
|---|---|---|
| `HttpSyncGraphQlClient` | `RestClient` (blocking) | values: `retrieveSync(path).toEntity(T)` |
| `HttpGraphQlClient` | `WebClient` | `Mono`/`Flux`: `retrieve(path).toEntity(T)` |
| `WebSocketGraphQlClient` | graphql-transport-ws | subscriptions as `Flux`: `retrieveSubscription(path)` |

Every request starts from `document(text)` or `documentName("clubDigest")`, which loads
`src/main/resources/graphql-documents/clubDigest.graphql`. `variable(name, value)` adds variables;
`retrieve...("club")` picks a path in `data`; `toEntity`/`toEntityList` decode with Jackson.

### What toEntity does with errors (measured, lab 12.2)

- a null field with no error: `null` (sync), an empty `Mono` (reactive). Your code decides that is a 404.
- an error on that path: `FieldAccessException`, carrying the response's errors
  (`Invalid field 'club', errors: [{message=Validation error (FieldUndefined@[club/nope]) ...}]`).
- userErrors (Module 4's payloads) are data: `toEntity(ReviewPayload.class)` succeeds; check the list.
- `execute()` / `executeSync()` give the whole `ClientGraphQlResponse` when you want to handle errors yourself.

### Interceptors, headers, mutate

`SyncGraphQlClientInterceptor` and `GraphQlClientInterceptor` see each request and response at the GraphQL
level (logging, metrics, error mapping). HTTP headers are per client: `client.mutate().header("X-Shelfie-User",
user).build()` makes a cheap per-request copy that keeps the interceptors. Two surprises from the lab:
`documentName(...)` does **not** send an `operationName` (an interceptor sees `null` until you call
`.operationName(...)`), and a Boot property called `shelfie.url` was silently bound from the course image's
`SHELFIE_URL` environment variable.

### Sync, reactive, virtual threads

Sync blocks the request thread while Shelfie answers. With `spring.threads.virtual.enabled=true` that thread
is virtual and cheap, so sync is the default for one or two calls per request. Reactive pays off for fan-out
(`Mono.zip` of five calls) or in a WebFlux service.

## Java build (20 min)

Lab 12.2: `shelfie-digest` on :4000, with the sync client for `GET /clubs/{id}`, the reactive one for
`/reactive`, a per-request user for `POST /books/{id}/reviews`, an interceptor counting operations, and a
`WebSocketGraphQlClient` subscription to Module 11's chat (`contract/chat-server/`) that survives a restart via
`retryWhen(Retry.backoff(...))`.

## Experiment (15 min)

Call Shelfie from the second service, then subscribe to chat from it. Stop the chat server for a few seconds:
what is logged, what comes back, and which messages are gone?

## Check

1. `retrieveSync("club").toEntity(Club.class)` returned `null`. Name the two situations that look like this
   from `toEntity`, and how you would tell them apart.
2. Why does the digest create a per-request client with `mutate()` instead of adding the user header in an interceptor?
3. The chat subscription came back after the restart. Is the feed complete?

<details><summary>Answers</summary>

1. `club` is null without an error (unknown id), or the whole `data` is null with no error on that path. To
   see errors that are not on the path, use `executeSync()` and inspect `getErrors()`.
2. HTTP headers belong to the transport, which is fixed per client; a GraphQL-level interceptor sees the
   document, variables and extensions, not the HTTP request. `mutate()` copies the client with one more header
   and keeps its interceptors.
3. No: a subscription delivers only events after it starts. Messages sent while it was down are lost unless
   the client queries for them (lab 11.2's gap fill: `messages(roomId, after: lastId)`, holding live events
   until it returns).
