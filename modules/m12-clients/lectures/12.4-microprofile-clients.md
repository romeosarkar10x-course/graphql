# 12.4 MicroProfile clients

## Hook (2 min)

Quarkus services in the same company call Shelfie too. MicroProfile GraphQL's client API (implemented by
SmallRye) offers two styles: declare an interface and let it build the document, or build the document
yourself in Java.

## Concept (15 min)

### Typesafe: an interface

```java
@GraphQLClientApi(configKey = "shelfie")
public interface ShelfieApi {
  @Query
  Club club(@NonNull @Id String id, @NestedParameter("currentBook.reviews") @Name("last") int last);
}
```

The method is the root field; parameters are variables; the **return type is the selection set**: every
component of `Club`, recursively. `@NestedParameter` puts an argument on a nested field. Configuration:
`quarkus.smallrye-graphql-client.shelfie.url`. Sent (captured with `contract/Capture.java`):
`query club($id: ID!, $last: Int!) { club(id: $id) {name memberCount owner {name} currentBook {...
reviews(last: $last) {...}}} }` with `operationName: "club"`.

Measured trap: without `@NonNull`, `@Id String id` is declared as `ID` (nullable), and Shelfie refuses it:
`Variable 'id' of type 'ID' used in position expecting type 'ID!'`. Java types are not GraphQL types; the
client guesses, and nullability is where guesses go wrong.

### Dynamic: a builder

```java
var doc = document(operation(QUERY, "clubCard", vars(var("id", nonNull(GQL_ID))),
    field("club", args(arg("id", var("id", nonNull(GQL_ID)))), field("name"), field("owner", field("name")))));
Response r = dynamic.executeSync(doc, Map.of("id", id));
Club club = r.getObject(Club.class, "club");
```

What you read is what is sent, and selections can be built at runtime. It sent no `operationName` even for a
named operation.

### Against 12.2 and 12.3

Typesafe is the shortest to call and the hardest to review (the document is implicit). Dynamic is a document
file written in Java. Neither checks the schema at build time.

## Java build (20 min)

Lab 12.4: a Quarkus command-line app printing the club card both ways from one config key, each in one request
with the id as a variable and `reviews(last: 2)` asked of the server.

## Experiment (15 min)

Write the same call both ways; compare readability for the writer, the reviewer and whoever debugs it at 2 a.m.

## Check

1. Where does the typesafe client's selection set come from, and what is the risk?
2. Why did `@Id String id` fail against Shelfie?
3. When would you reach for the dynamic client?

<details><summary>Answers</summary>

1. From the return type's fields, recursively. Adding a field to a shared record silently adds it to every
   query that returns it (over-fetching, or a validation error if the server does not have it).
2. A `String` is nullable in Java, so the client declared `$id: ID`; the argument is `ID!`, and a nullable
   variable may not be used where a non-null type is expected.
3. When the selection is built at runtime (a field picker, an admin console, a generic tool), or when you want
   the document visible in code.

</details>
