# 6.1 Spring for GraphQL setup

## Hook (2 min)

Your Module 5 server is 121 lines. The Spring version of the same schema has no HTTP code, no wiring,
no `GraphQL` object, and starts in 0.8 seconds.

## Concept (15 min)

| You wrote in Module 5 | Spring for GraphQL 2.1 (Boot 4.2) |
|---|---|
| Parse SDL, `RuntimeWiring` | every `*.graphqls` under `classpath:graphql/`; controllers become fetchers |
| `GraphQL.newGraphQL(...)` | `GraphQlSource`, customisable with `GraphQlSourceBuilderCustomizer` |
| `HttpServer`, status codes | `/graphql` over Spring MVC or WebFlux (`spring-boot-starter-webmvc` here) |
| GraphiQL | `spring.graphql.graphiql.enabled=true` |
| a virtual-thread executor | `spring.threads.virtual.enabled=true` |

Measured on the build machine, `slowHello` (100 ms blocking), Tomcat's default 200 threads:

| | 200 requests | 1,000 | 2,000 |
|---|---|---|---|
| platform threads | 1,598 req/s | 1,928 | 1,888 |
| virtual threads | 1,610 req/s | 5,907 | 7,904 |

200 threads / 0.1 s = 2,000 req/s is the platform ceiling; virtual threads remove it.

What Spring does not do: the GraphQL-over-HTTP September 2026 status codes. Lab 5.4's audit passes 11 of
25 against Spring for GraphQL 2.1 (no GET, 200 for validation errors, no 294;
`_workbench/2026-11-21-m05-probe/spring-graphql-audit.txt`).

## Java build (20 min)

## Experiment (15 min)

`java Load.java 1000` with virtual threads on and off.

## Check (3 min)

1. Where must the schema file live for Boot to find it?
2. Why does `spring.threads.virtual.enabled` change throughput for `slowHello` but not for `hello`?

<details><summary>Answers</summary>

1. `src/main/resources/graphql/` (any `*.graphqls` or `*.gqls`).
2. `hello` never blocks, so threads are never the bottleneck; `slowHello` holds its thread for 100 ms.
</details>
