# 6.9 Framework bake-off

## Hook (2 min)

Four Shelfies answer the same club card. The fastest starts in 0.3 s, the slowest in 1.4 s; a native
binary answers in 32 ms. Which number should decide?

## Concept (15 min)

Median of 3 rounds, `Bench.java`, course image, 24-core machine (`_workbench/2026-11-21-m05-probe/bake-off.txt`,
`_workbench/2026-11-21-m06-native/race.txt`):

| Stack | Lines | First answer ms | RSS MB | p95 ms | req/s |
|---|---|---|---|---|---|
| raw graphql-java (m05/09) | 146 | 303 | 584 | 1.08 | 13,369 |
| Spring for GraphQL (m06/01) | 103 | 1,109 | 607 | 1.57 | 9,378 |
| DGS (m06/07) | 49 | 1,448 | 659 | 1.63 | 8,843 |
| Quarkus (m06/08) | 69 | 519 | 518 | 1.42 | 9,006 |
| Spring native | 103 | 49 | 155 | 0.66 | 18,202 |
| Quarkus native | 69 | 32 | 93 | 1.32 | 10,592 |

Read with care: the apps are not feature-equal (DGS and Quarkus serve a slice), RSS mostly reflects default
heap sizing, and loopback latency measures framework overhead (under a millisecond everywhere), not a real
fetcher's. For a long-running server the differences are noise next to the database; for scale-to-zero,
startup is everything.

Native builds: `bin/course native` runs Maven in GraalVM CE 25.0.2. Spring native built in 43 s, Quarkus
native in 33 s.

## Java build (20 min)

Lab 6.9: finish `Bench.java` (percentiles, RSS), run `bake.sh` on your four apps.

## Experiment (15 min)

Fill the table; pick a stack for Shelfie and name the number that would change your mind.

## Check (3 min)

1. Why is RSS a weak comparison with default JVM flags?
2. When does native image clearly win?

<details><summary>Answers</summary>

1. Default heap sizing depends on machine RAM and is not about the framework; set the same `-Xmx` first.
2. Scale-to-zero and short-lived processes, and dense hosting where memory per instance costs money.
</details>
