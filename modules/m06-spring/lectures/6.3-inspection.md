# 6.3 Schema mapping inspection

## Hook (2 min)

Lab 6.1's app passes every test, and its startup log says: `Argument nullness errors: {...books[2 args]=[int
first should be NULLABLE], ...}`. Send `books(first: null)` and the whole response is `data: null`.

## Concept (15 min)

At startup Spring compares schema and code and logs a report:

| Section | Means |
|---|---|
| Unmapped fields | a schema field with no controller method and no matching property |
| Unmapped registrations | a mapping for a field the schema does not have |
| Unmapped arguments | a method argument no schema argument fills |
| Field / argument nullness errors | (2.0, JSpecify) a `@Nullable` method behind a non-null field, or a primitive behind a nullable argument |
| Skipped types | types it could not check |

Nullness needs JSpecify: `@NullMarked` on the package makes unannotated types non-null; `@Nullable` marks
the rest. It is a type-use annotation: write `Data.@Nullable Club`, not `@Nullable Data.Club` (which does
not compile).

A report in a log is a report nobody reads. `GraphQlSourceBuilderCustomizer` → `inspectSchemaMappings(report
-> ...)` can throw, and then a mismatch is a failed deployment instead of a production bug.

## Java build (20 min)

Lab 6.3: clean the report, annotate nullness, fail startup; the test injects three mismatches.

## Experiment (15 min)

Introduce the three mismatches yourself and read the report each produces.

## Check (3 min)

1. `first: Int = 10` bound to `int`: why is that an error when the argument has a default?
2. Without `@NullMarked`, which section of the report stays empty?

<details><summary>Answers</summary>

1. A client may send `first: null` explicitly; the default only applies when the argument is omitted.
2. Field nullness errors: unannotated return types have unknown nullness.
</details>
