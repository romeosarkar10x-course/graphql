# 9.6 Persisted queries for speed

## Hook (2 min)

A mobile client sends the same 6 KB document a thousand times a minute. The server parses and
validates it a thousand times. No CDN can cache it, because it's a POST.

## Concept (15 min)

### Automatic persisted queries (APQ)

The client sends `extensions.persistedQuery: {version: 1, sha256Hash}` and no text. The server
answers from its store, or with `PersistedQueryNotFound`; the client then retries with the text and
the hash, and the server checks the hash, parses, validates and stores the document. graphql-java 26.1
implements the protocol in `ApolloPersistedQuerySupport` (a `PreparsedDocumentProvider`) over a
`PersistedQueryCache` you supply.

Measured (`_workbench/2026-11-21-m09-probe/apq.txt`):

- unknown hash: `PersistedQueryNotFound`, HTTP 200;
- text with a hash that isn't its SHA-256: `PersistedQueryIdInvalid`;
- **a known hash with different text runs the cached document and ignores the text** (club 2 asked,
  club 1 returned): the hash is checked only on a miss (`PersistedQuerySupport`, source in `gj-src/`).

### GET for CDN caching

With the hash in the URL, the request is a short GET, and a GET can be cached by Varnish or a CDN if
the response says so. Through Varnish (`wire.txt`, 50 dashboards):

| Mode | Request bytes | Hit rate | Median |
|---|---|---|---|
| POST | 281 | 0% | 17.3 ms |
| GET with the text | 357 | 98% | 0.4 ms |
| APQ GET | 187 | 98% | 0.3 ms |

The latency gain comes from GET plus `Cache-Control`, and any cacheable GET gets it. What APQ adds is
size: a 64-character hash instead of the document, below URL limits, and no parsing on the server.
One trap: with no `Cache-Control`, Varnish keeps a `PersistedQueryNotFound` for 120 s, so registration
doesn't take effect.

### Why APQ is not security

Anyone can register any document: send its text with its hash. APQ limits bandwidth, not what runs.
An allow-list of documents registered at build time (trusted documents, Module 10) is a security
control.
