# 9.3 java-dataloader and Spring

## Hook (2 min)

1,250 statements to 8, with the same response, byte for byte. Then one more field, written the way the
docs suggest, and the request never returns.

## Concept (15 min)

### The pieces

- **java-dataloader 6.0.0** (graphql-java 26.1 depends on it): `BatchLoader` answers a `List` in key
  order; `MappedBatchLoader` answers a `Map` and missing keys are null. A `DataLoaderRegistry` holds one
  loader per name, per request. `BatchLoaderEnvironment.getContext()` passes request context (the viewer,
  say) into the batch function.
- **Spring for GraphQL 2.1**: `BatchLoaderRegistry` registers loaders once at startup and Spring
  creates them per request; a `DataLoader` parameter on a `@SchemaMapping` method is found by name.
  `@BatchMapping` is the shortcut: a method from parents to a `Map<Parent, Value>`, registered and called
  for you.
- **Arguments go in the key.** `@BatchMapping` has no field arguments, so `members(first)` needs a loader
  keyed by `(clubId, first)`. One statement can still serve every key: number the rows per parent with
  `row_number() over (partition by club_id ...)` and keep the largest `first`.

### Dispatch strategies, and the hang

graphql-java 26 dispatches loaders per level (`PerLevelDataLoaderDispatchStrategy`): when every field
of a level has been asked for, it dispatches. A **chained** load, made in `thenCompose` after the first
load completes, comes too late for its level. If the first batch function is asynchronous, it is never
dispatched and the request hangs (`_workbench/2026-11-21-m09-probe/chain.txt`). With in-memory
`completedFuture` loaders the default works, so in-memory tests hide it.

Two flags fix it, per request, in the `GraphQLContext` (`DataLoaderDispatchingContextKeys`):
`setEnableDataLoaderChaining` and `setEnableDataLoaderExhaustedDispatching`. **Neither Spring for GraphQL
2.1.0 nor Boot 4.2.0 sets them** (both jars searched): in the Spring app, `ownerPicks` gave no response
in 10 s until a `WebGraphQlInterceptor` set the key.

## Check (3 min)

1. Why can't `members(first: 3)` and `members(first: 5)` share a key?
2. Your chained loader works in a unit test and hangs in the app. Why?

<details><summary>Answers</summary>

1. They have different answers. A key without the argument would give both aliases the same list.
2. The unit test's batch function returns a completed future, so the chained load runs before the level
   finishes. The app's loaders are asynchronous, and per-level dispatch never sends the late load
   unless chaining is enabled.
</details>
