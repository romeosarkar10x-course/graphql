# 9.8 Engine and JVM tuning

## Hook (2 min)

Switch to ZGC, the newest collector with the shortest pauses. At 256 MB the app's p50 went from 10 ms to
20 seconds.

## Concept (15 min)

### What there is to tune

- **Document caching**: a bounded `PreparsedDocumentProvider` parses and validates each distinct document
  once (about 19.5 µs saved per request, lab 9.7). APQ uses the same hook.
- **Schema build cost**: building the schema and its wiring at startup, once. Never per request.
- **Threads**: Spring MVC runs each request on a Tomcat thread (200 by default).
  `spring.threads.virtual.enabled=true` uses virtual threads instead: cheap to block, which helps when
  requests wait on I/O. The database pool (Hikari, 10 connections by default) is still the shared limit.
  Reactor (WebFlux) is the other road: non-blocking end to end, a different programming model.
- **GC**: G1, the default, balances throughput and pauses. ZGC collects concurrently with very short
  pauses, but needs headroom and spends CPU on barriers.

### The measurement

150 dashboards/s for 20 s, one run each (`_workbench/2026-11-21-m09-probe/tune-256m/`, `tune-1g.txt`):

| Config | 256 MB p50 / p99 | 256 MB failed | 1 GB p50 / p99 | GC pauses at 1 GB |
|---|---|---|---|---|
| platform, G1 | 10 / 28 ms | 0 | 10 / 27 ms | 466 ms |
| virtual, G1 | 10 / 27 ms | 0 | 9 / 17 ms | 395 ms |
| platform, ZGC | 20,001 / 60,001 ms | 2,984 | 12 / 21 ms | 3 ms |
| virtual, ZGC | 20,001 / 60,000 ms | 2,966 | 11 / 21 ms | 4 ms |

At 256 MB, ZGC logged 4,919 allocation stalls, then `OutOfMemoryError: Java heap space` killed Tomcat's
acceptor thread. At 1 GB it removed the pauses (3 ms against 466 ms in total) without improving the
percentiles: those pauses weren't what set this app's tail. These are single runs, so differences of a
few ms are noise.

### Picking with evidence

Same load, same heap, same machine, warmed up; more than one run; look at the logs behind every number
that surprises you. Then name what would change the answer: heap size, live data, request rate, slow
downstream calls, the percentile your SLO is written at.

## Check (3 min)

1. ZGC's pauses are 100x shorter. Why didn't p99 drop 100x?
2. When would virtual threads clearly win here?

<details><summary>Answers</summary>

1. GC pauses were a small part of the tail. The rest is CPU work, queueing and the database, and ZGC's
   concurrent work takes CPU from requests.
2. When requests block for a long time on I/O (a slow downstream service) and 200 platform threads run
   out while the CPU idles.
</details>
