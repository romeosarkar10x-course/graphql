# 9.5 Caching layers

## Hook (2 min)

Four caches, each one reasonable. Then a reader renames a book and still sees the old title, and another
signs in and is greeted by someone else's name.

## Concept (15 min)

### The four layers

| Layer | Lives | Shared by | Key | Invalidated by |
|---|---|---|---|---|
| per request | a DataLoader | one request | entity id | the request ending; `clear`/`prime` after a write in the same request |
| entity | Caffeine, in each JVM | all requests on one instance | entity id | eviction on write, TTL |
| response | Redis | every instance | everything the response depends on | mutations (tags or a flush), TTL |
| HTTP | browser, CDN (Varnish) | everyone behind it | URL plus `Vary` headers | `Cache-Control` max-age only, unless you purge |

Each layer up is shared more widely and harder to invalidate. A cache goes stale for one of two
reasons: nobody tells it the data changed, or two different questions share a key.

### Per-user keys

Anything personal (`viewer`, permissions, "my clubs") must be in the response key, or marked
`Cache-Control: private, no-store` for HTTP caches. Spring for GraphQL 2.1 sends **no Cache-Control at
all**, and Varnish 9.1's built-in rules then keep every GET for 120 s, including one sent with
`X-Shelfie-User` (`_workbench/2026-11-21-m09-probe/apq.txt`). POST is never cached by Varnish.

### Response caching in Spring

A `WebGraphQlInterceptor` can answer without executing:
`new WebGraphQlResponse(new DefaultExecutionGraphQlResponse(request.toExecutionInput(), result))`.
Store only error-free query responses, and never mutations.

### GET for HTTP caching

`spring.graphql.http.methods: GET,POST` (the default is POST only). A GET mutation is refused with 405,
with `Allow: POST,GET`, which lists GET even though GET was just refused.

## Java build (20 min)

Lab 9.5: an app with all four layers and five bug reports, one per scenario file.

## Experiment (15 min)

Five stale-data bugs; find which layer is guilty from the headers (`X-Response-Cache`, `X-Cache`,
`Cache-Control`), the statement count, and whether it happens within one request.

## Check (3 min)

1. A stale title shows `X-Response-Cache: MISS` and 3 statements. Which layer?
2. Why is `Vary: X-Shelfie-User` not enough on its own?

<details><summary>Answers</summary>

1. Not Redis (miss) and not Varnish (the app ran). Something in the app returned an old object: the
   entity cache, or the request's loader if the write was in the same request.
2. Some shared caches ignore or limit `Vary`, and a cache that does vary on it still stores one copy
   per user. `private, no-store` says plainly that nothing shared may keep it.
</details>
