# 9.4 Lookahead and smarter SQL

## Hook (2 min)

Eight statements is good. One statement must be better. The measurement says otherwise.

## Concept (15 min)

### Selection-set-driven fetching

A fetcher can see what the client selected below it: `DataFetchingFieldSelectionSet.contains("members/reviews/book")`,
and `getFields("members")` with each field's arguments. The root fetcher can then:

- **project**: read only the columns and tables asked for (`clubs { name }` reads one table);
- **join or nest**: fetch the whole tree in one statement and hand the children their data, so their
  resolvers don't load anything.

jOOQ's `MULTISET` nests a query per row: `multiset(select(...).from(membership).where(club_id = c.id))`
becomes a list inside each club. On PostgreSQL, jOOQ 3.21.9 renders it as a correlated subquery with
`jsonb_agg(jsonb_build_array(...))` (`_workbench/2026-11-21-m09-probe/lookahead-dashboard.sql`). JPA's
answer is an entity graph (`@EntityGraph`), which joins to-one and to-many associations up front.

### The measurement

100 dashboards after 20 warm-up requests (`compare.txt`):

| | Statements | Median | p95 |
|---|---|---|---|
| naive | 1,250 | 43.6 ms | 54.9 ms |
| batched | 8 | 11.6 ms | 17.3 ms |
| one MULTISET statement | 1 | 15.2 ms | 19.3 ms |

PostgreSQL built 1,000 small JSON arrays and the app parsed them, while the eight batched statements
were plain index range scans. A round trip to a local database costs about 0.1 ms, so seven fewer
round trips saved little.

### When it wins, and what it costs

It wins with expensive round trips (a remote database, a service), when the database can filter or
aggregate what loaders would fetch and discard, or when the selection lets you skip joins. It costs
code that knows the whole subtree, a fallback for aliases with different arguments, and SQL that must
agree with the loaders on order and limits.
