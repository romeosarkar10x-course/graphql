# 9.7 Measuring properly

## Hook (2 min)

"It feels faster" is not a result. A single curl isn't either. Neither is an average over a run that
started with a cold JVM.

## Concept (15 min)

### Two kinds of benchmark

- **Micro (JMH 1.37)**: one operation in a loop, with warm-up, forks and dead-code protection.
  Executing the dashboard document with no data takes 22.6 µs; with a cached parsed document, 3.1 µs.
  So parsing and validating cost about 19.5 µs per request (`_workbench/2026-11-21-m09-probe/jmh.txt`).
  It's a true number, but on its own it says nothing about the 14 ms a real request takes.
- **Load (Gatling 3.16.1)**: real requests against a running app. Use an **open** workload
  (`constantUsersPerSec`): users arrive at a fixed rate whatever the latency, so queueing shows. A
  closed loop of N users slows down with the server and hides it.

### Percentiles, warm-up, and where you measure

Report p50, p95 and p99, never only the mean. Warm up first: the same batched app, cold, gave
p50/p95/p99 = 15/422/837 ms; after a 10 s warm-up, 14/17/18 ms (`gatling.txt`, `before-after.txt`).

Client and server disagree. Micrometer's `graphql.request` percentiles (Spring for GraphQL's observation,
via actuator) reported p99 = 520 ms for that warm run. Its histogram covers a sliding window that still
held the warm-up (`percentile.txt`). Report the client's percentiles for the measured phase. Server
percentiles can't be averaged across instances either.

### Where the time goes

- **JDK Flight Recorder**: `-XX:StartFlightRecording`, then `jfr view hot-methods`.
- **async-profiler 4.6**: a CPU flame graph. Its Maven Central jar carries the native library, and
  `event=itimer` works in containers without perf_events. Both showed graphql-java's
  `PerLevelDataLoaderDispatchStrategy` and the per-key row filter in the batched app.

## Java build (20 min)

Lab 9.7: a JMH benchmark, a Gatling simulation, Micrometer percentiles, and `measure.sh` running them

## Experiment (15 min)

Before (naive) and after (batched), 20 dashboards/s for 20 s: p50/p95/p99 51/60/64 ms to 14/17/18 ms.

## Check (3 min)

1. Why an open workload?
2. Micrometer says p99 = 900 ms and Gatling says 64 ms for the same run. Which is wrong?

<details><summary>Answers</summary>

1. Real users don't wait for each other. A closed loop sends less when the server slows down, so it
   can't show the queue building.
2. Neither. They measured different things over different periods. Gatling measured the requests of the
   measured phase from outside; Micrometer measured a window inside the app that includes the warm-up.
</details>
