# 9.2 DataLoader from scratch

## Hook (2 min)

`Review.book` runs 1,000 times per dashboard, and all 1,000 run at the same level of the tree. What if
the first 999 calls only wrote down the id, and the last one asked for all of them?

## Concept (15 min)

### Batching per tick

A DataLoader separates *asking* from *fetching*. `load(key)` returns a future and remembers the key.
`dispatch()`, called when the engine has nothing else to do at this level, sends every remembered key to
a batch function in one call: `select ... where id = any(?)`. The engine then completes the futures,
and the resolvers' results resolve.

### The rules that make it correct

- **Key order.** The batch function answers a list of keys with a list of results in the same order.
  A `Map` answer (a "mapped" batch loader) avoids the ordering trap when rows can be missing.
- **Dedupe and memoisation.** A key asked for twice in one request is sent once; one asked for again
  later is answered from memory. That memory is **per request**: the cache is a consistency feature
  (one book is one object for the whole response), not a performance cache.
- **Per-key errors.** One missing book shouldn't fail 999 others: the batch answers each key with a
  value or an error. A failed batch fails all its keys.
- **Failures are not remembered** in java-dataloader 6.0.0: a second `load` of a key whose batch failed
  is sent again (`_workbench/2026-11-21-m09-probe/failcache.txt`).
- **Max batch size.** `where id = any(?)` with 50,000 ids is a statement too; split it.

### What dispatching costs

A load made after its level was dispatched (a chained load in `thenCompose`) waits for the next
dispatch. Lecture 9.3 shows what graphql-java does with that by default.

## Check (3 min)

1. Why must the memo be per request?
2. The batch function returns 9 results for 10 keys. What should happen?

<details><summary>Answers</summary>

1. Shared across requests it would be an entity cache with no invalidation: one user's rename would
   never reach another user's request (lab 9.5, scenario 1, is the per-request version of that bug).
2. Every key in that batch fails. Guessing which one is missing would hand some caller the wrong value.
