# 7.6 Designing for evolution

## Hook (2 min)

A REST API ships `/v2` and runs both for years. GraphQL's answer: clients select fields, so a schema
can grow forever and remove a field only when nobody selects it. That works only if every change is
classified before it ships, by a machine, against what clients actually send.

## Concept (15 min)

### Breaking, dangerous, safe

| Class | Meaning | Examples (lab 7.6, SchemaDiff verdicts) |
|---|---|---|
| Breaking | some valid operation stops validating, or a response stops matching its declared type | remove or rename a field; `Int` to `Int!` on an argument or input; a new required argument or input field; output `String!` to `String`; a field's type changes |
| Dangerous | every operation stays valid, but results can change meaning | new enum value; new union member; changed argument default; deprecation (SchemaDiff) |
| Safe | nothing a client did can go wrong | new field or type; new optional argument or input field; output `Book` to `Book!` |

The direction rule: an **output** may get stricter (`Book` to `Book!` gives readers a guarantee), an
**input** may get looser (`Int!` to `Int`). The reverse breaks someone.

### Two tools, two opinions

On lab 7.6's 15 changes, graphql-java 26.1's `SchemaDiff` and graphql-inspector 7.0.2 agree on every
breaking change and differ twice: a new optional argument is dangerous for inspector, unreported by
SchemaDiff; a deprecation is dangerous for SchemaDiff, safe for inspector
(`_workbench/2026-11-21-m07-probe/fifteen-changes.txt`). Both are right about what they model.

### Diffs are not clients

Game 7a shows the gap from both sides. SchemaDiff calls removing an unused field BREAKING, yet no client
breaks. And `publishedYear: Int` to `String` keeps every document valid (it's still a leaf), yet an app
that parses the value as a number fails at run time. The strongest gate validates the **operations clients
really send** (Module 10's trusted documents, Module 16's field usage) and uses the diff to classify.

### The deprecation lifecycle

1. Add the replacement (safe), then mark the old field `@deprecated(reason: "Use about: it supports
   Markdown.")`. The reason is Markdown (spec) and should name the replacement; the default, "No longer
   supported", tells nobody anything.
2. Measure usage per client. Announce a date (GitHub writes it in the reason: "Removal on 2027-01-01 UTC").
3. Remove when usage has been zero for a full client release cycle: a deliberate breaking release.

[RFC #1231](https://rfcs.graphql.org/rfcs/1231/) (RFC 1, advanced 2026-07-02) adds a rule that keeps step 1
honest: the schema with every deprecated element removed must itself be valid. Deprecating a type's only
field is then an error. [RFC #997](https://rfcs.graphql.org/rfcs/997/) (RFC 1) extends `@deprecated` to
object types, so a union member or interface implementation can be retired the same way.

## Java build (20 min)

Lab 7.6: classify 15 changes with both tools, then a Maven project whose JUnit test runs SchemaDiff
against the released schema (fail on breaking, print dangerous) and checks RFC #1231's rule; plus a GitHub
Actions workflow running it and graphql-inspector.

## Experiment (15 min)

Classify the 15 changes yourself first, then check against the tool. Write down every miss and the rule it
taught you. Then play game 7a.

## Check (3 min)

1. Why is `Book` to `Book!` safe on an output field but `Int` to `Int!` breaking on an argument?
2. Your diff gate fails a pull request that removes `Membership.joinedAt`. Field usage says nobody selects
   it. What should happen?

<details><summary>Answers</summary>

1. Readers of an output field already handle a value; a guarantee costs them nothing. Senders of an
   argument may omit or null it; requiring it rejects their documents.
2. It's a deliberate breaking change backed by evidence: approve it explicitly (most gates have an
   override label), ideally after a deprecation period announced to clients you don't see in the logs.
</details>
