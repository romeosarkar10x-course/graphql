# 7.7 Anti-patterns and boundaries

## Hook (2 min)

AniList's `Mutation.UpdateUser` takes 19 arguments; its `Query.Media` takes 75. GitHub has `databaseId:
Int` on 73 types, described as "Identifies the primary key from the database", now deprecated because 32
bits ran out. Big, successful APIs, and every one of these is in game 7b.

## Concept (15 min)

### The catalogue

| Anti-pattern | Looks like | Costs | Instead |
|---|---|---|---|
| Kitchen-sink update | `updateUser(input:)` with 15 fields from four screens | partial failures with nowhere to go; one permission for everything | one mutation per intent (`updateProfile`, `setNotificationPreferences`) |
| `JSON` escape hatch | `scalar JSON`, `settings: JSON` | no validation, docs, introspection or codegen; shape frozen anyway | model the shape; `@oneOf` inputs for "one of these" |
| Raw CRUD exposure | `insertReview`, `upsertMembership`, `deleteRow(table:)`, `rawQuery(sql:)` | clients learn tables; the API can't enforce rules; injection | intent mutations (`joinClub`); never SQL |
| Leaking database names | `tbl_users`, `ReviewEntity`, `owner_user_id`, `created_at` | storage changes become API breaks | domain names; references (7.3) |
| Boolean-flag arguments | `meetups(include_past: Boolean)`, `books(only_available: true)` | combinations nobody designed; unreadable call sites | enum argument (`when: UPCOMING`) or a filter input |
| Identity in arguments | `getNotifications(user_id:)` | anyone acts as anyone | a `viewer` entry point; identity from the request |
| Timestamps as numbers | `created_at: Int`, AniList `Media.updatedAt: Int` | seconds or millis? zone? | a `DateTime` scalar |
| Generic response | `Response { success message data: JSON }` | no changed object, so a refetch | `XPayload` with the object and `userErrors` (Module 4) |

`bin/course design lint --rules naming,references,json-scalars,boolean-args,kitchen-sink,db-names,crud-names,timestamps`
checks the mechanical part. Passing it is the floor.

### Boundaries: bounded contexts

A large schema is several teams' models in one graph. Group types by **bounded context** (domain-driven
design): Clubs, Catalogue, Reviews, Profiles, Notifications. Each context owns its types' data; fields on
the border (`Book.averageRating` is computed by Reviews but sits on a Catalogue type) need a stated owner.
The map is useful today for code ownership and essential in Module 15: a federated graph's subgraphs
follow these lines, and a border field becomes one subgraph extending another's type.

## Check (3 min)

1. `markNotificationsRead(input: { all: Boolean })` has a boolean. Is it the boolean-flag anti-pattern?
2. Why is a `viewer` field better than `user(id:)` with the caller's own id?

<details><summary>Answers</summary>

1. Not in the lint's sense (it's an input field, not an argument that changes what a field returns), but
   ask the question: `ids` or `all` is a "one of" choice, which `@oneOf` would state precisely.
2. The server decides who the caller is; with `user(id:)` the client could pass anyone's id, and private
   fields (email, settings) would need an extra authorisation check on every one of them.
</details>
