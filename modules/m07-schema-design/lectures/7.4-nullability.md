# 7.4 Nullability as a decision

## Hook (2 min)

Lab 3.4 showed where a null lands. Now the design question: the club page has 25 values. With every
field non-null, how many survive when the ratings service is down? Zero: one failing star rating
propagates up to `Query.club!` and `data` is null.

## Concept (15 min)

### `!` is a promise

Non-null says "never null, error or not". If a resolver fails anyway, the null propagates to the
nearest nullable ancestor ("null bubbling"). So a `!` is only safe where the value comes **with its
parent** and can't fail alone. A checklist, per field:

1. **Absent in correct data?** (no cover, signed out, nothing planned) Nullable. Done.
2. **Served by another service or query** than its parent? Nullable, because it can fail on its own.
3. Neither: non-null. A promise you can keep.

Lists have two decisions: the list (`[User!]` nullable, the service is down) and the items (`User!`,
each member is just an id).

### Semantic nullability

Step 2 makes fields nullable that are never null in correct data (`User.name`), so every client writes
null checks for outages only. The [Semantic Nullability RFC](https://rfcs.graphql.org/rfcs/SemanticNullability/)
(RFC 0) collects ways to say "null only on error". One of them, a directive:

```graphql
directive @semanticNonNull(levels: [Int!]! = [0]) on FIELD_DEFINITION
type User { name: String @semanticNonNull }
```

The wire type stays nullable (old clients see the same schema); clients that understand the directive
type the field as non-null and treat a null as "look in `errors`".

### Error behaviours (`onError`)

[RFC #1163](https://rfcs.graphql.org/rfcs/1163/) (RFC 1, champion Benjie Gillam) lets the client choose
per request what happens on an error: `PROPAGATE` (today's bubbling), `NULL` (the null stays where the
error happened) or `ABORT`. The working group decided on 2026-08-06 that PROPAGATE stays the default
forever. graphql-java 26.1 already has an experimental form of `NULL`: the operation directive
`@experimental_disableErrorPropagation` (enabled by default, `Directives.isExperimentalDisableErrorPropagationDirectiveEnabled()`).
With it, `!` goes back to meaning "never null in correct data", which is exactly what `@semanticNonNull`
writes down for clients that don't opt in.

## Check (3 min)

1. `Club.owner: User!` while `User.name: String @semanticNonNull`. Why not make `owner` nullable instead?
2. If every client sent `onError: NULL`, would you still need the audit?

<details><summary>Answers</summary>

1. The owner's id is on the club row, so the `User` object always exists; what fails is the profile
   behind it, field by field. Nulling `owner` would hide the owner's id and every healthy field.
2. Yes, for step 1: data that is genuinely absent must be nullable whatever the error behaviour. The
   error-only nullables (step 2) are what `onError: NULL` would let you make `!` again.
