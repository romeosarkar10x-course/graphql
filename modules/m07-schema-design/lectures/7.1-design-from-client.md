# 7.1 Design from the client

## Hook (2 min)

The starter of lab 7.1 is a schema nobody would write on purpose, yet most first schemas look like it:
`getClub(club_id: Int): club_row`, `owner_user_id`, `author_names: String`. It was written by looking at
the tables. Nobody looked at a screen.

## Concept (15 min)

### Demand-driven design

A schema is the API's **product surface**, and its users are client developers. Start from what a
screen shows (lab 7.1's `contract/screens/*.json`), not from what the database stores:

1. Write the screen's data as JSON, key for key: the **view model**.
2. Every object in it is a type; every key a field; every list a list (or a connection, 7.3).
3. Ask where each value comes from. Some come from no single table (`viewerIsMember` depends on the
   caller; a member's `role` belongs to the membership, not the member).
4. Only then write SDL, and write the query each screen sends. If the query's response doesn't have the
   screen's shape (aliases allowed), the design is not done.

Thinking in graphs: clients navigate from an entry point along fields (`club(id:)` to `owner` to
`clubs`), so relationships are fields that return objects, never ids to look up (7.3).

### Naming

The spec doesn't mandate a style; the ecosystem settled on one and tools assume it:

| Kind | Style | Shelfie |
|---|---|---|
| Types, interfaces, unions, enums, inputs | PascalCase | `Club`, `ClubRole`, `CreateReviewInput` |
| Fields and arguments | camelCase | `currentBook`, `memberCount`, `first` |
| Enum values | UPPER_CASE | `WANT_TO_READ` |

Name things by what they are to the client: `user(handle:)`, not `getUserById(user_id:)`. No `get`
(every query field gets), no table names, no transport suffixes (`Dto`, `Response`).

### Descriptions are the documentation

"Descriptions should be provided as Markdown (as specified by CommonMark) for every definition in a type
system" (September 2025 spec, "Descriptions"). They travel through introspection into every IDE,
explorer and code generator. A good description answers what the name can't: units and ranges ("1 to 5"),
order ("newest first"), and **what null means** ("Null between books"). `"The name"` on `name` is noise.

## Java build (20 min)

Lab 7.1: design the schema from three screens, write each screen's operation, and check it with
`bin/course design shape`, which runs the operation on mock data and compares the response's key paths
with the view model (`missing` and `extra` paths). `bin/course design lint` checks naming, descriptions
and references.

## Experiment (15 min)

The SDL-only test: hand only your `.graphqls` to a teammate (or an AI assistant, or yourself a day later)
and ask for the club page. Count the questions before they can start. Most are description gaps.

## Check (3 min)

1. Why is `viewerIsMember` on `Club` and not computed by the client?
2. Your query's field is `members(first: 5)` but the screen's key is `memberPreview`. Change the schema?
3. Which three facts should a description of a nullable list field state?

<details><summary>Answers</summary>

1. Only the server knows both the caller and the membership; the client would need the whole member list
   to work it out.
2. No: alias it in the query (`memberPreview: members(first: 5)`). Screen names belong to clients; the
   schema's name must suit every screen.
3. What null means (vs an empty list), the order, and any default or maximum size.
</details>
