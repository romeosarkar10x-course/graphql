# 7.3 Modelling relationships

## Hook (2 min)

`review { authorId bookId }`, then `user(id: $authorId)`, then `book(id: $bookId)`: three operations
and two round trips to draw one review card. GraphQL's whole pitch (Module 1) was one request per
screen. A foreign key in the schema takes it back.

## Concept (15 min)

### References, not keys

An output field that holds another object's key makes every client do the join. Return the object:
`author: User!`, `book: Book!`, `owner: User!`. The server already has the key; one fetcher turns it
into the object (and Module 9 batches those lookups). Inputs are different: `CreateReviewInput.bookId`
is fine, a client can't send an object.

### List or connection?

| | List `[User!]!` | Connection `UserConnection!` |
|---|---|---|
| Size | small and bounded (a book's authors) | unbounded (a club's members, a book's reviews) |
| Paging | never | `first`/`after`, `pageInfo` (Module 8) |
| Data about the pair | none | on the **edge** |
| Changing later | list to connection is **breaking** (the field's type changes) | - |

Decide by the largest realistic size, not by today's seed data. A plain list of 50,000 members is a
denial of service you shipped yourself.

### Edge data

Some facts belong to neither end of a relationship: Asha's **role** is MODERATOR in one club and MEMBER
in another; she **joined** each on a different day. On `User`, `role` would be one value for every club;
on `Club`, a map. On the edge between them, it is one value per pair:

```graphql
type ClubMemberEdge { cursor: String! node: User! role: ClubRole! joinedAt: String! }
```

If the relationship needs no paging, the same idea is a plain type: `memberships: [Membership!]!` with
`role`, `joinedAt`, `club` and `user` (lab 7.1's profile, mini-project request 2).

## Java build (20 min)

Lab 7.3: replace six keys with references, turn `memberIds` + `memberRoles` (two lists zipped by position)
into a `members` connection whose edges carry role and join date, and rewrite the review card as one
operation.

## Experiment (15 min)

Remove `authorId` from the schema; run `bin/course design clients` with the new schema on the old review
card. That validation error is what every deployed client would see. (Lecture 7.6: deprecate first.)

## Check (3 min)

1. Why is `CreateReviewInput.bookId: ID!` fine when `Review.bookId` is not?
2. `User.clubs` is a list. A product manager asks for the user's role in each club. List, connection, or
   neither?

<details><summary>Answers</summary>

1. Input is the client telling the server which object; output is the server telling the client, and
   there it can hand over the object itself instead of a key to look up.
2. Neither change to `clubs`: add `memberships: [Membership!]!`, a list of pair objects carrying the role.
   The relationship is still small, so no connection; the new data needs a type for the pair.
</details>
