# 7.2 Global object identification

## Hook (2 min)

Shelfie's ids are `c1`, `b1`, `u1`: unique per table. A client cache keyed by `id` stores Club `c1`, then a
Book with key `c1` overwrites it, if any table ever reuses a key. And a client holding only an id from
a push notification can't fetch the object: which root field takes it?

## Concept (15 min)

### The Relay convention

The [GraphQL Global Object Identification spec](https://relay.dev/graphql/objectidentification.htm)
(Relay's server specification) asks for:

- an interface `Node` that "must include exactly one field, called `id` that returns a non-null `ID`";
- a root field `node` that "must take exactly one argument, a non-null ID named `id`" and returns `Node`;
- refetch semantics: when the object can't be loaded (deleted, unavailable), `node` is null;
- identity: two objects with the same id in one response must be equal, field for field.

Optional "plural identifying root fields" take a list and return a list in the same order:
`nodes(ids: [ID!]!): [Node]!` with null where `node(id:)` would be null.

### Opaque global ids

Encode the type with the key: `base64url("Club:c1")` = `Q2x1YjpjMQ`. Base64 is not security; anyone can
decode it. It is a signal: **don't parse this**. Because clients don't build ids, the server can change
the encoding later (add a shard, a version prefix) without breaking anyone who only passes ids back.

Rules:

- `decode` must reject everything it didn't make (bad base64, no type, unknown type): null, not a crash.
- `Book:c1` (a club's key with a book's type) must not return the club: look up by type first.
- Keep the raw key available for integrations that need it, but under another name (`databaseId`, and
  see game 7b on what happened to GitHub's 32-bit one).

### Where it's going

The [Object Identification RFC](https://rfcs.graphql.org/rfcs/ObjectIdentification/) (RFC 0, proposed by
Lenz Weber-Tronic of Apollo) proposes an `__id` introspection field on every object, interface and union,
so a client with no schema knowledge can find out whether an object is identifiable. It's a strawman as
of 2026-11-21.

## Check (3 min)

1. Why must `nodes(ids:)` return `[Node]!` and not `[Node!]!`?
2. A client stores ids in its local database. You change the encoding from `Club:c1` to `v2:Club:c1`.
   What must `decode` do?

<details><summary>Answers</summary>

1. One unknown id would turn the whole list null under `[Node!]!`; the spec wants one entry per id, null
   where that one fails.
2. Keep accepting the old format forever (or as long as stored ids live): ids are persisted by clients, so
   the old encoding is part of the contract even though it is "opaque".
</details>
