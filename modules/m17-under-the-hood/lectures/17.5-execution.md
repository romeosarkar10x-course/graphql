# 17.5 Execution on virtual threads

## Hook (2 min)

Section 6 is about 15 pages of numbered steps. Follow them, one method per algorithm, and you have an executor
that gives graphql-java's responses on Module 2's operations. Put each field on a virtual thread and it is fast.

## Concept (20 min)

### The algorithms

```
ExecuteRequest(schema, document, operationName, variableValues, initialValue)
  GetOperation(document, operationName)                       6.1
  CoerceVariableValues(schema, operation, variableValues)     6.1.2
  ExecuteQuery / ExecuteMutation / Subscribe                   6.2
    ExecuteRootSelectionSet
      CollectFields(objectType, selectionSet, variableValues) 6.3.2
      ExecuteCollectedFields(...)                              6.3
        ExecuteField                                           6.4
          CoerceArgumentValues                                 6.4.1
          ResolveFieldValue                                    6.4.2
          CompleteValue                                        6.4.3
            ResolveAbstractType, CollectSubfields
```

`ExecuteCollectedFields` is new in the September 2025 edition (earlier: `ExecuteSelectionSet`): field collection
happens once, before execution. `CollectFields` applies `@skip` and `@include`, follows fragments whose type
condition applies, and groups fields by response name, in document order.

### Errors

- **Request errors** (parse, validation, `GetOperation`, `CoerceVariableValues`): `errors`, no `data`.
- **Execution errors** (6.4.4): the position becomes null, the error has `path` and `locations`. If the position
  is non-null, the null **propagates** to the nearest nullable parent; if there is none, `data` is null.

In Java one private exception does it: thrown by `CompleteValue` on a null in a non-null position, caught where
the type is nullable.

### Order and concurrency

The spec allows a query's fields to run in any order or in parallel ("normally"), and requires mutation root
fields to run one after another ("serially", 6.2.2). The response keeps document order either way.

Java 25's virtual threads make "one thread per field" cheap:

```java
try (var pool = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = new LinkedHashMap<String, Future<Object>>();
    fields.forEach((key, group) -> futures.put(key, pool.submit(() -> executeField(type, source, group, path.add(key)))));
    futures.forEach((key, f) -> result.put(key, join(f)));
}
```

A resolver that blocks for 200 ms blocks its virtual thread only; seven of them take 200 ms, not 1,400.
graphql-java uses `CompletableFuture`s instead: no thread at all while waiting, and DataLoader dispatch when a
level is waiting (Module 9). Same semantics, a different cost model.

## Check

1. A non-null field inside a nullable list item errors. What becomes null?
2. Why must `CollectFields` group by response name rather than field name?
3. What does the response look like when `CoerceVariableValues` fails?

<details><summary>Answers</summary>

1. The list item (the nearest nullable position), not the list; the error has the full path with the index.
2. Aliases: `a: title` and `b: title` are two entries; `title` twice is one entry, executed once with its
   sub-selections merged.
3. `{"errors": [...]}` with no `data` entry: it is a request error (7.1.3).
