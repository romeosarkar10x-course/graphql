# 17.4 Validation

## Hook (2 min)

A document that parses can still be nonsense: a field that does not exist, two fields fighting over one response
key, a fragment that spreads itself. Validation is the spec's list of what a server must reject before running
anything.

## Concept (20 min)

### The rules

Section 5 has about 30 rules, each with a formal specification. Six of them cover the hard algorithms:

| Rule | Section | Idea |
| --- | --- | --- |
| FieldsOnCorrectType | 5.3.1 | every field exists on its parent type (or is `__typename`) |
| OverlappingFieldsCanBeMerged | 5.3.2 | same response name, same field and arguments, mergeable shapes |
| KnownArgumentNames | 5.4.1 | every argument is defined on its field or directive |
| NoFragmentCycles | 5.5.2.2 | fragment spreads do not form cycles |
| NoUnusedVariables | 5.8.4 | every defined variable is used (through fragments too) |
| VariablesInAllowedPosition | 5.8.5 | `IsVariableUsageAllowed`: a variable's type fits where it is used |

### Field merging

The hardest. `FieldsInSetCanMerge(set)`:

1. For each pair with the same response name, `SameResponseShape` (scalars equal, lists and non-nulls match,
   sub-selections merged recursively).
2. If the parent types are equal or not both object types, the field names and arguments must be identical, and
   the merged sub-selections must merge too.

Fragments and cycles make it expensive: implementations compare pairs once and remember them.

### Variables in position

`$id: ID` used where `ID!` is expected is invalid, unless the variable has a default or the position has one
(`IsVariableUsageAllowed`). `[Int]` fits `[Int]`; `Int` fits `[Int]` only through input coercion, which is not
allowed here (`AreTypesCompatible`).

### Counting errors

The spec says when a document is invalid, not how many errors to report. graphql-java 26 reports a cycle once per
fragment at either end of the back edge; graphql-js counts differently. The lab compares error counts exactly for
four rules and "fires or not" for these two.

## Check

1. Why is `{ book(id: 1) { title } book(id: 2) { title } }` invalid?
2. `{ search(text: "a") { ... on Book { id: title } ... on Club { id } } }`: valid?
3. When may `$n: Int` be used for an argument of type `Int!`?

<details><summary>Answers</summary>

1. Same response name, different arguments, same parent type.
2. No. The parents (`Book`, `Club`) are different object types, so the field names may differ, but
   `SameResponseShape` still applies: `title` is a `String!` and `Club.id` an `ID!`, different scalars under one
   response name.
3. Only when the variable has a non-null default or the argument has a default value (`IsVariableUsageAllowed`,
   5.8.5); a null at run time is then a field error.

</details>
