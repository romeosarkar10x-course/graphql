## Concept (15 min)

### The edition

GraphQL over HTTP, **September 2026 edition** (https://http-spec.graphql.org/September2026/, published
2026-11-12): requests by GET and POST, `application/graphql-response+json`, status codes, legacy clients.
Recap from Module 5:

| Situation | `application/graphql-response+json` |
| --- | --- |
| JSON body cannot be parsed | 400 |
| not a well-formed GraphQL-over-HTTP request (wrong parameter types) | 422 |
| document does not parse | 400 |
| validation fails, operation unclear, variables do not coerce | 422 |
| executed (even with field errors) | 200 |

For a legacy client (it accepts only `application/json`), the edition says to behave "as if the request had
specified `Accept: application/graphql-response+json`", replacing the Content-Type only on 2xx responses.

### graphql-http

[graphql-http](https://github.com/graphql/graphql-http) 1.23.1 (MIT, 2026-09-28) has an audit suite: each audit
has an id, a level (MUST, SHOULD, MAY) and a request. It was released before the edition, and in places it audits
older text: it asks for 200 for parse, validation and coercion failures with `application/json` (572B, FDE2,
7B9B), 400 for coercion failures (86EE), and offers 400 where the edition says 422 (18 MAY notices). An audit is a
tool: the spec decides.

### Beyond the edition

- **Batching** (an array of requests in one body) is not in the edition. It hides a slow operation behind others
  and defeats per-request limits; HTTP/2 multiplexing does the same job.
- **Persisted documents** (an id instead of `query`) are not in the edition either; Module 10 used them for
  safelisting.

## Experiment (10 min)

Read graphql-http's source for audit 572B: the exact request it sends and what it checks. Then find the sentence
in the edition that answers it.

## Check

1. Which status does the edition give a request whose `variables` is a string?
2. A client sends `Accept: application/json` and a document that fails validation. Status and Content-Type?
3. Why is a JSON `null` for `operationName` not an error?

<details><summary>Answers</summary>

1. 422: parameters of the wrong type make it not well-formed.
2. 422 with `Content-Type: application/graphql-response+json`: the edition handles it as if the client had
   asked for that media type, and replaces the Content-Type with `application/json` only on 2xx responses.
3. The parameters are optional, and null is JSON's way to say "none"; graphql-http's 0221 is a MUST.

</details>
