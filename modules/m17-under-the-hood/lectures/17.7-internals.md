# 17.7 graphql-java internals

## Hook (2 min)

You have built every part of an engine in about 1,500 lines. graphql-java's main sources are about 99,000 lines
(v26.1, comments included). Where
does the difference go?

## Concept (20 min)

### The path of a request (v26.1)

```
GraphQL.execute
  ParseAndValidate          parser.Parser (ANTLR) → GraphqlAntlrToLanguage → language.Document
                            validation.Validator → OperationValidator (all rules, one walk)
  Execution                 ValuesResolver.coerceVariableValues
    AsyncExecutionStrategy  (AsyncSerialExecutionStrategy for mutations)
      ExecutionStrategy     resolveFieldWithInfo → fetchField → completeField → completeValue
  Instrumentation hooks around every step; PreparsedDocumentProvider caches parse + validate
```

### Where the lines go

- **Limits and safety**: `ParserOptions` (1 MB of characters, 15,000 tokens by default), complexity and depth
  limits, good-faith introspection checks.
- **Extension points**: `Instrumentation`, `DataFetcher` and `DataFetcherResult`, custom scalars with three value
  forms (external, internal, literal), type resolvers, schema transformations.
- **Performance**: `CompletableFuture`-based execution with DataLoader dispatch, cached parsing and validation,
  `ExecutableNormalizedOperation`.
- **Features beyond the spec**: `@defer` (incremental delivery, not in the September 2025 edition), field visibility, schema diffing,
  printing with options.

### Differences you have met

The ANTLR grammar files differ from the spec in a few places (U+2028, `{}` in SDL, the lookahead). The built-in
introspection types are built in Java, with graphql-java's own descriptions. Validation is one visitor, so error
counts follow its traversal.

### Building it

graphql-java builds with Gradle (wrapper 9.4.0, Java 25 toolchain, release 11 bytecode). `publishToMavenLocal`
installs it into `~/.m2`, where any Maven project can use it. Read `build.gradle`'s version and signing blocks
first: the lab spells out what they mean.

## Check

1. Which graphql-java class corresponds to your `Validator`, and how is it organised differently?
2. Why do graphql-java's custom scalars need three conversions?
3. What does `-PpublishToMavenLocal` change in graphql-java's build?

<details><summary>Answers</summary>

1. `OperationValidator`: all rules in one class, one traversal, with a predicate to select rules; ours walks once
   per rule.
2. Values arrive as JSON (variables), as AST literals (in the document) and as Java objects (from resolvers), and
   must convert between them (`serialize`, `parseValue`, `parseLiteral`; `ValuesResolverConversion`).
3. Signing becomes optional (`setRequired { !project.hasProperty('publishToMavenLocal') }`), so no PGP key is
   needed.

</details>
