# 17.1 Reading the spec and the RFC process

## Hook (2 min)

Sixteen modules of servers that reject this, null that, and refuse a third thing. Every one of those behaviours is
a sentence in one document. This module reads that document, then builds an engine from it.

## Concept (20 min)

### The document

The GraphQL specification, **September 2025 edition** (https://spec.graphql.org/September2025/), is the course's
baseline. Seven sections and five appendices:

| Section | What it defines |
| --- | --- |
| 2 Language | the grammar: lexical tokens (2.1), documents, operations, fragments, values |
| 3 Type System | types, SDL, extensions, the built-in directives (3.13) |
| 4 Introspection | `__typename`, `__schema`, `__type` and the `__*` types |
| 5 Validation | the rules a document must pass before execution |
| 6 Execution | the algorithms: `ExecuteRequest`, `CollectFields`, `ExecuteField`, `CompleteValue` |
| 7 Response | `data`, `errors`, `extensions`, request vs execution errors |
| Appendices | notation (A), conformance (B), grammar summary (C), the specified definitions (D), examples (E) |

The **draft** (https://spec.graphql.org/draft/) has what has been accepted since. Example: empty selection sets
(RFC #1227), accepted and merged on 2026-09-17, are in the draft but not the edition.

### How to read it

- **Grammar** productions: `Name :: ...` is lexical (characters), `Name : ...` syntactic (tokens). `list`, `opt`,
  and `[lookahead ...]` constrain them (appendix A).
- **Algorithms** are numbered steps with names like `CoerceVariableValues()`. An implementation that follows the
  steps conforms. That is how this module's engine is written: one method per algorithm.
- **Normative words**: must, should, may (appendix B; RFC 2119). "Should" leaves implementations room; this is
  where engines differ.
- **Validation rules**: an informal paragraph, a **Formal Specification** in steps, an **Explanatory Text** with
  counter-examples.

### What changes it: RFCs

From graphql-spec's CONTRIBUTING.md: an RFC has a **champion** and moves through stages, usually at Working Group
meetings:

| Stage | Entrance |
| --- | --- |
| 0 Strawman | none: a problem, maybe a sketch |
| 1 Proposal | a champion, problem and solution with examples, incomplete spec edits, known drawbacks |
| 2 Draft | consensus this is the preferred solution, precise spec edits, a GraphQL.js implementation |
| 3 Accepted | complete spec edits, a tested GraphQL.js implementation; merged by an editor, in the next edition |
| X Rejected | |

Examples (rfcs.graphql.org, read 2026-11-23): #849 full Unicode in strings (Accepted, in this edition's lexer,
lab 17.2); #1058 list coercion (Draft); #1179 `CoerceInputValue()` (Proposal); #1227 empty selection sets
(Accepted). Guiding principles include "favor no change" and "simplicity and consistency over expressiveness and
terseness".

### Implementations lag

graphql-java 26.1, the course's engine, rejects a description on an operation (`"Lists clubs." query { ... }`):
the September 2025 edition added it (RFC #1170). This module finds a dozen such gaps, and checks each one against
the text.

## Check

1. Which part of the spec decides that `{ a: b a: c }` is invalid: grammar, validation or execution?
2. What makes something a request error rather than an execution error?
3. At which stage must an RFC have a GraphQL.js implementation, and at which must it be merged?

<details><summary>Answers</summary>

1. Validation: 5.3.2 Field Selection Merging. It parses fine.
2. It happens before execution starts (parse, validation, operation selection, variable coercion): the response
   has `errors` and no `data` entry (7.1.3).
3. Draft needs one (it might not be merged); Accepted needs a tested one, merged or ready to merge.
