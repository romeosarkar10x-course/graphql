# 10.4 Demand control

## Hook (2 min)

The fan-out query from 10.3 passes graphql-java's depth limit (100) and field limit (100,000). Its cost,
with list sizes multiplied in, is 43,388,772. Shelfie's most expensive real screen costs 430.

## Concept (20 min)

### Five limits, five attacks

| Limit | Stops | When it runs |
|---|---|---|
| Depth, field count (`QueryComplexityLimits`) | deep nesting, alias floods | validation, before any resolver |
| Cost (`MaxQueryComplexityInstrumentation` + `FieldComplexityCalculator`) | fan-out | before execution |
| List caps (`first` ≤ 50) | one enormous page | per field |
| Timeout (cancel the `ExecutionInput`) | slow fields within budget | during execution |
| Cost budget per caller (token bucket) | brute force, scraping, many cheap requests | before execution, across requests |

graphql-java 26 ships `QueryComplexityLimits` with defaults of depth 100 and 100,000 fields, set per request
through the `GraphQLContext` (`QueryComplexityLimits.KEY`) or JVM-wide. The defaults stop absurd documents;
they are far above any real screen and far below nothing an attacker needs.

### A cost function

`cost(field) = own + children`, times `first` for a list. `books(first: 10) { title }` costs
10 × (1 + 1) = 20. Weight slow fields (Shelfie's `recommendations` weighs 10). The cost is a prediction from
the document and variables: it charges the page size asked for, not returned. Publish it
(`extensions.cost`) so clients can see what they spend.

### Tuning

Price every real operation (the client's documents, or production logs), set the limit well above the
most expensive, then check that each attack from 10.3 still fails. Lab 10.4's values: depth 10, 500 fields,
cost 5,000, `first` ≤ 50, 1 s, 10,000 points a minute. Real screens cost 108 to 430 (measured).

### Rate limits that understand GraphQL

Count cost, not requests: a bucket of points per caller per minute (Bucket4j: capacity, greedy refill),
keyed by user, or by IP for anonymous callers. Refuse with a code and a retry time.

## Java build (20 min)

Lab 10.4's `DemandControl`: a `WebGraphQlInterceptor` that puts the limits into each request's context, the
cost instrumentation, an instrumentation that wraps data fetchers for list caps and cancels the input after
1 s, and a budget instrumentation that computes the same cost with `QueryComplexityCalculator` and spends
it from the caller's bucket. Mind the edge: `{ __typename }` costs 0, and Bucket4j refuses to consume 0
(finding 17).

## Experiment (15 min)

Tune until `tests/attacks.hurl` fails all seven attacks and `tests/real.hurl` passes all eight screens. Then
find a real query your cost function prices badly.

## Check

1. Why is a cost limit needed when depth and field limits are in place?
2. `clubs(first: 10) { members(first: 10) { clubs(first: 10) { name } } }`: its cost with Shelfie's function?
3. Why does the timeout have to cancel the execution rather than just stop waiting for it?

<details><summary>Answers</summary>

1. Depth and field counts measure the document, not the work: a depth-7, 8-field query made millions of
   fetches because each list multiplies the next.
2. 10 × (1 + 10 × (1 + 10 × (1 + 1))) = 10 × (1 + 10 × 21) = 2,110.
3. Abandoning the response leaves the resolvers running and holding a thread and memory; cancelling the
   `ExecutionInput` makes graphql-java stop dispatching fields.
</details>
