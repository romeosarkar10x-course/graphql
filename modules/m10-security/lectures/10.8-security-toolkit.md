# 10.8 Security testing toolkit

## Hook (2 min)

graphql-cop scanned the vulnerable fork and reported five problems. The fork has at least thirteen. The
scanner missed the forged token, the SQL injection, and every authorization bug.

## Concept (15 min)

### What each tool is for

| Tool | What it does | Here |
|---|---|---|
| **graphql-cop** 1.15 | 13 checks for misconfiguration: aliases, directives, field duplication, introspection, GET, CSRF via url-encoded POST, IDE, tracing | `bin/course seckit graphql-cop` |
| **Clairvoyance** 2.5.5 | rebuilds a schema from "Did you mean" suggestions when introspection is off | `bin/course seckit clairvoyance` |
| **InQL** | Burp Suite extension: generates requests for every operation, finds cycles | described only (needs Burp's GUI) |
| **DVGA** | Damn Vulnerable GraphQL Application, a practice target | described only; the course's fork plays that role |
| **OWASP ZAP** | general web scanner with a GraphQL add-on: imports a schema, fuzzes arguments | described only (large image) |

### Scanners check patterns

Each graphql-cop check is one request and one condition (101 aliases answered; exactly 10 errors for 10
directives; 500 copies of `__typename` answered). Fix the cause, not the condition, and read why it fired:
lab 10.4's field limit refused only *more than* 500 fields, so graphql-cop's 500 passed. The scan also
caught a real bug: `{ __typename }` costs 0 and crashed the cost budget (finding 17). What scanners cannot
see: authorization (`node(id:)` leaks), business logic (mass assignment, request-versus-attempt rate
limits), token handling, injection behind a specific argument.

### Introspection off is not a secret schema

Clairvoyance recovered nothing from graphql-java (no suggestions, and it does not parse graphql-java's
messages; finding 22). But a wordlist still works by hand: an unknown field says `FieldUndefined`, a real
one says `SubselectionRequired for type '[Book!]!'` or `Missing field argument 'id'`. Trusted documents
close that door; introspection off only narrows it.

### Regression tests

Every finding and every exploit becomes a test that would fail if the fix were undone. The proof that a
test tests something: run it against a server that has the bug. Lab 10.8's suite runs against your server
(all pass) and the vulnerable fork (8 or more must fail).

## Java build (20 min)

Lab 10.8: `ShapeLimits` (aliases ≤ 30, directives ≤ 10, none repeated) as a `PreparsedDocumentProvider`,
the field limit at 200, introspection off, and a JUnit 6 suite of black-box HTTP tests.

## Experiment (15 min)

Scan, fix, rescan. Run Clairvoyance with introspection off. Then list what lab 10.3 and the capture the flag
found that the scanner did not.

## Check

1. graphql-cop reports no findings. Is the server secure?
2. Why must a security regression test be run against a vulnerable server too?
3. Introspection is off. How could an attacker still learn `Query.books` exists and returns `[Book!]!`?

<details><summary>Answers</summary>

1. No: it means none of 13 configuration patterns matched. Authorization, logic and token handling are
   untested by it.
2. A test that passes on both a fixed and a broken server checks nothing; failing on the broken one
   proves it detects the bug.
3. Send `{ books }`: graphql-java answers "Subselection required for type '[Book!]!' of field 'books'".
</details>
