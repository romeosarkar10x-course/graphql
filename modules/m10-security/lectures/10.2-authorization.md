# 10.2 Authorization

## Hook (2 min)

`club(id: "c1")` returns null to ben: the private club is hidden. `node(id: "v1")` hands him its first
review anyway. Same data, a second door, no check.

## Concept (15 min)

### Rules live in the business layer

Authentication says who; authorization says what they may do, and it belongs next to the data, not in the
transport and not in the schema alone. GraphQL makes this urgent because every object is reachable many
ways: by id (`club`), through the generic `node(id:)`, through lists on other types (`Book.reviews`,
`Reader.clubs`), and through mutation payloads. The rule "a private club and its reviews are for members"
must hold on every path, so write it once (`Access.canSee(Club)`) and call it everywhere a club or review
leaves the server.

### Three granularities

- **Row level**: which objects exist for this caller (private clubs, their reviews). Usually: return null
  or filter the list, as if the object did not exist, so ids cannot be probed.
- **Field level**: which fields of a visible object (`email` for its owner, `inviteCode` for the club's
  owner). Usually: null for the field, the object stays.
- **Operation level**: which mutations (`renameClub` for the owner). An error: the caller asked to do
  something.

Spring for GraphQL classifies Spring Security's exceptions for you: `AccessDeniedException` becomes
`FORBIDDEN`, or `UNAUTHORIZED` when the caller is anonymous (finding 6).

### Where the leaks are

1. `node(id:)` (Relay's global object identification) resolves anything by id: it must apply row rules.
2. Lists and connections on *other* types: `Book.reviews` showed reviews from every club.
3. Subscriptions: the check must run when the client subscribes. A filter on the event stream runs on
   the thread of whoever caused the event, with *their* security context (lab 10.2's `reviewAdded`).
4. Error messages and counts: "not a member of c1" confirms c1 exists; `totalCount` can count hidden rows.

### Declaring rules in the schema

A directive like `@auth(role: MODERATOR)` makes the rule visible to clients and reviewers. It is only
documentation until code enforces it: a `SchemaDirectiveWiring` wraps each annotated field's data fetcher.
Role rules fit directives; row rules ("member of this club") need data and belong in services.

## Java build (20 min)

Lab 10.2: one `Access` component; `@PreAuthorize("@access.isMember(#clubId)")` on `ClubService`
(`@EnableMethodSecurity`), so a REST endpoint or a job calling the service gets the same rule; a
`SchemaDirectiveWiring` for `@auth`, registered with a `RuntimeWiringConfigurer`.

## Experiment (15 min)

Write `my-forbidden.hurl` before you write a single rule: for anonymous, ada, ben, max, olu and root, try
every path to a private review, an email and an invite code, and every mutation they should not run. Watch

## Check

1. Why null for a hidden club, but an error for a forbidden mutation?
2. Name three paths to a private review in Shelfie's schema.
3. What does `@auth(role:)` in the SDL do without a wiring?

<details><summary>Answers</summary>

1. Null makes a hidden object indistinguishable from a missing one, so ids cannot be probed. A mutation
   is an explicit request; the caller needs to know it was refused, and why (FORBIDDEN, UNAUTHORIZED).
2. Any three of: `node(id: "v1")`, `club(id: "c1") { reviews }`, `book(id:) { reviews }`,
   `node(id: "r4") { ... on Reader { clubs { reviews } } }`, a `reviewAdded` subscription.
3. Nothing: it is metadata. graphql-java keeps the applied directive on the field; only code that wraps
   the data fetcher enforces it.
</details>
