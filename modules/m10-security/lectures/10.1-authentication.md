# 10.1 Authentication

## Hook (2 min)

Nine tokens, one query: `{ viewer { id } }`. Two get an answer. Seven get a 401 before GraphQL has parsed
a single character, and one of the seven claims to be `root` without any signature at all.

## Concept (15 min)

### Who is calling is an HTTP question

Authentication belongs at the HTTP layer, in front of GraphQL: a filter verifies the credential and hands
the request a principal, or refuses it. Resolvers never see a raw token. Reasons:

- one request holds many fields; a check in each resolver is a check someone forgets;
- a bad credential should cost nothing: no parsing, no validation, no partial `data`;
- one policy covers `/graphql`, GraphiQL, actuator and REST alike, and a 401 with `WWW-Authenticate` is
  something every client and proxy understands.

Anonymous is still allowed: a request with **no** token is anonymous (`viewer: null`), a request with a
**bad** token is refused. Lab 10.1's probe: expired, forged, unsigned, wrong audience, wrong issuer and
malformed tokens all got 401 with `Bearer error="invalid_token"`; a `Basic` header was ignored, so that
request was simply anonymous (`_workbench/2026-11-21-m10-probe/FINDINGS.md` items 2 and 3).

### Sessions or tokens

| | Session cookie | JWT bearer token |
|---|---|---|
| Server state | yes, a lookup per request | none: verify the signature offline |
| Logout / revocation | instant | waits for `exp`, or a deny list |
| Sent by the browser on its own | yes, so CSRF must be defended (10.3) | no: JavaScript adds the header |
| Readable by page scripts | no (`HttpOnly`) | yes, if stored in the page |

Shelfie uses short-lived JWTs (5 minutes) because its API serves a web app, a CLI and, from Module 15,
other services that verify offline. A browser-only product often does better with a session cookie held by
a backend-for-frontend.

### OAuth 2 and OpenID Connect in one paragraph

The user signs in at an **authorization server** (Keycloak here), which issues an **access token** for an
**audience** (`shelfie-api`). The API is a **resource server**: it checks the signature against the
issuer's keys (JWKS, found through `/.well-known/openid-configuration`), then `iss`, `aud`, `exp`. OIDC adds
identity: claims like `preferred_username`. Browser and mobile clients get tokens with the **authorization
code flow with PKCE**; lab 10.1's tests use the password grant only because they have no browser.

### The `viewer` field

`viewer` is the GraphQL face of authentication: "the signed-in user, or null". It needs no argument, so a
client cannot ask for someone else's private view by changing an id, and caching layers can key on it.

## Java build (20 min)

Lab 10.1: `spring-boot-starter-oauth2-resource-server` (Spring Security 7.2), configured from properties:

```yaml
spring.security.oauth2.resourceserver.jwt:
  issuer-uri: http://keycloak:8180/realms/shelfie   # finds the JWKS, checks iss
  audiences: shelfie-api
  principal-claim-name: preferred_username
  authorities-claim-name: roles
  authority-prefix: ROLE_
```

and a `SecurityFilterChain` that permits every path, validates any bearer token, turns off sessions and
CSRF (no cookies are involved). `viewer` takes `@AuthenticationPrincipal Jwt jwt`, null when anonymous.

Keycloak runs as a course service (`bin/course ref up`, `http://keycloak:8180`), not in Testcontainers:
the course container has no Docker socket. Its realm signs with a key that is in the repository on purpose
(`contract/keys/README.md`), so `bin/course token ada --expired` can mint tokens Keycloak never would.
From lab 10.2 on, apps verify offline with `public-key-location` and never call Keycloak. They check `iss` with a
`JwtIssuerValidator` bean instead of `issuer-uri`: on Spring Boot 4.2, `issuer-uri` next to a public key still
makes Spring fetch Keycloak's discovery document on the first token, and fail when Keycloak is down
(`SecurityConfig.courseIssuer()`; finding 4).

## Experiment (15 min)

Call `{ viewer { id name roles } }` with no token, a Keycloak token, and `bin/course token` with
`--expired`, `--forged`, `--none`, `--aud other-api`, `--iss http://evil.test/...`. Record the status and
the server's words for each. Then decode a token (`cut -d. -f2 | base64 -d`) and find every claim the app
relies on.

## Check

1. Why is a request with no token treated differently from a request with a bad token?
2. What does a resource server check in a JWT, in order?
3. Where does `viewer` get the reader from, and why does it take no argument?

<details><summary>Answers</summary>

1. No token is a legitimate anonymous caller (public data). A bad token is a client error or an attack;
   answering it anonymously would hide the problem and let a forged token degrade silently.
2. Structure, the signature against the issuer's key (picked by `kid`, algorithm from the configuration,
   never from the token), then `exp`/`nbf`, `iss`, `aud`. Spring Security's `JwtValidators` do the claims.
3. From the verified principal in the security context (`@AuthenticationPrincipal`). Without an argument
   there is nothing for a client to tamper with, and "me" stays one cacheable shape.
</details>
