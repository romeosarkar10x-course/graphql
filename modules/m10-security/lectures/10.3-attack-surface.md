# 10.3 The attack surface

## Hook (2 min)

A 300-byte query, no token, depth 8, under every default limit: 241,230 field fetches. One level deeper
and the server is dead (`OutOfMemoryError`, process gone). The next request gets no connection.

## Concept (20 min)

GraphQL has generic web risks (injection, CSRF) and some of its own, because the client writes the query.

| Attack | What it does | graphql-java 26.1 + Spring by default |
|---|---|---|
| Deep nesting | cycles in the schema (`Book.reviews.book...`) make any depth valid | refused over depth 100 |
| Fan-out | lists inside lists multiply: 12 × 10 × 12 × 10 ... | **allowed**: 241,230 fetches passed |
| Alias overloading | the same expensive field 500 times in one request | allowed under 100,000 fields / 15,000 tokens |
| Batched brute force | 1,000 `joinClub` attempts as aliases in one request | allowed: request rate limits miss it |
| Fragment cycles | `...A` spreads `...B` spreads `...A` | refused at validation |
| Field suggestions | "Did you mean 'inviteCode'?" leaks the schema | **never** suggests |
| Introspection | the whole schema, deprecated internals included | on (abusive shapes refused by the good-faith check) |
| CSRF | a cross-site `<form>` posts a mutation with the victim's cookies | GET mutations 405, `text/plain` 415 |
| Injection | a resolver builds SQL from an argument | the resolver's problem, as anywhere |

Measured in lab 10.3 and `_workbench/2026-11-21-m10-probe/FINDINGS.md` items 7 to 13.

### Why depth is the wrong worry

Depth alone is cheap when each level has one item (98 levels, 98 fetches, 12 ms). Cost comes from
multiplying lists. A limit must price `first` (lecture 10.4).

### Request counting is not attempt counting

A rate limit of "10 requests a minute" let 6,000 invite-code attempts through in 6 requests. GraphQL
puts many operations' worth of work in one request; limits must count what resolvers do.

### CSRF in GraphQL

Three conditions together: credentials the browser sends by itself (a cookie), a request a cross-site page
can send without a CORS preflight (GET, or POST with a "simple" content type: `text/plain`, form
encodings), and no CSRF token. Spring for GraphQL refuses mutations over GET (405) and `text/plain` (415) on
its own; the vulnerable fork's "compatibility" filter undid the second, and its cookie token supplied the
first.

## Java build (10 min)

`contract/vulnerable-shelfie/` is the fork: every shortcut has its excuse in a comment. `vulnerable.sh`
starts it with a 512 MB heap that exits on `OutOfMemoryError`; `attack.sh` sends one request and prints
status, time, bytes, the server's CPU time and memory from `/proc`.

## Experiment (25 min)

Lab 10.3: run each attack, record what it cost, then crash the node on purpose. Note which attacks the
defaults stopped and which need a limit you write.

## Check

1. Why did a 98-level query cost almost nothing while an 8-level one cost 241,230 fetches?
2. A rate limit allows 10 requests a minute. How many invite codes can one attacker try per minute?
3. Which three choices made the fork's CSRF work?

<details><summary>Answers</summary>

1. The deep query followed one review per level; the 8-level one multiplied lists of 10 and 12 at every
   level. Cost is the product of list sizes along each path, not the depth.
2. About 10,000: 10 requests of about 1,000 aliases each (the parser's 15,000-token cap allows that many).
3. Tokens accepted from a cookie, a filter treating `text/plain` as JSON (no preflight), and CSRF
   protection off.
</details>
