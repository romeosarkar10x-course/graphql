# 10.6 Public API security

## Hook (2 min)

A naive client sends 40 requests as fast as it can: 8 answered, 32 throttled, job failed. A client that
reads two numbers from each response does all 40 in 5.4 seconds, never throttled.

## Concept (15 min)

### You cannot allowlist strangers

Third-party developers write their own documents, so trusted documents (10.5) do not apply. A public
GraphQL API instead **identifies** each client app, **limits** what it may do and how much, and **tells**
it where it stands.

- **API keys** identify the app (the bearer token still identifies the user). A key shipped in a mobile
  or browser app is not a secret: it identifies, it does not authenticate.
- **Scopes** limit each key (`read`, `write:reviews`, `write:clubs`). Both rules apply: the review bot may
  write reviews, but only where the user may.
- **Cost budgets** per app: a leaky bucket (a maximum and a restore rate per second) charged with each
  query's computed cost, so one integration cannot starve another.
- **Abuse monitoring**: served and throttled counts per key, cost per request, keys seen from many places.

### How the big public GraphQL APIs do it

(From their documentation as of 2026-11-21; not measured in this course.)
- **GitHub**: each user gets a budget of points per hour, computed from the connections' `first`/`last`;
  the schema exposes `rateLimit { cost remaining resetAt }`.
- **Shopify Admin API**: a leaky bucket per app and store; every response carries
  `extensions.cost` with `requestedQueryCost`, `actualQueryCost` and
  `throttleStatus { maximumAvailable, currentlyAvailable, restoreRate }`, and an over-budget request gets
  a `THROTTLED` error.

Lab 10.6 copies Shopify's shape. The point of both: the client can compute how long to wait instead of
retrying blindly.

### Backing off correctly

Before each request: if `currentlyAvailable` < the expected cost, sleep `(cost − available) / restoreRate`.
After a throttle: the error carries the same numbers. Lab 10.6's Spender finished 40 × 140 points through a
1,000-point bucket restoring 1,000 a second in 5.4 s; the theoretical floor is 4.6 s.

## Java build (20 min)

Lab 10.6's `PublicApi`: a servlet filter for the key (401 before GraphQL), a `WebGraphQlInterceptor` that
puts the client in the context, an instrumentation for scopes on mutation fields and the bucket, and
`GET /_admin/usage`.

## Experiment (15 min)

Write `Spender.java`; compare it with a loop of curl calls; read `/_admin/usage` for both.

## Check

1. Why do GraphQL APIs price requests instead of counting them?
2. The review bot (`write:reviews`) posts as ben to club c1. Which rules decide, and what happens?
3. A response says `requestedQueryCost: 140, currentlyAvailable: 60, restoreRate: 50`. How long should the client wait?

<details><summary>Answers</summary>

1. One request can be one field or millions of fetches; a count says nothing about load. Cost tracks the
   work and lets clients plan.
2. The key's scope (allowed) and lab 10.2's rule for the user (ben is not a member): FORBIDDEN.
3. (140 − 60) / 50 = 1.6 seconds.
</details>
