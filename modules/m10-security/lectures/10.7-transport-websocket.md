# 10.7 Transport and WebSocket security

## Hook (2 min)

The starter accepted a socket from `http://evil.test`, acknowledged a forged token, logged every bearer
token it saw, and told the client its recommender's internal host name and live API key.

## Concept (15 min)

### WebSockets authenticate differently

A browser cannot put an `Authorization` header on a WebSocket handshake. graphql-transport-ws sends the
token in the first message, `connection_init`'s payload, and the server must verify it there and refuse the
socket (close `4401 Unauthorized`) if it is bad. Consequences: the token is checked once per socket, so a
long-lived socket outlives the token's `exp` unless the server tracks it; and authorization for each
subscription runs when it starts (lecture 10.2).

### Origins

Browsers send cookies on a cross-site WebSocket upgrade and CORS does not apply to WebSockets the way it
does to `fetch`, so a cookie-authenticated socket that accepts any `Origin` is open to **cross-site WebSocket
hijacking**. Spring refuses cross-origin handshakes by default, *unless CORS allows the origin*: Boot hands
`spring.graphql.cors` to the GraphQL WebSocket handler. Measured (finding 18): no CORS config, only
same-origin sockets; `allowed-origins: https://shelfie.test`, only that origin; `allowed-origin-patterns: "*"`
(the starter), every origin. A permissive CORS line opened the socket.

### CORS is about reading

CORS tells a browser which origins' scripts may read responses. It does not stop a request from being
sent (a simple `text/plain` POST still executes), and it means nothing to curl. Allow your own origins;
never reflect any origin while allowing credentials.

### Secrets in logs, internals in errors

Logs travel further and live longer than requests: never write `Authorization`, cookies, API keys or
sensitive variables. Error messages go to clients: an unresolved exception should be `INTERNAL_ERROR` with
an id that leads to the server log (Spring for GraphQL's default), never the exception's message.
