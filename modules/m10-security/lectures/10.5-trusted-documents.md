# 10.5 Trusted documents

## Hook (2 min)

An attacker copies Shelfie's Home query from the browser's network tab, adds `email` to every member, and
replays it. Every limit from 10.4 says yes: it is cheap. The only question left is: did *we* write this?

## Concept (15 min)

### Allowlist what you ship

For your own clients you know every operation at build time. **Trusted documents** (also called persisted
documents or persisted operations) make that a rule: the client build extracts each operation, hashes it,
and writes a manifest; the server runs only documents in the manifest, by id. The GraphQL Foundation's
Golden Path recommends it for first-party APIs. Effects:

- an attacker cannot shape a query at all: no fan-out, no aliases, no probing fields;
- every operation can be costed, tested and cached in advance;
- requests shrink to an id and variables; parsing and validation run once per document.

### APQ is not trust

Automatic persisted queries (Module 9.6) look similar: a hash instead of text. But APQ *registers any
document* the first time it sees the hash with its text. It is a bandwidth feature. The fork's
`grantBadge` ("only from persisted queries") fell to a document the attacker registered themself. A
trusted-document server refuses an unknown id even with matching text, and refuses a known id sent with
other text.

### What stays open

- **Variables** are still the attacker's: `Club($id)` must still check the caller may see `$id`.
- **Third parties** cannot be in your manifest: a public API needs keys, scopes and budgets (10.6).
- **Development** needs ad-hoc queries: a flag, never on in production.
- **Introspection** is no longer needed in production: clients build against the schema file. Turn it off
  (`spring.graphql.schema.introspection.enabled: false`), knowing it hides little from a determined
  wordlist (lecture 10.8).

### Deploying

New operations ship server first (manifest with the new ids), client second. Old ids stay until no
installed client uses them: mobile apps stay installed for months.

## Java build (20 min)

Lab 10.5: `client/BuildManifest.java` writes Apollo's manifest format (`id` = SHA-256 of the trimmed body);
a `PreparsedDocumentProvider` registered with a `GraphQlSourceBuilderCustomizer` looks up
`extensions.persistedQuery.sha256Hash`, runs the manifest body through `parseAndValidate`, caches it by id,
and refuses everything else with `NOT_TRUSTED`. A request with only a hash arrives with the query text
`PersistedQueryMarker` (finding 14).

## Experiment (10 min)

Capture the Home query, edit it, replay it ad hoc against lab 10.4's server and then against yours. Then
try to register it through APQ.

## Check

1. Why does APQ not stop an attacker, and what does a manifest change?
2. A trusted `Club($id)` runs for anyone. Is authorization still needed?
3. In what order do you deploy a new operation, and why?

<details><summary>Answers</summary>

1. APQ stores whatever document arrives with its own correct hash, so the attacker can register theirs.
   The manifest is fixed by your build: an id outside it, or text that does not hash to the id, is refused.
2. Yes: the variables are the caller's. Trusted documents limit the shapes, not the data each caller may see.
3. Server first (it must know the new id), then the client. Old ids stay until no deployed client sends them.
</details>
