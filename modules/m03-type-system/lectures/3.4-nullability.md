# 3.4 Nullability and lists

## Hook (2 min)

The ratings service is down for ten minutes. Every Shelfie club page is blank: not the rating, the whole
page. One `!` on `averageRating`, and a rating outage became a site outage.

## Concept (15 min)

### Every type is nullable unless it says otherwise

| Type | The field may be null | Items may be null |
|---|---|---|
| `[User]` | yes | yes |
| `[User]!` | no | yes |
| `[User!]` | yes | no |
| `[User!]!` | no | no |

### Null propagation ("bubbling")

When a field errors, or returns null where its type is non-null, the response gets an error with a
`path`, and the null goes to the **nearest nullable ancestor**: the field itself if nullable, otherwise
its parent, and so on. A list item counts as a step. If the walk reaches a non-null root field, `data`
itself is `null`. Sibling root fields are independent.

```
club: Club            <- lands here if everything below is non-null
  currentBook: Book!
    averageRating: Float!   <- throws
```

### Choosing

Make a field nullable when it can be **legitimately absent** (no reviews, no current book) or can
**fail independently** of its parent (another service, another user's data). Keep it non-null when it is
the same row and required (ids, names). Evolution is asymmetric: nullable to non-null later breaks no
client; non-null to nullable breaks every client that stopped checking.

(Semantic non-null, RFC #1065, was a working-group attempt to separate "null because of an error" from
"null on purpose"; it is stalled at RFC 0. Module 7 returns to it.)

## Check (3 min)

1. `members: [User!]!`, one member's `name: String!` throws. What is null?
2. Same with `members: [User]!`?

<details><summary>Answers</summary>

1. The club (the nearest nullable ancestor above the list), or more if `club` is non-null.
2. Only that member's entry in the list.
