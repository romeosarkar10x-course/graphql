# 3.2 Built-in scalars, Java-side

## Hook (2 min)

`JSON.parse('{"id": 9007199254740993}').id` in any browser gives `9007199254740992`. A Java service that
puts its `long` keys into JSON numbers has a client that updates the wrong row, and no error anywhere.

## Concept (15 min)

### The five built-ins

| Scalar | Spec | Java (graphql-java) | Watch out |
|---|---|---|---|
| `Int` | **32-bit** signed | `Integer` | `long` values above 2^31-1 fail to serialise |
| `Float` | double precision | `Double` | not for money (use a decimal scalar, 3.3) |
| `String` | UTF-8 text | `String` | |
| `Boolean` | true/false | `Boolean` | |
| `ID` | serialised as a **String** | `String` | accepts an integer as input, always outputs a string |

### Coercion, both directions

- **Output coercion** (`serialize`): Java value to JSON, during execution. `Long.MAX_VALUE` as `Int` is a
  field error: `Can't serialize value ... Expected a value that can be converted to type 'Int' but it was
  a 'Long'`.
- **Input coercion**: literals during **validation**, variables during **variable coercion**. Both run
  before any resolver. `3000000000` as an `Int` literal: `WrongType ... Expected value to be in the
  integer range`.

### Long IDs, safely

Expose 64-bit keys as `ID`: an opaque string no client rounds or does arithmetic on. Parse incoming IDs
defensively: a malformed ID is "not found", not a 500. Large *counts* are different: they need a 64-bit
number scalar (`Long` from graphql-java-extended-scalars) or a string, depending on the reader.

## Check (3 min)

1. A client sends `{"id": 42}` (a JSON number) for `$id: ID!`. Accepted?
2. Which stage rejects `{ review(id: 3000000000) }` when the argument is `Int!`?

<details><summary>Answers</summary>

1. Yes: `ID` input coercion accepts integers; the resolver receives the string `"42"`.
2. Validation (the literal does not fit `Int`); nothing executes.
