## Concept (15 min)

### Six ideas that make GraphQL GraphQL

1. **The schema is the contract.** A typed description of everything the API can return, written in
   SDL (Schema Definition Language). The reference server's is
   [schema.graphqls](../../../reference/shelfie-ref/src/main/resources/graphql/schema.graphqls):
   ```graphql
   type Club {
     name: String!
     owner: User!
     members(first: Int = 10): [User!]!
     currentBook: Book
   }
   ```
2. **Types form a graph.** `Club → owner → User → clubs → Club`... Fields can take arguments
   (`members(first: 5)`), so every edge can be filtered or capped.
3. **The client chooses the shape.** A query is a selection of paths through that graph; the response
   is exactly that tree, no more.
4. **One endpoint.** Every operation goes to `/graphql`. The URL no longer identifies the resource; the
   document does.
5. **Introspection.** The schema can be queried like data, which is how GraphiQL autocompletes and
   documents itself (lecture 0.3).
6. **Spec vs implementations.** The spec says how a query is validated and executed; graphql-java, Spring
   for GraphQL, gqlgen, Apollo Server are implementations.

### Where the work went

The server still looks up the owner, the members, the book, the reviews and the reviewers. Each field in
the schema has a **resolver** (graphql-java calls it a *data fetcher*): a function that produces that
field's value from its parent. In the reference server:

```java
@SchemaMapping
public User owner(Club club) {                 // resolves Club.owner
    return store.user(club.ownerId()).orElseThrow();
}
```

The joins moved from the client, across the network, to the server, in-process. That is the trade: the
client gets one round trip; the server team now owns resolving *any* shape a client asks for, efficiently
(N+1 queries, Module 9) and safely (expensive queries, Module 10).

### What you lose

- **URL-based HTTP caching.** `GET /api/books/b1` caches in every browser and CDN. `POST /graphql` does
  not (Module 9.5–9.6 win some of it back).
- **Status codes and per-endpoint metrics** mean less (lecture 0.4; Module 16.1).
- **Simplicity:** a schema, a runtime, resolvers, before your first response.

## Check (3 min)

1. Which part of a GraphQL server decides the value of `Club.owner`?
2. Why did REST win at 0 ms latency in the reference measurement?

<details><summary>Answers</summary>

1. The resolver (data fetcher) for `Club.owner`: here the `owner(Club)` method.
2. On localhost round trips cost almost nothing, and GraphQL adds work per request: parsing, validating
   and executing the document. With 11 cheap requests vs 1 slightly dearer one, REST can win. The
   advantage appears when round trips are expensive.
</details>
