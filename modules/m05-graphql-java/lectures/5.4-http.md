# 5.4 Serving over HTTP yourself

## Hook (2 min)

The GraphQL spec says nothing about HTTP. On 2026-11-12 the GraphQL Foundation published the first
edition of the spec that does: [GraphQL over HTTP, September 2026](https://http-spec.graphql.org/September2026/).
A copy is in `_workbench/2026-11-21-m05-probe/`.

## Concept (15 min)

### Requests

| | Rule |
|---|---|
| POST | MUST be supported; body `application/json` with `query` (string), optional `operationName`, `variables` (map), `extensions` (map); unknown keys MUST be ignored |
| GET | MAY be supported; parameters in the URL, `variables` and `extensions` as JSON strings; a mutation over GET MUST be refused (405 RECOMMENDED, with `Allow`) |

### Responses: media type first

The server MUST support `application/graphql-response+json` and MUST respect `Accept`. A legacy client
that only accepts `application/json` gets the same status codes, but 2xx responses carry
`Content-Type: application/json`. Nothing acceptable: 406.

### Status codes

| Situation | Status |
|---|---|
| `data` and no `errors` | 200 |
| `data` and `errors` (partial success) | **294**, a code the spec defines itself, only with its own media type |
| Body is not JSON | 400, not the GraphQL media type |
| Not a well-formed request (`qeury`, `variables: []`) | 422 |
| Document does not parse | 400 |
| Validation fails, operation ambiguous, variables do not coerce | 422 |
| Unsupported method, mutation over GET | 405 with `Allow` |
| Unsupported `Content-Type` | 415 |

Two reasons for codes beyond 200: intermediaries (gateways, logs, alerting) can count failures without
reading bodies, and clients that see the GraphQL media type know the body is GraphQL even on a 4xx.

### The JDK is enough

`com.sun.net.httpserver.HttpServer` with a virtual-thread executor serves this. Keep the GraphQL-over-HTTP
logic in a class that takes method, URL query, headers and body, and returns status, headers and body:
the same class then runs behind Javalin (lab bonus) or anything else.

## Check (3 min)

1. A query returns `data` and one field error. Status for `Accept: application/json`?
2. Why must a JSON parse failure not use `application/graphql-response+json`?

<details><summary>Answers</summary>

1. 200 with `Content-Type: application/json` (294 is only for the GraphQL media type).
2. That media type promises a well-formed GraphQL response; the server could not produce one, and an
   intermediary's error page would look the same.
</details>
