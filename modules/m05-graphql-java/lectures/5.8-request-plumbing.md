# 5.8 Request plumbing

## Hook (2 min)

The same 50-character query, 20,000 times: 55,621 requests per second. Add one cache of parsed
documents: 266,598. Nothing in the fetchers changed.

## Concept (15 min)

### GraphQLContext

One map per request, built with the `ExecutionInput` and visible to every fetcher on every thread:
`env.getGraphQlContext().get("viewer")`. It is the right place for the viewer, the tenant, a request id
or a DataLoader registry. A `ThreadLocal` is not: async fetchers run on other threads (game 5b, B7).

### Caching parsed documents

`PreparsedDocumentProvider.getDocumentAsync(input, parseAndValidate)` is asked for each request's
document. Return a cached `PreparsedDocumentEntry`, or call the function and cache its result.

| Rule | Why |
|---|---|
| Key on the query text, not variables | the same document runs with any values |
| Bound the cache (Caffeine `maximumSize`) | the key is attacker-controlled; unbounded means memory exhaustion |
| One cache per schema | the entry skips validation too |

Clients that inline values instead of using variables make every request a miss: one more reason for
variables, and for persisted queries (Module 9).

### Cancellation

`ExecutionInput.cancel()` sets a flag. graphql-java checks it as it dispatches fields
(`EngineRunningState.throwIfCancelled`) and ends with "Execution has been asked to be cancelled". A
running fetcher is never interrupted: lab 5.8's 1-second query stopped after 303 ms with 3 of 10 slow
fetchers started. To stop sooner, give the backend call its own deadline.

## Check (3 min)

1. Why not key the document cache on query text plus variables?
2. After `cancel()`, does a fetcher in the middle of a JDBC call stop?

<details><summary>Answers</summary>

1. Variables do not change the parsed or validated document; including them only lowers the hit rate.
2. No: cancellation is checked between steps. The JDBC call needs its own timeout.
</details>
