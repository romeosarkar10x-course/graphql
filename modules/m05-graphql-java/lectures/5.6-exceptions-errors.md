# 5.6 Exceptions and errors

## Hook (2 min)

graphql-java's default answer to a bug: `"Exception while fetching data (/e) : Cannot invoke
"String.length()" because "<local3>" is null"`. For a timeout: `"... : ratings-service did not answer in
2000 ms"`. Every exception message goes to the client.

## Concept (15 min)

### Request errors vs field errors

| | When | Response |
|---|---|---|
| Request error | parse, validation, variable coercion | `errors`, no `data` |
| Field error | a fetcher throws or returns a null for a non-null field | `errors` with `path` and `locations`, `data` with nulls |

### Null propagation

A field error makes the field null. If the field is non-null (`mustWork: String!`), that null is itself
an error, so the parent becomes null, and so on up to the first nullable field
([Handling Execution Errors](https://spec.graphql.org/September2025/#sec-Handling-Execution-Errors)).
Lab 5.6: `mustWork` fails and `club` comes back null; `hello` beside it is fine.

### Turning exceptions into errors

`DataFetcherExceptionHandler` gets the exception, path and environment and returns `GraphQLError`s.
`GraphqlErrorBuilder.newError(env)` keeps path and locations; `errorType(...)` takes any
`ErrorClassification`, which shows up as `extensions.classification`.

| Kind | Classification | Client message |
|---|---|---|
| domain (not found, forbidden, invalid) | named | the domain message |
| transient (timeout) | `UNAVAILABLE`, `retryable: true` | generic, no internal names |
| bug | `INTERNAL` | "Internal error (ref …)"; the ref and the exception go to the log |

Module 4.3's rule still holds: failures the product expects belong in the schema as data
(`userErrors`, result unions); errors are for the exceptional.
