# 5.1 The `GraphQL` object

## Hook (2 min)

Every framework in Module 6 ends in the same three lines: build a `GraphQL` object, hand it an
`ExecutionInput`, turn the `ExecutionResult` into a map. This module removes the framework and keeps the
three lines.

## Concept (15 min)

### One request, three phases

| Phase | graphql-java | Fails with | Spec section |
|---|---|---|---|
| Parse | `graphql.parser.Parser` | `InvalidSyntax` (a request error) | [Language](https://spec.graphql.org/September2025/#sec-Language) |
| Validate | `graphql.validation.Validator`, ~30 rules | `ValidationError` (a request error) | [Validation](https://spec.graphql.org/September2025/#sec-Validation) |
| Execute | `ExecutionStrategy` calling your fetchers | field errors, partial data | [Execution](https://spec.graphql.org/September2025/#sec-Execution) |

`GraphQL.execute(input)` runs all three. A request error stops before execution, so the response has
**no `data` key at all**; a field error leaves `data` with nulls in it.

```java
var graphQL = GraphQL.newGraphQL(schema).build();       // build once, share: it is thread-safe
var input = ExecutionInput.newExecutionInput(query).variables(vars).build();
Map<String, Object> response = graphQL.execute(input).toSpecification();
```

`toSpecification()` returns the [Response](https://spec.graphql.org/September2025/#sec-Response) map:
`errors` first when present, `data` only when execution started, `extensions` only when something put
some there.

### Limits before any of your code runs

The parser refuses documents over 15,000 tokens by default: "More than 15,000 'grammar' tokens have
been presented. To prevent Denial Of Service attacks, parsing has been cancelled." A 5,000-field query
(`f0: hello f1: hello ...`) has 15,002. `ParserOptions` changes the limit per call; Module 10 decides
what the limits should be.

## Java build (20 min)

Lab 5.1: `Phases.java` prints the spec map for five queries, then times parse, validate and execute
separately by handing execution a document it already parsed.

## Experiment (15 min)

Time each phase for a 2-field and a 5,000-field query. On the build machine (2026-11-21, course image):
parse 23.5 ms, validate 25.2 ms, execute 33.4 ms for 5,000 fields of `hello`. For trivial fetchers the
front half dominates; with real fetchers execution does.

## Check (3 min)

1. A query has a syntax error. Does the response have `data: null`?
2. Why build the `GraphQL` object once rather than per request?

<details><summary>Answers</summary>

1. No: `data` is absent. Only a request error can remove it; `data: null` means execution ran and a
   field error propagated to the root.
2. Building it is expensive (schema, strategies, instrumentation chain) and it holds no per-request
   state, so one instance serves all threads.
</details>
