## Concept (15 min)

### Types and behaviour live apart

| | Schema-first | Programmatic |
|---|---|---|
| Types | SDL text, `SchemaParser` into a `TypeDefinitionRegistry` | `GraphQLObjectType.newObject()...` |
| Fetchers | `RuntimeWiring`, which fills the code registry | `GraphQLCodeRegistry`, keyed by `FieldCoordinates` |
| Build | `SchemaGenerator.makeExecutableSchema` | `GraphQLSchema.newSchema()` or `FastBuilder` |
| Good for | a contract people read and review | schemas generated from something else |

Either way fetchers sit in the code registry, never on the type objects, so one set of types can be
wired several ways and transformed freely.

### Transforming a schema

`SchemaTransformer.transformSchema(schema, visitor)` walks every element and lets a
`GraphQLTypeVisitorStub` change or delete it: lab 5.7 deletes every field marked `@internal` to make a
public view of an internal schema.

### Building fast

Measured for 2,000 object types (course image, third round): SDL 41.7 ms, `newSchema()` 25.0 ms,
`FastBuilder` 1.3 ms. `FastBuilder` skips the full type traversal and, in 26.1, schema validation
unless you call `withValidation(true)` (checked with `javap`). You must add every type yourself.

A trap found while writing the lab: chaining each type to the next (`T0.next: T1`, `T1.next: T2`, ...)
makes schema building recurse once per link, and from 1,000 links it throws `StackOverflowError`
(`_workbench/2026-11-21-m05-probe/schema-chain-stackoverflow.txt`).
