# 5.3 Async execution

## Hook (2 min)

Ten sibling fields, 200 ms each. graphql-java's query strategy is called `AsyncExecutionStrategy`, and
the query takes 2,003 ms.

## Concept (15 min)

### Async is a property of the fetcher

The strategy dispatches a field, and if the fetcher returned a finished value, moves on; if it returned
an unfinished `CompletableFuture`, it moves on **without waiting**. A fetcher that blocks before
returning has finished by then, so nothing overlaps.

| Fetcher | Executor | 10 x 200 ms (measured, course image) | 1,000 x 200 ms |
|---|---|---|---|
| blocks | none | 2,003 ms | 200 s |
| `supplyAsync(task, pool)` | fixed pool of 4 | 602 ms (3 waves) | 50,036 ms |
| `supplyAsync(task, pool)` | `newVirtualThreadPerTaskExecutor()` | 204 ms | 226 ms |

`supplyAsync(task)` with no executor uses `ForkJoinPool.commonPool()`: cores - 1 threads, shared with
every parallel stream in the JVM, meant for CPU work. Blocking calls do not belong there (game 5b, B1).

### Serial mutations

Mutations use `AsyncSerialExecutionStrategy`: it waits for each root field's future before starting the
next, as the spec's serial execution requires
([Normal and Serial Execution](https://spec.graphql.org/September2025/#sec-Normal-and-Serial-Execution)).
The same async fetchers in a mutation take n x 200 ms, in document order.

### What virtual threads do not fix

They make waiting cheap, not work. A thousand concurrent fetchers still meet a database pool of ten
connections, and a `join()` on a bounded pool can still deadlock it (game 5b, B8).
