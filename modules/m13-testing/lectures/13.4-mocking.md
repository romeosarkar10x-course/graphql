# 13.4 Mocking

## Hook (2 min)

The backend is two sprints away. The screen is due on Friday. Build it against a server that answers any query
on the schema with believable data, then point it at the real one and change nothing. What did the mock hide?

## Concept (15 min)

### Schema-driven mocks

A schema says every field's type, so fake data needs no resolvers. In graphql-java that is a `WiringFactory`
that provides a data fetcher for every field, a type resolver for every interface and union, and a scalar for
every custom scalar. graphql-java ships `MockedWiringFactory`, but it only makes a schema executable: probed, it
answers `club: null` and turns a non-null `search` into an error. A useful mock decides by type (Int, enum,
list, abstract type), then by name (email, url, `*At`, `*Count`, name, title), echoes `id` arguments, sizes lists
by `first`/`last`, and derives every value from the seed and the response path: same request, same answer.

### The switch

Lab 13.4's screen reads `SHELFIE_URL`, so moving from the mock to Shelfie changes no code. It does change the
data: the mock never returns null, and the real Good Omens has no reviews. Mocks hide the states that matter
most to a screen (null, empty, error) unless you ask for them on purpose.

### Named mocks: MockSpec

[MockSpec](https://rfcs.graphql.org/rfcs/MockSpec/) (RFC 0, strawman, opened 2026-02-02) gives those states a
place. An operation marked `@mock` or `@mock(name: "unrated")` is answered from
`__graphql_mocks__/<OperationName>.json`, whose keys are named responses (`__default__`, `unrated`, an error
state), each a full GraphQL response. A missing file is generated; a mock that no longer fits its operation must
be detected (the RFC: run the operation with no resolvers and the mock as root value). It is written for clients;
mini-project 13.10 reads it in a server so any client can use the files.

### Mocking a downstream API

When your service calls someone else's GraphQL API, a schema mock answers anything, including the wrong
request. **WireMock** (3.13.2; the 4.x line is still beta) is a real HTTP server the test programs: stubs match
on the request body (`matchingJsonPath("$.operationName", equalTo("UserReviews"))`, the variables), so a client
that sends the wrong variable gets no answer and fails. Stub the bad days too: errors with `data: null`.

## Check

1. Why derive mock values from the response path instead of a random generator?
2. What does a WireMock stub catch that a schema-driven mock server cannot?
3. Your screen works on the mock and crashes on Shelfie. Name the likely cause.

<details><summary>Answers</summary>

1. The same request gives the same response (stable tests and screenshots), positions differ, and there is no
   state to reset; a seed changes everything at once.
2. A wrong request: stubs match on operation name and variables, so a client sending the wrong user id gets no
   stub and fails, where a schema mock happily answers.
3. A null or empty value the mock never produced (an average with no reviews, an empty list), or an error
   response the mock never sent.
