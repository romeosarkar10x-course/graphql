# 13.5 Schema checks in CI

## Hook (2 min)

A pull request makes `books(titleContains:)` required. The diff tool says "1 breaking change". Nobody knows
which app breaks, so the change is merged with an override, and Android search stops working. The pipeline must
say *who* breaks and *why*.

## Concept (15 min)

### Three checks, one gate

1. **Snapshot**: the schema is committed (`src/main/resources/graphql/*.graphqls`, or an introspection dump for
   code-first servers); a pull request changes it visibly.
2. **Breaking-change detection**: diff the base branch's schema against the pull request's. graphql-java's
   `SchemaDiff` reports `DiffEvent`s with a level (BREAKING, DANGEROUS, INFO), a category (MISSING, STRICTER,
   INVALID, ADDITION, DIFFERENT, DEPRECATION_ADDED...), the type, the field and the components.
3. **Operation validation**: every known client document validated against the new schema
   ([Validation](https://spec.graphql.org/September2025/#sec-Validation)): the check that says *which* operation
   breaks, at which line.

### Usage decides

A registry (GraphQL Hive, Apollo GraphOS) records which operations clients really send and fails a check only
for changes that touch operations seen recently; a breaking change nobody uses is allowed. With the clients'
documents in the repository you can do the same offline: walk each operation against the old schema, collect the
coordinates it uses (`Book.isbn`, `CreateReviewInput.headline`, `Visibility`, `Club.members(first:)`), and match
each diff event to the operations that use it. Precision matters: a changed default reaches only operations that
leave the argument out. (Hive and GraphOS are described here, not run: both need an account.)

### Where the tools disagree (probed)

| Change | graphql-java SchemaDiff | graphql-inspector 7.0.2 |
|---|---|---|
| field deprecated | DANGEROUS | safe |
| default 10 to 5 | DANGEROUS, message cut off ("of type 'Club") | dangerous, "changed from 10 to 5" |
| new argument `String! = "title"` | BREAKING | dangerous |
| new enum value | DANGEROUS | dangerous |

The third row is a false alarm by the spec's own rule: an argument is required only when it is non-null **and**
has no default. An old query without it validated, and the resolver received `"title"` (probed). Game 13.9 is
built on rows like this.

### In GitHub Actions

graphql-inspector's action (`graphql-hive/graphql-inspector@master`, inputs `schema: 'main:path'`,
`fail-on-breaking`, `annotation-level`) annotates the diff line by line in the pull request. A second job runs
your usage-aware check and writes its output to the job summary when it fails, so the red cross explains itself.
The course cannot run GitHub Actions; `bin/course inspector diff old new` runs the same inspector locally.

## Experiment (15 min)

Open a pull request with a breaking change; the pipeline must explain why it failed. Locally: run your check on
scenario 05 (a required argument) and read the output as a reviewer would: which app, which file and line, what
its users see.

## Check

1. Why diff against the base branch's schema rather than the previous commit's?
2. A field nobody queries is removed. Should the build fail?
3. Why validate client operations when you already have a diff?

<details><summary>Answers</summary>

1. The pull request is merged into the base branch: that is the schema clients run against, whatever happened in
   the branch's own history.
2. Not for known clients (a registry would allow it), but report it: unknown clients (partners, old app versions)
   may use it, and a public API may prefer deprecation first.
3. The diff says what changed; validation says which operation breaks, where, and with which error, including
   breaks the diff rates lower (a nullable variable used where a non-null is now expected).

</details>
