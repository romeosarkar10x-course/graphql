# 13.6 Linting and architecture rules

## Hook (2 min)

Five changes: a controller that reads a repository, a service that imports graphql-java, a tab and trailing
spaces, a `page_count` field, a `@deprecated` with no reason. The code compiles, the schema loads, the tests
pass. Which tool catches which?

## Concept (15 min)

### Schema lint: graphql-eslint

[graphql-eslint](https://the-guild.dev/graphql/eslint/docs) runs ESLint rules over `.graphql`/`.graphqls`
files, so it does not care what language the server is written in. Rules that need the whole schema
(`no-unreachable-types`, `strict-id-in-types`) need it loaded: the parser's `graphQLConfig.schema`, or a
`graphql.config.yml`. Useful rules for a schema: `naming-convention` (PascalCase types, camelCase fields,
UPPER_CASE enum values, no `get` prefixes on queries), `require-description`, `require-deprecation-reason`,
`no-unreachable-types`. Probed: `flat/schema-recommended` reported 66 problems on Shelfie's schema, which has a
description on everything: 64 because it wants block `"""` descriptions, 2 because payload types have no `id`.
A lint config is a house style; choose it, then enforce it.

### Code format: Spotless

`spotless-maven-plugin` checks (`spotless:check`) and fixes (`spotless:apply`) formatting, bound to `verify` so
CI fails on it. Hygiene steps (unused imports, trailing whitespace, tabs) leave the code's layout alone; a
formatter step (palantir-java-format, google-java-format) owns every line after one big reformat commit, and
ends style arguments in reviews.

### Architecture rules: ArchUnit

ArchUnit reads compiled classes and asserts on their dependencies, as plain JUnit tests:
`layeredArchitecture()` for graph → service → store, `noClasses().that().resideInAPackage("..graph..")
.should().dependOnClassesThat().areAnnotatedWith(Repository.class)` for "controllers never touch
repositories", `noFields().should().beAnnotatedWith(Autowired.class)`. Probed: the layered rule alone allowed a
controller to call a repository, because graph may use store (it returns the store's records); the narrow rule
caught it. ArchUnit 1.5.1 reads Java 25 class files.

### Banned patterns

Each tool owns a layer: the schema (names, descriptions, deprecations), the source (format, imports), the
architecture (dependencies). None of them replaces tests, and in lab 13.6 the compiler caught none of the five.

## Java build (20 min)

Lab 13.6: `eslint.config.mjs` from `flat/schema-recommended` plus house rules, Spotless in the pom, an
`ArchitectureTest` with four rules; Node.js runs inside the course container from `.cache/node`.

## Experiment (15 min)

Introduce 5 violations; see which tool catches each. The grader does it on a copy of your project and prints the
table; in the reference run each violation was caught by exactly one tool, and the compiler by none.

## Check

1. Why is graphql-eslint useful to a Java team?
2. A layered rule passes, yet a controller calls a repository. How?
3. Why bind `spotless:check` to `verify` instead of running `spotless:apply` in CI?

<details><summary>Answers</summary>

1. It reads the SDL, the contract every client sees, so the same rules apply whatever the server's language,
   and front-end teams already use the same tool on their operations.
2. The layers allow graph to use store (records), and the repository lives in store: the rule permits the
   dependency. Ban the specific dependency (classes annotated `@Repository`).
3. CI must not change code behind the author's back; it fails, and the author runs `apply` and commits.

</details>
