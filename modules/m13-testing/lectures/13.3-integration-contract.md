# 13.3 Integration and contract tests

## Hook (2 min)

The repository mock returns reviews newest first because the test told it to. The SQL says `ASC`. Every test
passes; every user sees the oldest reviews. Only a real database runs SQL.

## Concept (15 min)

### Real dependencies, per test run

**Testcontainers** starts real services in Docker for a test run and removes them after: PostgreSQL, Kafka,
Keycloak, the same images as the course services. `@Container` on a static field shares one container per test
class. Spring Boot's `@ServiceConnection` wires a container's connection details into the app with no
properties; for Keycloak, an issuer URI goes in through `@DynamicPropertySource`. Failsafe runs `*IT` classes in
`mvn verify`, after surefire's fast `*Test` classes.

In the course, tests run inside a container with no Docker of their own, so `bin/course` mounts the host's
Docker socket for labs whose `lab.json` needs `"docker"` (only those: the socket controls the host's Docker).
Testcontainers 2.0.5 then reached the containers through the course network's gateway with no settings.
Measured on one machine: PostgreSQL up in 0.9 s, Kafka in 2 s, Keycloak with the course realm in about 11 s;
lab 13.3's five ITs run in about 16 s.

### What only the real thing catches

SQL (ordering, `ROUND(AVG(...), 2)`, a unique constraint that turns a second review into "already reviewed"),
topic names and serialisation on a real broker, token signatures and audiences from a real identity provider.
Probed: through `@AutoConfigureHttpGraphQlTester` alone, a valid bearer token never reached the controller
(`UNAUTHORIZED`), while the same test on a real port authenticated. The cause (Spring Boot 4.2.0): the tester
wraps a `WebTestClient`, and with no `MockMvc` bean in the context Boot binds that client straight to the
application context (`MockMvcWebTestClient.bindToApplicationContext`), which builds a MockMvc **without servlet
filters**, so Spring Security's filter chain never runs. Add `@AutoConfigureMockMvc` next to it: Boot then binds
the client to its own MockMvc, which registers the filters, and the token authenticates. The lesson stands: the
closer a test is to a real client, the fewer such surprises.

### Black-box contracts

A **contract test** knows only the interface: requests in, responses out. Hurl files are language-neutral, so the
same `contract.hurl` runs against Module 5's graphql-java server and Module 13's Spring server. Writing one shows
what is really shared: both refuse a rating of 6 and an anonymous review; only Module 13 trims bodies and refuses
a second review, so those cannot be in a shared contract. Behaviour and protocol are different contracts: on
Module 5's 25-check GraphQL-over-HTTP audit, the Module 5 server passes 25 and the Spring server 11 (lab 13.3's
run), while both pass all 14 behaviour checks.

## Check

1. What does `@ServiceConnection` replace?
2. Why can a Hurl contract not catch "the event went to the wrong topic"?
3. Two servers pass the same behaviour contract and score 25 and 11 on the HTTP audit. Are they compatible?

<details><summary>Answers</summary>

1. The `spring.datasource.*` or `spring.kafka.bootstrap-servers` properties you would otherwise set from the
   container's mapped host and port.
2. Kafka is not part of its interface: it sees requests and responses only. That is what the integration test,
   with a consumer on the real broker, is for.
3. For clients that send well-formed requests, yes: same data. For clients that rely on status codes and media
   types for errors (422, `application/graphql-response+json`), no.
