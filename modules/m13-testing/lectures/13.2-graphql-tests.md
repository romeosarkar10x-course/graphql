# 13.2 GraphQL-aware tests

## Hook (2 min)

A subscription test that sleeps for a second passes on your laptop and fails in CI one run in ten. Assert that
`reviewAdded` emits exactly three events, in order, and make it fail only when the server is wrong.

## Concept (15 min)

### Documents in files, assertions on paths

Spring for GraphQL's testers load `src/test/resources/graphql-test/<name>.graphql` with `documentName("name")`:
the same documents a client sends, reviewed like code. Assert on **paths**:
`path("club.members[*].handle").entityList(String.class).containsExactly(...)` pins what the test cares about,
so adding a field to the document does not break it. `errors().verify()` fails on any error you did not expect.

### Error assertions

GraphQL errors are data: classification (`extensions.classification`), path, locations, message.
`errors().expect(e -> e.getErrorType() == NOT_FOUND && e.getPath().equals("review"))` filters the ones you
expect; `errors().satisfy(...)` gives you the list. Rule violations returned as `userErrors` are not GraphQL
errors at all: test them as data.

### Three testers, three depths

| Tester | Goes through | Sees |
|---|---|---|
| `ExecutionGraphQlServiceTester` (`@AutoConfigureGraphQlTester`) | `ExecutionGraphQlService` | execution, no HTTP, no `WebGraphQlInterceptor` |
| `HttpGraphQlTester` (`@AutoConfigureHttpGraphQlTester`, MockMvc; or a `WebTestClient` on a port) | the web layer | headers, interceptors, HTTP status |
| `WebSocketGraphQlTester` on a random port | graphql-transport-ws | subscriptions, connection init |

Probed in lab 13.2: a broken `ViewerInterceptor` (wrong header name) failed only the `HttpGraphQlTester` tests;
every in-process test, which sets the viewer on the execution input itself, passed.

### Subscriptions in tests

Shelfie's feed is a hot multicast sink: events published before the server registers the subscription are lost.
`StepVerifier.create(flux).then(publish)` runs `publish` after the **client** subscribes, which is not when the
server has. Wait for a signal (`ReviewService.liveSubscribers() >= 1`) rather than sleeping, bound the flux with
`take(Duration)`, and `expectNext(a, b, c).verifyComplete()`: a fourth event or a missing one both fail. Publish one
event to another book to prove the filter.

### DGS

DGS's `DgsQueryExecutor` runs a document in-process and reads results with JsonPath
(`executeAndExtractJsonPath(query, "data.club")`). DGS 12 runs on Spring for GraphQL, so for HTTP and WebSocket
the Spring testers above apply to a DGS app too.

## Experiment (15 min)

Assert a subscription emits exactly 3 events in order. Then run the grader: it makes the subscription stop after
two, leak another book's reviews, and reorder events. All three must turn the test red; three runs in a row of
the reference test passed.

## Check

1. Which tester would miss a bug in a `WebGraphQlInterceptor`, and why?
2. Why is `Thread.sleep` the wrong fix for a flaky subscription test?
3. When is comparing the whole JSON response better than path assertions?

<details><summary>Answers</summary>

1. `ExecutionGraphQlServiceTester`: it calls `ExecutionGraphQlService` directly, so the web layer, interceptors
   included, never runs.
2. It guesses how long the server needs; on a slower machine the guess is wrong. Wait for an observable signal
   that the subscription is registered.
3. When the exact response is the contract (a snapshot of a public API, or errors must not appear anywhere);
   the cost is rewriting expected files whenever a field is added.

</details>
