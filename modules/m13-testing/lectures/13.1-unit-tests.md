# 13.1 Unit tests

## Hook (2 min)

Delete the body of a resolver and replace it with a call that drops one argument. Every service test still
passes. Which tests notice? In lab 13.1, only the one that sent a GraphQL document.

## Concept (15 min)

### Test the rules apart from GraphQL

Shelfie under test ([contract/shelfie-app](../contract/shelfie-app/)) is three layers: `graph/` controllers
translate GraphQL, `service/` holds the rules, `store/` holds data. The rules (rating 1 to 5, a trimmed body,
one review per user per book, every broken rule reported, the average rounded half up) have many cases and no
GraphQL in them, so they get **unit tests**: construct `ReviewService` with mocked repositories and a fixed
`Clock`, no Spring context, a few milliseconds per test. Edges matter more than the middle: 5 and 6, 500 and 501
characters, spaces only.

### Mock what is slow or has side effects

Mockito stands in for `ReviewRepository` (writes, ids). `CatalogRepository` is plain seed data, so the catalogue
tests use the real one: a real value is cheaper and less brittle than a mock that knows its API.

### The slice: schema and controllers, no server

Some behaviour exists only inside graphql-java's execution: an argument's default (`first: Int = 20`), the
argument names, the viewer from `GraphQLContext`, the error classification `ErrorAdvice` adds. A
`@GraphQlTest` **slice** starts just that: the schema, `@Controller` and `@ControllerAdvice` beans and a
`GraphQlTester`, no web server and no `WebGraphQlInterceptor`. It does not scan `@Service` or `@Repository`:
supply them in a `@TestConfiguration`. It does read `@Bean` methods on the `@SpringBootApplication` class
(probed: a second `Clock` bean failed with "overriding is disabled").

### Do the tests catch bugs?

Coverage says a line ran, not that a test would fail if it were wrong. Lab 13.1 grades tests by **planted bugs**
(mutants): eight one-line changes, each of which some test must fail on. Game 13.8 lets PIT do the same at scale.

## Java build (20 min)

Lab 13.1: `ReviewServiceTest` and `CatalogServiceTest` (JUnit 6, Mockito, AssertJ, parameterised bounds,
`StepVerifier` for the feed) and `ShelfieControllerSliceTest` (`@GraphQlTest` over four controllers and the
advice, the viewer set with `configureExecutionInput`).

## Experiment (15 min)

The grader deletes `Query.books`' filter on its way to the service (mutant U5). Only
`ShelfieControllerSliceTest.booksPassesTheFilterAndTheCapThrough` failed in the reference suite; every service
test passed. Then try it yourself: break `ReviewController` so a missing viewer posts as `u1`, and see which
layer's tests go red.

## Check

1. Why test `ReviewService` without Spring?
2. What can a `@GraphQlTest` slice see that a unit test of the controller method cannot?
3. Your coverage is 100% and a planted bug survives. How?

<details><summary>Answers</summary>

1. The rules have many cases and no GraphQL in them; without a context each test is milliseconds, so the edges
   (5/6, 500/501) cost nothing, and a failure points at the rule, not at wiring.
2. Everything graphql-java does around the method: schema defaults, argument binding by name, `GraphQLContext`
   values, exception handling by `@GraphQlExceptionHandler`, and the shape of the response.
3. The line ran, but no test asserted on what it produced (a result unchecked, a boundary never tested), so the
   changed line gave the same pass.
