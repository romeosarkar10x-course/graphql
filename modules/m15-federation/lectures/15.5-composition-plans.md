# 15.5 Composition and query plans

## Hook (2 min)

`{ club(id: "c1") { members { reviews { book { title } } } } }`: three clubs' worth of members, every review,
every book. A naive gateway makes hundreds of calls. The router made four: one per subgraph.

## Concept (15 min)

### Composition as a CI gate

Every pull request that touches a subgraph composes the whole graph. On failure the build stops and the last good
supergraph stays in place; on success the new supergraph is the artifact the router loads. Registries (GraphOS,
Hive, Cosmo) add history and client usage checks on top; the composition rules are the same.

### Query plans

The router turns a query into a **plan**: `Fetch` nodes (one subgraph request), `Sequence`, `Parallel`, and
`Flatten` (put `_entities` results back at a path). Ask for it: Apollo Router with `Apollo-Expose-Query-Plan: true`
(plugin `experimental.expose_query_plan`), Hive Router with `hive-expose-query-plan: true`
(`query_planner.allow_expose`). The course reduces both to steps
([contract/PlanSteps.java](../contract/PlanSteps.java)). Measured on the contract graph, both routers:

| Query | Steps |
|---|---|
| a book's title | `[catalog]` |
| a book and its reviews | `[catalog] [reviews]` |
| latest reviews, author handle (`@provides`) | `[reviews]` |
| latest reviews, author name and book title | `[reviews] [accounts, catalog]` |
| a club's books with `weeksToRead` (`@requires pages`) | `[clubs] [accounts, catalog] [clubs]` |
| the N+1 query above | `[clubs] [accounts, reviews] [catalog]`: 1 request each |

Rules: the root field's owner first; a new step when a field needs keys only an earlier step returns; parallel
when the same step's keys suffice; `@provides` removes a step, `@requires` adds one.

### What is left of N+1

The router removes N+1 between subgraphs. Inside each `_entities` call it is the subgraph's job (15.4), and depth
still costs sequential steps: latency grows with steps, not items.

## Check

1. Why does `weeksToRead` come back to clubs in a third step?
2. Why does adding `handle` to a review's author not add a step?
3. Where does N+1 survive in a federated graph?

<details><summary>Answers</summary>

1. `@requires(fields: "pages")`: catalog must answer `pages` first, then clubs computes from it.
2. reviews `@provides(fields: "handle")` on `Review.author`.
3. Inside subgraphs' resolvers, and as steps for deep queries.
