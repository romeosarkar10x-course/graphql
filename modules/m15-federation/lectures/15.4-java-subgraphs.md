# 15.4 Java subgraphs

## Hook (2 min)

A router sends reviews one `_entities` request with fifteen `Review` representations. Your resolver can answer it
with one database query or fifteen. Spring for GraphQL gives you three ways to write it; they cost 1, 1 and 15.

## Concept (15 min)

### Wiring

Spring for GraphQL 2.x (Boot 4.2.0 here) with federation-jvm (`com.apollographql.federation:
federation-graphql-java-support:7.0.0`, not in Boot's BOM: pin it):

```java
@Bean FederationSchemaFactory schemaFactory() { return new FederationSchemaFactory(); }
@Bean GraphQlSourceBuilderCustomizer federation(FederationSchemaFactory f) {
    return b -> b.schemaFactory(f::createGraphQLSchema);
}
```

The factory adds `_service { sdl }`, `_entities` and `_Any`. Start-up fails with `Unmapped entity types: 'Review'`
for any `@key` type without an `@EntityMapping`: a useful checklist.

### @EntityMapping, three forms

- **Single**: `@EntityMapping Book book(@Argument String id)`: called once per representation.
- **List**: `@EntityMapping List<Book> book(@Argument List<String> idList)`, or `List<Map<String, Object>>` for
  the whole representations (two keys); return in order, `null` for unknown.
- **DataLoader**: `@EntityMapping CompletableFuture<Review> review(@Argument String id, DataLoader<String, Review>
  loader)`, a loader registered with `BatchLoaderRegistry`; it can be shared with ordinary fields.

Probed: an unknown id from the single or DataLoader form raises `RepresentationNotResolvedException`, which
becomes `INTERNAL_ERROR` unless a `@GraphQlExceptionHandler` maps it (the course maps it to `NOT_FOUND`); the List
form returns `null` quietly. A reactive `Flux` loader with a `null` element fails the whole batch.

The router already collects every representation at a path into **one** `_entities` request per subgraph per
step; batching inside the subgraph is yours.

### DGS and Kotlin

DGS (Netflix): `@DgsEntityFetcher(name = "Show")` taking the representation map, batching through a DataLoader.
graphql-kotlin 11 (Expedia; federation-jvm 7.0.0 and graphql-java 26.1 inside): `toFederatedSchema`,
`@KeyDirective`, `FederatedTypeSuspendResolver`. It links federation v2.13 by default, which the course's composer
(v2.0 to v2.9) refuses: pin the version with `@LinkDirective` (mini-project 15.10).

## Java build (20 min)

Lab 15.4: catalog with the List form (both keys), reviews with DataLoader and single forms, and
`reviews`/`reviewCount`/`averageRating` sharing one named loader.

## Experiment (15 min)

Count store queries per `_entities` call. Measured: five books through the single form, 6 queries against 1 with
the List form; `reviews` and friends unbatched over the latest reviews' books, 15 against 1.

## Check

1. Why does the router not send one `_entities` request per review?
2. Which form for a key that may be `id` or `isbn`?
3. What does a client see for an unknown entity with no exception handler?

<details><summary>Answers</summary>

1. It plans per path: every representation at one path goes in one request per subgraph.
2. The List form with whole representations, so one query can look up both kinds.
3. `INTERNAL_ERROR` on that path, from `RepresentationNotResolvedException`.

</details>
