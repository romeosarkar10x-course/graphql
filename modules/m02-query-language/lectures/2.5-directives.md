# 2.5 Directives in operations

## Hook (2 min)

The September 2025 spec says `@skip` on a subscription's root field is invalid. Ask graphql-java 26.1
and it says `valid`. Swap the literal for a variable and the validator throws a
`NullPointerException`. Today you find out who is right, and why it matters.

## Concept (12 min)

### `@skip` and `@include`

```graphql
query ClubCard($id: ID!, $detailed: Boolean! = false) {
  club(id: $id) {
    name
    teaser: members(first: 1) @skip(if: $detailed) { name }
    ...ClubDetails @include(if: $detailed)
  }
}
```

They go on fields, fragment spreads and inline fragments. A field is included only if `@skip` is false
**and** `@include` is true; neither wins. `{ hello @skip(if: false) @include(if: false) }` returns
`{"data": {}}`.

### Directive locations

Every directive declares where it may appear. Executable locations are `QUERY`, `MUTATION`,
`SUBSCRIPTION`, `FIELD`, `FRAGMENT_DEFINITION`, `FRAGMENT_SPREAD`, `INLINE_FRAGMENT` and
`VARIABLE_DEFINITION` (`query Q($a: Int @someDirective)`). Put one in the wrong place:

`query Q @include(if: true) { hello }` gives `MisplacedDirective : Directive 'include' not allowed here`.

### Custom executable directives

A server may declare its own, `directive @uppercase on FIELD`, and implement it by wrapping data
fetchers (Module 14). Undeclared ones fail validation: `UnknownDirective : Unknown directive 'uppercase'`.
The reference server declares `@defer` too; Module 11 uses it.

### The subscription root rule

A subscription must have exactly one root field, and the server must know which one during
validation, before it has variables. So the spec ("Single Root Field") forbids `@skip` and `@include`
in a subscription's root selection set. Measured on graphql-java 26.1
(`_workbench/2026-11-21-m02-probe/validate-sub.txt`):

| Document | graphql-java 26.1 | Spec |
|---|---|---|
| `subscription { meetupScheduled(clubId: "c1") @skip(if: false) { id } }` | valid | invalid |
| the same with `@skip(if: $off)` and `$off: Boolean = false` | `NullPointerException` in the validator; HTTP 500 from the reference server | invalid |
| two root fields | `SubscriptionMultipleRootFields` | invalid |

Implementations lag the spec. When they disagree, the spec is the contract and the implementation has
a bug: Module 17 shows where to report one.

## Check (3 min)

1. `@include(if:)` takes `Boolean!`. Could `$detailed` be declared as plain `Boolean`? As `Boolean = false`?
2. `teaser: members(first: 1) @skip(if: $detailed)` and `members(first: 3)` inside the included
   fragment: why no conflict?

<details><summary>Answers</summary>

1. Plain `Boolean`: no, `VariableTypeMismatch ... type 'Boolean' used in position expecting type
   'Boolean!'`. `Boolean = false`: yes; the spec allows a nullable variable into a non-null position
   when it has a non-null default (measured: `_workbench/2026-11-21-m02-probe/probe-nullable-var.txt`).
   An explicit `"detailed": null` would then be a runtime error, which is why the lab uses `Boolean!`.
2. Different response keys (`teaser` and `members`). Without the alias they would conflict even though
   only one is ever included: validation does not know the variable's value.
</details>
